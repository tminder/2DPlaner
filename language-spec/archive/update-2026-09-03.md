## The three standing core-product questions, all closed (D-071–D-074, 2026-09-01)

`open-questions.md` had flagged F-001 and F-002 as this project's own top priority since early on — both are now built, not just designed:

- **F-001, the last unbuilt placement mode: `flush`.** An element can now be both contained inside its parent *and* pinned flush against whichever wall it's nearest to (a window or door built into a wall, as opposed to a sofa merely kept inside a room) — the third and last of the three placement modes this question had been tracking. Layers cleanly on top of the existing containment clamp rather than replacing it.
- **F-002's last open promise: drag-editability for a module-composed element.** A prior session's `wall-with-door-module.js` prototype proved a module could *generate* structure from a few parameters, but nothing about dragging one of its generated pieces had ever been tried. Now it has: dragging a generated wall segment moves the whole composite; dragging its door slides along the wall, clamped to the wall's own span. A real, structural bug was found and fixed along the way — the drag system's own throwaway reparse never ran the same composite-expansion step `rerender()` does, so a synthesized child simply didn't exist in the tree being edited. `parse()` and `parseExpanded()` are now properly split so every caller gets the tree it actually expects.
- **F-017: undo/redo.** A real design fork was surfaced and discussed before writing any code: should a drag or a context-menu action be made to participate in the textarea's own native undo stack, or should this be a separate mechanism? Checked directly, not assumed — making a programmatic edit register on the native stack requires focusing the textarea first, which pops the on-screen keyboard on a touch device on every single drag, undermining the mobile pass from two days earlier. Built instead as a small, explicit history of full-text snapshots, with both keyboard shortcuts and toolbar buttons (keyboard alone would leave undo unreachable on mobile, where Ctrl+Z isn't a concept).
- **F-016: Duplicate.** Clones an element's whole subtree with every id freshly renamed, internal corner-references and connections correctly repointed. Scale, requested alongside it, was deliberately not bundled in — it raises real, still-open design questions of its own (what "scale" means for a shape built from shared corners, no existing gesture to hang a resize handle off of) and was asked about directly rather than guessed at.

## Stepping back: an independent review of the language itself

Everything above was building against the language as it already exists. What followed was different in kind: a deliberate pause to ask whether the language's own *design* is actually good, using critique criteria chosen independently of the project's own self-stated goals (domain coverage, whether the hand-rolled parser is the only real spec, failure-mode consistency, how cleanly the module system's extension points are scoped) rather than just checking the language against its own stated aims.

The concrete test: hand-authoring a real Fiat Ducato campervan interior plan, and separately comparing it against one an independent AI (given the identical prompt, no access to this project) produced on its own. Both attempts, plus a "what if positions were snapped to a grid instead" thought experiment prompted by a real spreadsheet-based van layout, surfaced fourteen new, genuine findings — recorded as `open-questions.md` F-018 through F-031, several confirmed by actually running the plan in a real browser rather than only reading the code:

- A container whose children fully cover it becomes unreachable to click (F-019).
- `childPlacement` silently only ever checked a node's *immediate* parent, not any more distant ancestor (F-020).
- Two always-shown labels near each other render directly on top of one another (F-018).
- Collision and containment settings are only ever enforced *during* a drag, never against a plan's own initial, as-authored layout — confirmed the hard way, since the independently-generated comparison plan had `allowCollisions: false` set and still shipped several unflagged overlaps (F-022).
- Two elements can silently share an id, and a drag on one then corrupts the *other's* position instead (F-028).
- No formal schema exists anywhere — the parser is the only real specification, which is exactly why an unrecognized `shape` value, an unimplemented `rotation`, and a `flush` declared without its required `placement` all fail completely silently (F-023).
- No rotation, no version marker on the plan format, the same "pinned to an edge, slides, clamps" logic independently rebuilt four times with no shared code, no way to reach an element hidden behind another, no way to share a style across several elements without repeating it, no multi-select, no version marker — each recorded as its own entry (F-021, F-024–F-027, F-029), two of the least-designed ones (a reusable component concept, discrete grid-snapped dragging) deliberately left for later rather than sketched prematurely (F-030, F-031).

Three follow-up requests were logged the same way, not designed yet: a Word-like icon menu for the App's own toolbar (F-032), exporting a plan as a flattened image (F-033, since built — see below), and sharing a plan with someone else, split explicitly into two different exposure levels — a static view versus handing over the editable source (F-034).

`planning/project-overview.md` was refreshed the same day with a full status snapshot and a severity-ranked recommendation for what to build next from this list.

## Six real bugs, found and fixed (D-075, D-077–D-079)

Rather than working through the fourteen findings by number, the two most severe were tackled first — the ones in the same class as "a setting silently doesn't do what it claims" — and the fixes kept surfacing further real bugs along the way, not just theoretical ones.

**A load-time validation pass (F-022, with F-028 folded in).** No new mechanism was needed — the collision and containment checks already used mid-drag (and already known correct) just needed a second call site: run once against a freshly loaded plan's own resting layout, with results shown in a small dedicated panel rather than only surfacing whatever a user happens to stumble into by dragging. Re-run against the original comparison plan, it found 36 real overlapping pairs — far more than the two originally spot-checked by hand. Duplicate element ids are now caught the same way. Building this surfaced its own bug: the shared boundary-check math falsely flagged a deliberately `flush` element as *not* contained, a floating-point artifact of how ray-casting handles a point sitting exactly on an edge — fixed with a small tolerance, mirroring a principle collision-checking already used ("resting exactly flush is legitimate, not a violation").

**Click-cycling through stacked elements (F-019, and F-021's core case with it).** Rather than building the cheapest fix for F-019 alone, the underlying mechanism question was asked directly: what actually solves this for the long term? A parent-reaching shortcut would have fixed only F-019's specific case; a mechanism based on *what's actually painted at a pixel* (via the browser's own `elementsFromPoint`) fixes both F-019 and the broader F-021 with the same code, since it doesn't care whether the reason two things overlap is a parent/child relationship or pure coincidence. A repeated click at the same spot now steps through everything stacked there, wrapping back to the top.

**`childPlacement` now searches upward through every ancestor (F-020).** A grandchild nested two levels under a container that declared "keep everything inside me" could previously be dragged arbitrarily far outside it, with zero warning — the check only ever consulted the *immediate* parent. Fixed at both places that shared the bug: the drag-time clamp, and the just-built load-time validation pass, which had the identical one-level gap and would otherwise have kept missing a static (never-dragged) violation of exactly this kind.

**Always-shown labels nudge apart instead of overlapping (F-018).** A small, iterative pass measures each `show: "always"` label's real rendered size and pushes any two that overlap apart, a few iterations, using the browser's own layout rather than estimating text width. Building it surfaced a second bug: label text and the (much more numerous) per-edge length labels turned out to share one flat markup group, so an early version of the fix dragged edge-length labels away from the walls they describe too — fixed by giving label text its own nested group so only that moves.

## Two small, directly requested additions (D-076, D-080)

**A favicon, and a link back to the marketing site from the App.** The favicon was designed from the site's own existing visual language — the homepage's floor-plan-shaped wordmark glyph and its fixed color palette — rather than a generic icon, rendered from an SVG and packaged into the sizes browsers actually need. Placed independently into all seven of the site's served directories rather than referenced from one shared path, since the App is deployed to two different hosts with two different path structures. The App's own header title is now a link to the real marketing site, since the App itself is reachable from either host and "back to the website" should mean the same place either way.

**Export as image (F-033).** Two new buttons alongside the existing code export: `Export PNG…` and `Export SVG…`. Always exports the whole plan at its natural best fit, regardless of whatever the editor's camera happens to be panned/zoomed to at the moment — checked directly by exporting while deliberately scrolled into one corner. A real bug was found by actually opening the first exported file: labels that are only ever invisible in the live app because of a page-level CSS rule rendered fully visible in the export, since that rule doesn't travel with a standalone file — fixed by dropping them from the export outright rather than trying to carry the rule along.

## Where things stand

- **Every fix in this update was verified against a real, running browser** (Playwright, headless Chromium) before being called done — this project's standing practice, applied without exception across four days of very different kinds of changes now: language/renderer features, a load-time validation pass, hit-testing, text layout, and file export.
- **All three of this project's own original top-priority open questions (F-001, F-002, plus F-016/F-017 alongside them) are closed.** The open-questions list has grown, not shrunk, but for a different reason: a deliberate review surfaced real gaps that testing alone would likely never have found, rather than this being scope creep.
- **Fourteen new findings from the language review, six fixed, eight still open** — the remaining ones range from cheap and well-scoped (a version marker on the plan format, F-025) to genuinely large and undesigned (a formal schema, F-023; a reusable component concept, F-030). `planning/open-questions.md` and the refreshed `planning/project-overview.md` are the current, living account of exactly what's left and in what order it's worth picking up.
