Everything built since [update-2026-10-07.md](update-2026-10-07.md). ## A tech-debt cleanup streak (D-186–D-190)

Five items picked up one after another, no design forks, each confirmed directly before building: `clampToContainment`/`checkContainment` now share one "is this a rect child" check instead of two copy-typed copies (D-186); `handleRendered`'s six unrelated jobs — geometry, overlay DOM, view box, selection visuals, the stack-hint badge — split into six named functions (D-187); a dozen independent `try { } catch { }` wrappers around `localStorage`/`sessionStorage` calls reduced to three shared helpers (D-188); the wall-with-door composite's synthesized segment ids now check against every id already in the plan before being used, closing a silent-collision risk the normal duplicate-id check never covered since these ids are synthesized after parsing (D-189); and a suspected bug in how that same composite handles a non-zero `position` was investigated directly and found not to exist at all — the comment claiming otherwise was wrong, not the code (D-190).

## Trademark risk recorded, a real Terms & Privacy page (D-191, D-192)

Checked directly, not assumed clear: no existing conflicting trademark for "Planagonia," but Patagonia (the outdoor brand) has a real, documented history of enforcement action against phonetically similar names in unrelated categories — a genuine risk, shown to the user and recorded rather than dismissed or acted on prematurely. Formal registration stays deferred until there's real revenue to justify it.

Separately, the hosted account/cloud-sync service — real accounts, real email addresses, already live — had nothing anywhere governing it beyond a source-code license. A new plain-language Terms & Privacy page states exactly what the service collects, where it's stored, and how to get it deleted, grounded in the actual verified technical facts rather than invented policy, linked from every registration form and the site-wide footer.

## `documentation/` → `language-spec/` (D-193)

The AI-facing plan-language spec folder had been confusingly named `documentation/` ever since `site-docs/` (the human-facing docs) was added — same folder, genuinely different audiences, no longer saying so with the name alone. Renamed via `git mv`, every real reference across the repo fixed; historical mentions inside already-written decisions were deliberately left as-is, describing what was true when they were written.

## Code is the source of truth, applied to its own last exception (D-194, D-195)

Requested directly: anchor "the code is always the master" as a sharpened, explicit rule in `core-aims.md` — clarified that an interaction writing to the code is fine (that's the expected bidirectional sync), the rule is about the *other* direction: what's rendered and what a menu shows must always be read back from the code, never a separately-tracked flag. Turning this into a real taxonomy (core / community / external modules) surfaced a genuine inconsistency: Interactivity, Code Highlighting, and the Layers panel were still force-injected into every plan regardless of what it declared — the one deliberate exception left over from much earlier. Removed outright; every shipped example now declares them explicitly, and every test now declares them by default too.

## The four shipped examples, reviewed and filled out (D-196)

Checked against the full feature list: Utility was already distinct, but Apartment and Campervan overlapped thematically, and no example anywhere demonstrated the wall-with-door module at all — a real gap for something that's been fully built and documented for a while. Apartment gained a real door and the Connections toggle made visible by default; Utility gained a declared grid, fittingly for an *electrical* grid plan; Campervan gained the collision-override mechanism, which immediately surfaced a real, previously-unnoticed geometric overlap in its own layout, fixed with a realistic justification rather than quietly reshuffled. No two examples share a signature feature anymore.

## Display units become real plan content; the camera gets its own module (D-197, D-198)

The metric/imperial display toggle used to live in `localStorage`, invisible to the plan's own code — now it's `settings.displayUnit`, written and read exactly like Grid or Connections, closing the one display toggle that had drifted from Core Aim 1's own rule now that the rule has been sharpened to say exactly that.

Separately: "Fit shouldn't be part of the interactivity module" turned out not to be a three-line move — pan, wheel-zoom, pinch-zoom, Fit, and the scale bar all share one mutable "where's the camera" state, so the real unit of extraction was all five together, not Fit alone. Now its own `view-module.js`, with a careful, several-small-discoveries walk through what could and couldn't be separated without duplicating shared state (recorded as a new open question, F-055, rather than solved speculatively).

## Doors: a real swing arc, a standalone element, and a plugin point for new element types (D-199)

The old door was a dashed line that "made little sense" — replaced with the real architectural convention, a quarter-circle swing arc, built as a genuinely new shape kind rather than a special case. A door no longer needs to live inside a wall-with-door composite either — it's a freely placeable standalone element now. Alongside it, a new `core.registerElementPreset` API lets any module add its own entry to the New Element menu, with the same automatic cleanup-on-unload every other module extension point already has.

## Registration stopped confirming which emails already exist (D-200)

`forgot-password.php` already returned an identical response regardless of whether an email was registered — `register.php` did the opposite for the one case that mattered, relaying WordPress's own "this email is taken" rejection straight back. Fixed to match: the same response either way, with a real account getting a fresh verification email sent either way too.

## Users can author and host their own modules (D-201)

The app already loads any module from any URL — "creating a module" only ever meant giving someone a place to paste their own JavaScript and a stable URL serving it back. A new dashboard, a new database table, and two endpoints (one authenticated for managing your own, one public and unauthenticated for serving the raw code a `module "..."` declaration actually loads) — "private vs. public" is deliberately just a label for now, not enforced access control, stated plainly in the UI rather than implying a guarantee that doesn't exist.

## A parser-accuracy fix: editing a property now works regardless of formatting (D-202)

Every property edit from the right-click menu — placement, flush, label, style — located its target with a regex that only matched a property sitting alone on its own line. Nothing in the plan language actually requires that formatting; a property written mid-line (legal, just unusual) silently broke every one of those edits, either doing nothing or inserting a stale duplicate alongside the untouched original. Rewritten to walk real tokens, mirroring the actual parser's own grammar — which also fixed two related bugs found along the way, not separately reported: a same-named key nested inside a value could previously false-match, and a trailing comment used to get silently deleted alongside an edited property.

## The header's "which tab is active" cue, seven rounds (D-204, D-205, D-208, D-211, D-213–D-215)

A long-running saga, each round a real, reported problem with the version before it, not scope creep: a plain color shift was too low-contrast to read (D-204); there was no baseline at all to interrupt (D-205); the logo itself (the default tab) never got the same treatment, so the line still showed through on every normal page load (D-208); the "cover the line with a matching background" mechanism depended on sub-pixel alignment that flex layout doesn't guarantee, visible as faint remnants once zoomed in (D-211, rebuilt as independent per-element borders); that version left gaps with no line at all in the spots nothing was told to draw one, so it was rebuilt a third time as one real continuous line with a JS-measured gap that moves with whichever tab is active (D-213); that version measured its own gap against the wrong font (the fallback, before the real webfont finished loading), correcting itself only once you touched a tab (D-214); and finally a small, genuinely separate bug — the logo's own math was correct but looked like a stray floating mark at the page edge, fixed with one special case (D-215). Each round checked directly against a live screenshot, several at 3x zoom, before being called done.

## The account area collapses to one icon; modules move onto one shared page (D-206, D-221)

The signed-in account area had grown to four always-visible header children competing for space. Save to Cloud moved into the File menu alongside Import/Export; everything else collapsed into one profile icon with a flyout (Profile, Custom modules, Sign out) reusing the exact same hover-or-tap mechanism Export/Grid's own flyouts already had.

Later, on direct request to merge "user modules und alle modules auf eine Seite" — the public module store and a signed-in user's own module dashboard now live together on one page, `/modules/`, reading the same shared session the app already uses. The old, now-redundant dashboard on the account page was removed outright, not left duplicated.

## The shipped apartment example's door, twice (D-207, D-209)

First pass: the door's open leaf geometrically overlapped the bed, and the opening itself ran past the end of its own wall — both real, confirmed-by-the-actual-math bugs, fixed with a swing-direction and position correction. Raised again immediately after shipping: the deeper problem was that the "wall" the door lived in was never a real wall at all, just a short stub dividing nothing. Rebuilt properly — the room's entire boundary is now four explicit wall segments with a real door cut into the one that needed it, matching this project's own documented canonical pattern for how `wall-with-door` is supposed to be used.

## Smaller fixes along the way (D-210, D-212)

A stack-hint badge's own earlier de-duplication fix left a confusing blank line where an element's name should have been — now a styled "(shown above)" placeholder instead of empty space (D-210). And a whole session's worth of fixes turned out to have never reached GitHub Pages at all — `scripts/deploy.sh` only ever pushes to the custom-domain server over SSH, with no concept of the second live host `docs/` is also deployed to; `git push origin master` is now a standing, explicit step at the end of every deploy pass that touches `docs/`, not an afterthought (D-212).

## A documentation and SEO audit (D-216, D-217)

Checked all four maintained documentation surfaces against the live code rather than assumed current: the human-facing docs and language spec were genuinely accurate, but the architecture document was badly stale — still describing both backend services as "not built yet," weeks after they went live. Rewritten throughout. Separately: Open Graph and Twitter Card tags added to every public page, a new shared preview image rendered in the site's own visual style, and the App itself gained the title/description/canonical tag it had been missing since it was added to the sitemap.

## The homepage, rewritten around who actually reads it (D-218)

The homepage led with "a floor plan is code" and showed raw source text above the rendered drawing — the right pitch for a developer, not this product's actual primary audience: someone who wants to sketch a layout quickly while staying in full control of it. Reworked around the real tension that audience has (a quick sketch is normally imprecise; a precise plan is normally slow) and the actual promise: "As fast as a sketch. As exact as a plan." The rendered drawing now leads visually, with the code as a clearly labeled secondary detail, not hidden.

## A real logo, site-wide (D-219, D-223)

Every page's "logo" had been a plain unicode character with zero visual relationship to the actual, carefully designed favicon — the two had never matched. Five directions sketched and compared at actual favicon size before picking the simplest one that kept the product's own visual metaphor, rolled out to all 15 places the old glyph appeared, plus a homepage nav decluttered to just what a first-time visitor actually needs. A follow-up caught a real color bug: the generated favicon had used the dark-mode amber value even for the light-mode default everyone actually sees first.

## The blog gets filterable categories (D-220)

Every post already carried a topic label that was never surfaced on the index — now shown inline and filterable via three pills, reusing an already-existing taxonomy rather than inventing a new one.

## New elements paint in front and attach to the mouse until placed (D-222)

A freshly inserted element used to always insert as its target's *first* child, meaning it could render behind an already-existing sibling — fixed to insert last instead. On a real pointer (mouse, not touch), picking a shape from the New Element menu now arms a ghost that tracks the cursor until the next click places it, instead of landing at one fixed default position every time.

## Grid/Snap's own Size field follows the Units toggle too (D-224)

A small, direct follow-up gap: the metric/imperial display toggle already converted every dimension label on screen, but the Grid and Snap flyouts' own numeric Size field stayed in raw meters regardless. Now it follows the same toggle everything else does.

## A full account/auth audit, a live production incident, and the project's first backend test coverage (D-225–D-234)

The single biggest thread of this update. Requested directly as a full top-to-bottom re-check of the registration/login flow, it uncovered and fixed a long chain of real issues, several only found by actually using the live flow rather than reading the code: a signed-in user can now change their own display name, having confirmed directly that the real sign-in *username* can never be changed at all — a WordPress limitation, not a missing feature (D-225). Clicking the emailed verification link now signs the visitor in directly instead of making them retype a generated credential by hand (D-226). `/profile/` was renamed to `/account/` site-wide — "Profile" never fit a page with no public-facing content at all (D-227). The registration form's password field was removed entirely, once it became clear the typed password was never the credential anything actually signs in with (D-228).

**A real production incident happened live, mid-session, and was fixed on the spot**: a user's own account — with a real saved plan — turned out to have a WordPress account that had been deleted outside the app at some point, leaving an orphaned local database row that blocked re-registration with a raw, unhandled PHP error instead of a clean message. Diagnosed directly against the live database, fixed with a careful, transactional migration that preserved the saved plan, and the underlying code bug (an exception that could leak server details to a visitor) fixed too (D-229). The `/modules/` page's own "Your modules" section, buried below a long public list, got its own tab once that was reported as the actual problem (D-230). And the browser's own "save this password?" prompt, which had silently stopped appearing, started working again once a line that cleared the password field immediately after sign-in was removed (D-231).

**The whole backend went from zero automated coverage to a real CI-only integration suite**, deliberately run against an actual throwaway WordPress + MySQL stack rather than a mock of one — several of this project's own real bugs (WordPress's Application Passwords being server-generated-only, a username field that silently wasn't the real username) were genuine WordPress behavior a hand-built fake would never have caught. Took four real CI debugging rounds to get the fixture itself right, each failure traced to a confirmed cause (service-container networking, Application Passwords' own HTTPS requirement) rather than worked around blindly. Coverage now spans registration, verification, sign-in, plans, modules, display-name changes, forgot-password, and both rate limits (D-232, D-233).

**Finally, raised in passing ("brauchen wir überhaupt ein Passwort fürs Login?"): an equally-prominent "Sign in via email" option**, reusing the same magic-link mechanism the verification flow already had rather than inventing a new one. In the same conversation, a real iPhone bug was reported — Export's own flyout menu "hidden behind" the code editor — and took **four separate rounds against the user's own real device** to actually fix, since nothing about any of it reproduced in Chromium's touch emulation or even a real desktop WebKit browser: the flyout wasn't opening at all (a bare `<div>` doesn't reliably get a touch-synthesized click on iOS Safari, fixed via `pointerup`), then opened but could double-fire a toggle underneath it, then opened but was clipped to the header's own bounds (a `position: fixed` element trapped inside a horizontally-scrolling container, a known iOS rendering bug), then visibly jumped into position a frame late. Each round diagnosed from the user's own precise live description, not guessed at (D-234).
