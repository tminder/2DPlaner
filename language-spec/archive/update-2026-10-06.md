## Modules can add their own header button (D-172)

Closed a question D-157 had deliberately left open until a second real need appeared: `core.registerHeaderAction({ id, label, title, onClick })` lets a loaded module add a single-click button to the header. The one real open question — whether this needs a trust gate beyond the existing untrusted-module confirmation dialog — was asked directly and resolved: no additional gate. A module already has full, unsandboxed page access regardless (the same standing tradeoff this whole module system has always made), so gating one specific API would be theater, not real protection. The actual answer is visible provenance instead: module-added buttons land in a dedicated "Modules" tab by default and render as plain, icon-free text — visually distinct from every native button by construction. A same-day follow-up extended this further: a button can instead land inside an existing File/Edit/View tab, at a chosen position relative to another button, while keeping that same plain-text styling regardless of where it ends up.

## The module-loading story: three rounds of getting it right (D-173, D-174, D-175, D-176)

This is worth reading as one continuous sequence, not four separate items — each round corrected something the previous one got wrong, found through direct, honest bug reports rather than discovered independently.

**Round one (D-173):** a full audit of every shipped module, asking plainly which ones belong in "core" (always loaded) versus optional. `grid-module.js` and `annotations-module.js` had been force-loaded into *every* plan since early on, regardless of whether that plan used anything they render — real waste for the common case of a plan using neither. The fix made them *content-triggered*: loaded automatically, but only when the plan's own parsed content actually used a relevant property (`settings.grid`, `label`/`dimensions`/`edgeLengths`). This also closed a known inconsistency: `wall-with-door-module.js` had needed an explicit declaration for the identical reason grid didn't, now treated the same way.

**Round two (D-174), the same day:** a sharper rule stated directly — module loading should be decided purely by a plan's own code, never by a UI interaction like a button click. This reopened `hierarchy-module.js`'s own long-standing click-triggered load (behind the header's Layers button) as the one remaining exception. Since there's no plan-content signal for "this plan wants a layers panel" the way grid/annotations each have one, it joined the always-loaded core set instead — the Layers button now only ever toggles visibility of an already-loaded panel.

**Round three (D-175), reported as two live bugs:** "the Modules tab shows but stays empty" and "modules load that don't appear in the plan's own code." Neither reproduced in a fresh browser session — until the real rule was stated plainly: a module should load *exactly* when `module "x"` is literally written in the plan's own text. Round one's content-inference (loading `annotations-module.js` because a `label` property existed, with no `module "..."` line anywhere) turned out to be precisely that complaint, accurately described — not a caching artifact. Reverted back to requiring an explicit declaration for every non-core module, applied uniformly with no special cases left between any of them. The app's own Grid/Connections/Dimensions header toggles were updated to write that declaration automatically the moment they turn a setting on, so the built-in UI never hits the resulting "used a property but forgot to declare its module" gap — recorded honestly as a real, accepted tradeoff for hand-written plans, not silently reintroduced. A related fix landed the same round: a module's header button (D-172) is now automatically removed when that module gets deactivated, even if the module's own cleanup code forgets to do it itself.

**Round four (D-176):** the *other* half of the original two-part bug report turned out to be a completely different, genuine bug — not a loading-logic issue at all. The Modules tab's own `hidden` attribute was being correctly set the entire time; a CSS rule (`.menu-tab-btn { display: flex }`, present since long before any of this) was silently overriding the browser's own default hidden-means-invisible behavior, because author stylesheet rules always beat the browser's built-in ones regardless of specificity. Two earlier rounds of "can't reproduce" had checked the attribute, which was always correct, and never checked whether the tab was actually visible on screen. One explicit CSS rule fixed it; a new test now checks real rendered visibility, not just the attribute, specifically so this exact class of miss can't happen silently again.

## A plan-wide units setting (D-177)

`settings.units: "m"` (the default) or `"none"` lets a plan declare its own numbers without a per-value `m` suffix on every single literal. Asked directly which of two real implementations was wanted before building either: pure notation (values always mean meters internally, exactly as today — this only changes whether the app's own freshly-written literals carry an explicit suffix) versus a genuine unit conversion (`"ft"` meaning every bare number gets reinterpreted as feet on every read, touching core rendering, drag math, and every module that reads a numeric property). The notation-only version was chosen — the plan language's own long-standing "stays metric internally, forever" position is completely unaffected either way. All three non-blank shipped examples now declare `units: "m"` and have every `m`-suffixed literal in their own source stripped bare, to actually demonstrate the feature rather than just support it.
