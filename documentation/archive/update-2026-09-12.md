# Update — 2026-09-12

Everything built since [update-2026-09-07.md](update-2026-09-07.md), across several working sessions from 2026-09-07 through 2026-09-12 — one of the longest continuous stretches of work this project has had. It covers a lot of ground: grid and snap finally becoming fully independent settings after three separate passes at the relationship between them, five real header revisions settling into today's shape (then two more targeted additions on top), the right-click menu rebuilt as a radial menu, structural reparenting closing a long-open question, a whole mobile-friendliness pass (reported directly, bug by bug), a metric/imperial display toggle, a new way to insert elements from the header, and a selection-visuals change replacing DOM reordering with dimming. As before, this is a readable summary, not a replacement for [planning/decisions.md](../../planning/decisions.md) — every `D-xxx` reference points at that entry for the full reasoning.

## At a glance

- **Grid and Snap are now fully independent settings**, the end point of three successive passes: D-122 first coupled them tightly (declaring a grid forced snapping); D-149 partly decoupled visibility from snapping; D-161 finished the job — Snap is its own `settings.snap` object with its own size, and the header's Snap button is the sole source of truth for whether it's on, full stop.
- **The header went through five full revisions to reach a stable shape** (D-128–D-132), then grew two more real additions on top: the "Fit" button moved out of the viewer and into the header (D-156), and a new "New Element" flyout under Edit lets someone insert a generic shape (Line/Rectangle/Circle/Polygon) without hand-typing it (D-162, corrected to generic shapes after an initial furniture-preset pass, D-163).
- **The right-click menu was rebuilt as a radial menu** (D-145) after first adding right-click "Connect to…" and a 5-item cap (D-144) — round icon buttons around the click point, nested groups blooming as a second ring, polished twice more (D-146, D-147) before D-152 found and fixed the one thing none of that exercised: it never actually worked on touch.
- **Structural reparenting shipped, closing F-012.** D-148 made "No placement" genuinely detach an element into its grandparent; D-150 generalized that to an arbitrary drop target via Shift-drag. D-154 later unified the two mechanics (and a separately-duplicated candidate-validity check) once the duplication crossed this project's own "third time, now share it" threshold.
- **A dedicated mobile-friendliness pass, every fix reported directly**: header overflow, iOS input zoom, an off-screen flyout (D-151); wrap-vs-scroll revised after feedback, surfacing and fixing two real regressions along the way (D-153); three more adjustments — the viewer filling its full area, more compact tabs, Layers becoming its own mobile tab (D-155); and a flyout that vanished the instant the mouse moved toward it (D-158).
- **A metric/imperial display toggle** (D-160) — the plan language itself stays metric forever; only the scale bar and dimension labels can now show feet/inches, a deliberate architectural line kept clean by a Plan-mode review before writing any code.
- **Selecting a covered element no longer reorders the DOM to bring it to front** — it now dims whatever's currently painted in front of it instead (D-164), replacing a mechanic that had stood since D-086. Caught its own real bug along the way: sharing a CSS class with an unrelated hover-highlight mechanism broke both.
- **The test suite has grown from 110 (last update) to 206**, still catching real bugs in this window's own new work before they shipped, not just legacy ones.

## Grid and Snap, three passes to full independence (D-122, D-149, D-156, D-159, D-161)

**D-122** first built grid-snapped dragging: declaring a grid made every drag/resize hard-snap to its own size, deliberately coupled — "no second flag" — at the time. **D-149** partly decoupled that: `snap: false` could show a grid without forcing snap, `layer: "none"` could keep snap with no visible pattern, `layer: "front"` + `opacity` put a semi-transparent grid *over* the plan, and the header's Grid toggle grew a flyout editing `type`/`size` directly. **D-159** finished editing every remaining grid sub-setting from the menu — Layer (Behind shapes / In front / Hidden) and Opacity joined Type/Size, closing F-042 for grid specifically.

That still left one real, reported bug: **declaring a grid at all silently kept snapping on by default**, regardless of a new Snap button D-156 had just added — the button could turn snapping *on* but, confusingly, never *off* while a grid was declared. **D-161** fixed this properly: `settings.snap` is now its own object (`{ size: ... }`, the same presence-means-on shape `grid` already uses), read with zero remaining dependency on `grid` in either direction, with its own flyout Size field independent of the Grid flyout's own. The old `grid.snap` sub-key is simply inert now, not read anywhere — a deliberate, reported-as-wanted behavior change, not an oversight.

## The header: five revisions to a stable shape, then two real additions (D-128–D-133, D-156, D-162, D-163)

The header went through five full revisions before settling — unified buttons → a two-row ribbon → hover-flyout tabs → docked-and-permanent → the logo replacing a dedicated File tab (D-128 through D-132) — then had its icons unified to inline Lucide SVGs, replacing a mix of emoji and Unicode glyphs (D-133). All of that predates this update's own new work, but two genuine new capabilities landed on top of that stable shape:

- **The "Fit" button moved out of the viewer and into the header's View tab** (D-156), reachable the same way `#hierarchy-panel` already was — a stable, hidden-by-default slot core provides, unhidden and wired by the module that actually owns the behavior. Found and fixed a real bug along the way: the relocated button silently jumped back into the viewer on the very next render, because the code that re-appends floating overlay elements after every render hadn't been told the button didn't live there anymore.
- **A new "New Element" flyout under Edit** (D-162) lets someone insert a fresh element without hand-typing it. The first pass offered furniture presets carried over from the bundled example plan (Bed, Desk, Table, ...) — reported back immediately as the wrong scope, corrected in **D-163** to the language's own four generic shape kinds (Line, Rectangle, Circle, Polygon) instead, which is what actually belongs in general-purpose app chrome.

## The right-click menu, rebuilt as a radial menu (D-144–D-147, D-152)

D-144 first added right-click "Connect to…" (previously only reachable via Ctrl/Cmd-drag) and capped the existing list-style menu at 5 top-level items. Per direct feedback, **D-145 replaced that whole list menu with a radial menu** — round icon buttons arranged around the click point, nested groups blooming outward as a second ring — followed by two polish passes: **D-146** (touch driving a real right-click, a real select-on-right-click bug, bigger buttons, an opening animation, a centered CSS-only tooltip) and **D-147** (a group ring no longer replaying the first ring's own opening animation). **D-152** later found and fixed the one thing none of this had actually exercised: "Connect to…" never worked on touch at all, because its target resolution relied on hover state a tap never produces — fixed by resolving the target fresh from the tap's own point instead of trusting a value only hover ever populated.

## Structural reparenting closes F-012, then gets unified (D-148, D-150, D-154)

**D-148** made "No placement (moves freely)" genuinely detach an element from its parent — promoted one level up, into the grandparent, with its position rewritten to stay visually put — instead of just clearing its placement properties where it sat. **D-150** generalized that exact strip→reparse→splice mechanic to an *arbitrary* drop target, triggered by an ordinary drag held with Shift through release, finally closing F-012's own long-unproven "moving the whole element block plus a coordinate transform" question. Two real bugs were found and fixed live before either shipped: an async-render race that hid the live highlight, and a single-line-formatted target nesting the moved element as a sibling instead of a child.

Building both the same way left real duplication behind — the identical "valid reparent/relate candidate" check hand-copied four times across the file, and `clearPlacement`/`reparentElement` carrying two near-identical copies of the same splice mechanic. **D-154** unified both once the duplication passed this project's own "third time, share it" threshold: one shared `isValidGestureTarget` helper, and `clearPlacement` now delegates its own grandparent case to `reparentElement` directly — provably equivalent, verified before the change, not just assumed.

## A dedicated mobile-friendliness pass, every fix reported directly (D-151, D-153, D-155, D-158)

**D-151** fixed four separate mobile issues in one pass: the header ribbon overflowing narrow screens, iOS Safari zooming in on any input under 16px, a flyout submenu opening off-screen, and a too-generous tab/toolbar gap. **D-153** revised the overflow fix per direct feedback — a single row that scrolls horizontally instead of wrapping onto a second line — and found two further real regressions live in the process: the CSS fix for the scroll accidentally clipped every flyout in the header (fixed by switching flyout positioning from CSS to JS), and the row was silently squeezing every button to fit instead of actually scrolling at all (fixed with `flex-shrink: 0`). **D-155** made three more directly-requested adjustments: the mobile viewer now fills its entire available area, the Code/Viewer tab buttons are more compact and properly theme-matched, and Layers became its own mobile tab instead of being entirely unreachable there. **D-158** later found and fixed a genuinely broken flyout: the same JS-positioned submenu from D-153 vanished the instant the mouse moved from the button toward it, because of a small gap between the two that broke the hover chain — fixed by attaching the flyout flush against its own button instead.

## Metric/imperial display, decided as a plan-mode review before any code (D-160)

A metric/imperial toggle was requested with the underlying design question genuinely open: should imperial be a display-only conversion, or should the language itself accept feet/inches as authored input? Decided directly, with the user deferring to "the long-term best solution": **the plan language stays metric-only forever** — a purpose-built language meant primarily for AI authorship (D-003) benefits from staying unambiguous, and portability shouldn't depend on whoever happens to be viewing it. A Plan-mode review (including an independent subagent check) caught a real rounding edge case before it ever became a live bug — 11.96 inches rounding to "12.0" has to roll into the next whole foot, not print literally. The new header toggle only ever affects the scale bar and any dimension/edge-length labels; the plan's own source text is provably untouched by it.

## Selection no longer reorders the DOM — it dims what's in front instead (D-164, D-165)

Selecting a covered/stacked element used to raise its whole subtree to the end of the SVG (D-086) so it would visually paint on top of whatever covered it — a real DOM reorder. Reported directly as the wrong approach: **D-164** replaces this with dimming whatever's actually painted in front of the selection at a point where the two genuinely overlap, leaving paint order untouched entirely. Its own test suite caught a real bug before shipping: reusing the same CSS class an unrelated hover-highlight feature already used meant moving the mouse away after selecting something silently cleared the new dim too — fixed with a genuinely separate class, same visual effect, independent lifecycle. **D-165** narrowed an adjacent resize-handle case the same week: a plain two-point line no longer gets 4 redundant bounding-box scale handles alongside its own 2 endpoint handles, since with only two points a "scale" is never anything more than a roundabout way of moving one endpoint — scoped precisely to the two-point case, so a longer multi-segment path keeps its own scale handles where they're still genuinely useful.
