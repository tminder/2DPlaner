# Update — 2026-08-31

A snapshot of everything built since the project's first commit (2026-08-30, 10:07) through today. Planagonia went from a set of throwaway language/renderer experiments to a live, publicly reachable product at `planagonia.com` — app, docs, profile, self-service registration, and a mobile-friendly pass — in that span. This is a readable summary, not a replacement for [planning/decisions.md](../../planning/decisions.md); every `D-xxx` reference below points at that entry for the full reasoning, the alternatives considered, and the exact bugs found along the way.

## At a glance

- **The language, renderer, and interaction model** (elements, connections, shared corners, drag-and-drop, modules) were designed and validated through 17 throwaway prototypes, then combined into the first real product.
- **The app** (`docs/`, live at `/app`) has zoom/pan, collision and containment checking, syntax highlighting, multiple named plans, and module-provided compositions.
- **A real backend went live**: WordPress-based auth (Application Passwords only, no plugins) and a PHP/MySQL storage service, both self-hosted, both tested end to end against the live server — not just written and assumed to work.
- **The whole site launched**: Homepage, human-facing Docs, Profile, and the App now live at `planagonia.com/{app,docs,profile}` with a proper sitemap, rate limiting, and self-service registration with email verification.
- **A mobile-friendly pass**, kept explicitly desktop-first, plus a run of real bugs found by actually testing in a browser rather than trusting the diff — a stale camera-fit box, a click-suppression bug, a CSS cascade-order mistake, a hidden-module regression.

## Language, renderer, and interactivity — the foundation (Prototypes 01–17)

Before any of this was a product, it was a sequence of small, disposable prototypes, each answering one question (D-002: plan the whole concept before committing to a build order). The core design that came out of it:

- **Two primitives only** (D-013): `Element` (a positioned, optionally shaped/styled node, optionally with children) and `Connection` (a relationship between two elements). No built-in "wall" or "door" concept — those emerge from composition.
- **Shared corner-node references** (D-018): two shapes can reference the *same* position element for a shared point (e.g. two wall segments meeting at a corner), rather than duplicating coordinates — dragging the corner moves everything that references it, for free. Later refined: literal points are the default; a corner reference is only worth its cost when a point is genuinely shared by more than one shape.
- **Drag-and-drop is a hard constraint, not a feature bolted on**: every visual element must be representable and editable via drag (D-009), including solving expressions backward when possible (D-012) and falling back to a visible warning when not (D-015).
- **Modules** (D-011/D-020) can add rendering, interactivity, or higher-level compositions, loaded via `module "name-or-url"` in a plan's own preamble. Proven three separate ways: a new shape renderer (Prototype 12), all of drag/select/connect/context-menu moved into a module (Prototype 14, D-031), and a module synthesizing child elements before render (Prototype 17, D-046 — "wall with a door" from four parameters instead of hand-authored corners).
- **Realism and collision checks** (D-020/D-041): self-intersecting polygons are rejected outright; sibling collisions are clamped (slide along whatever's blocking the drag) rather than hard-rejected, after an earlier hard-reject version was tried and reverted.
- **Containment** (D-032/D-044): an element can be constrained to stay inside its parent (`childPlacement`/`placement: "inside"`), with an exact clamp for a rect-in-rect and a slower but safe tangent-slide fallback otherwise.

A recurring theme worth naming: several of the real bugs in this phase were only found by combining everything into one working plan and actually using it (D-027's unified prototype) or by testing directly in a browser — not by re-reading the code. A negative-number literal silently losing its drag-editable span, a connection-adjacency test confusing "touching" with "containing," a viewBox auto-fit that visually cancelled out a rigid-translation drag entirely — none of these were caught by inspection alone.

## First hosted app (`docs/`, D-034 onward)

The first version meant to actually be used, not thrown away: local storage + file export, no accounts yet, deployed via GitHub Pages. Built on top of it since:

- **Viewer zoom/pan and a scale bar** (D-035), with the camera never resetting mid-drag.
- **Per-edge dimensions** (D-038) and **code syntax highlighting** (D-042) as their own modules, following D-039's precedent of keeping optional presentation out of core.
- **Multiple named plans**, saved client-side (D-043), with an example picker (Studio Apartment, Utility Connection, Blank).
- **Right-click context menu** (D-030) with Delete Element, and dangling-reference protection (can't delete a shared corner still in use, can't delete the plan root).

## Backend: real auth and storage (D-047–D-051)

The two-day arc's biggest single piece of new infrastructure. Auth is a self-hosted, headless WordPress instance running **WordPress core only — zero plugins** (D-019), verified via Application Passwords (never the account's real login password — REST API Basic Auth has never accepted anything else, confirmed the hard way more than once this session). Storage is a separate, minimal service that only knows `{id, name, text, updatedAt}` per plan — deliberately not routed through WordPress, to keep its attack surface small.

**The originally-designed Node.js storage service turned out to be undeployable** on the actual target hosting — its SSH environment is a minimal jail missing `libc.so.6`, so no Node binary can run there at all, discovered by actually connecting and testing rather than assumed from the hosting panel (D-048). Rewritten in PHP against real MySQL instead; the Node version stays in the repo as a design reference for a future VPS. Once live, deployment moved off the original `test.planagonia.com` staging host onto a dedicated `api.planagonia.com` subdomain (D-053).

Everything here was tested against the real, deployed server — a full login → CRUD round trip, multi-user isolation (a second account genuinely can't see the first account's plans), CORS, and the `docs/` frontend actually calling it (D-050).

## Site launch (D-052–D-057)

`planagonia.com` went from a stock hosting placeholder to a real, structured site:

- **Domain mapping decided**: path-based (`planagonia.com/app`, `/docs`, `/profile`), not subdomain-per-section — chosen partly on SEO grounds (Homepage and Docs should reinforce each other's relevance; App and Profile have no organic-search reason to prefer either shape).
- **Homepage, human-facing Docs, and Profile built and deployed** — Docs specifically written for a person using the app, distinct from `documentation/`'s AI-facing language spec.
- **Rate limiting** added to the storage service (D-056), closing a gap flagged since D-022: login attempts capped per IP, plan operations capped per signed-in user.
- **A dynamically generated `sitemap.xml`** (D-057), built from the actual pages' file-modification times rather than hand-maintained.
- Pre-production hardening along the way: an exposed test credential rotated, backend/staging hosts excluded from search indexing (D-052).

## Self-service registration (D-058, refined same day)

Visitors can create their own account — email + password, a confirmation email, then a working credential shown once on the confirmation page. Two real design questions were resolved directly with the user before writing code: a dedicated bot-Administrator WordPress account is needed to create other users via the REST API (no narrower role exists in WP core without custom code, which D-019 avoids), and email verification is required before an account can sign in.

**A real bug found only by testing the complete flow, not the pieces in isolation:** the first version let a visitor's own chosen password become their WordPress login password, on the assumption it could be used to sign in afterward — but Basic Auth has never accepted anything but an Application Password. Fixed by generating that Application Password at verification time instead, shown once, so a visitor never needs to know their account has a separate "real" password at all.

**Refined the same day, prompted by a direct question ("why username?")**: the registration form originally also asked for a username. Removed — WordPress needs one internally, but a visitor doesn't need to invent it. `derive_username()` now builds one from the email's own local part, with a collision-retry loop confirmed live against two different addresses that sanitize to the same base name.

## Bug fixes and polish (D-059–D-066)

A cluster of real, user-reported issues, each reproduced live before being fixed:

- **The interactivity module could go silently inactive.** Any plan that reached the editor without explicitly declaring `module "interactivity-module.js"` — which describes the actual AI-copy-paste workflow this whole project is built around — lost all drag functionality with no error shown. Fixed by always keeping the three shipped modules active regardless of what the current text declares, without rewriting the visible source.
- **Sign-in copy still spoke in raw WordPress terms** after registration had been simplified to email+password — relabeled to explain the credential in the product's own language.
- **Browsing an example plan silently cluttered "My plans."** Selecting one now only becomes a saved plan on the first actual edit.
- **The App reversed an earlier deliberate SEO exclusion** (flagged before changing it, since it undid a prior reasoned decision) — now included in the sitemap and no longer blocked in `robots.txt`, at direct request.
- **An Impressum page added**, with the real identifying details the user provided directly rather than inferred.
- **A cookie/local-storage notice** — worded to say what the site actually does (client-side storage, no real HTTP cookies exist anywhere in this project, confirmed by grepping for `document.cookie`/`Set-Cookie` and finding nothing) rather than a generic, inaccurate "this site uses cookies" banner.
- **A "Beta" badge** added to the App specifically, and **GitHub links removed from the Docs page**, both requested directly.

## Mobile-friendly, desktop-first (D-067–D-068)

Every page made usable on a phone while keeping desktop the unchanged default — every mobile rule lives inside a `max-width` media query layered over untouched desktop CSS, verified with real before/after screenshots at both a 390px and a 1400px viewport, not just eyeballed.

Two real overflow bugs were found this way that no amount of reading the CSS would have surfaced: Homepage's three-box "you describe it → …" diagram had no mobile handling at all, and the Docs page's two-column layout still overflowed *after* collapsing to one column, because a CSS grid item's default minimum width is its own content's size, not zero — the grid-layout counterpart of a flexbox trap already documented elsewhere in this codebase.

Requested as a direct follow-up the same day:

- **A hamburger menu** on Homepage/Docs/Profile/Impressum, replacing the earlier "just let it wrap" fix.
- **Code/Viewer tabs in the App**, replacing two half-height stacked panes that left neither one usable. Fixed a real bug along the way — hiding the bare `<textarea>` wasn't enough, since the code-highlighting module wraps it in its own element at runtime that a naive selector never touched.
- **A decluttered toolbar** — smaller controls, and the occasional-use buttons collapsed behind a single "⋯" toggle.
- **A structural fix for the cookie notice**, which the tabs change exposed: with only one pane visible at a time, a fixed-position notice has nowhere to sit without covering it. Fixed by taking it out of `position: fixed` entirely on mobile and using `order: -1` in the flex column instead, so it pushes the layout down rather than overlapping it.

## The Fit button (D-069, two rounds)

Reported directly ("fit button doesn't work"), and it genuinely never had: `handlePointerDown` called `preventDefault()` on every pointerdown inside the viewer, including on the Fit button itself (a child of the same container) — which silently suppressed the browser's own click-event synthesis for it. A pre-existing bug, reproduced on unmodified desktop first specifically to rule out that day's mobile work before looking further.

Fixing that surfaced two more, reported back as "it does something but not a clean fit": Fit was reapplying a *cached* fit box that dragging never updates (drags deliberately preserve the camera mid-drag), so an element dragged outside the plan's original bounds could end up cropped after clicking Fit — confirmed geometrically via `getBBox()`, not just visually. Fixing *that* then broke the plain "just reset my pan/zoom" case, since the recompute only clears the camera override when the box actually changed. Both fixed together: Fit now triggers a real recompute *and* unconditionally discards the current pan/zoom, verified against three separate scenarios (plain pan, zoom with nothing moved, and a far drag) before shipping.

## Where things stand

- **Live and deployed**: the whole site (`planagonia.com`, `/app`, `/docs`, `/profile`, `/impressum`), the storage service (`api.planagonia.com`), and headless WordPress auth (`auth.planagonia.com`) — all tested against the real, running infrastructure, not just written and assumed correct.
- **Still open**, per [planning/site-structure.md](../../planning/site-structure.md) and [planning/open-questions.md](../../planning/open-questions.md): resending a verification email if the first doesn't arrive, deep-linking a specific cloud plan from Profile into the App, whether `test.planagonia.com` gets retired now that the real domain carries the live layout, and the two genuinely unresolved core-product questions (F-001 constraint-solving scope, F-002 module API surface — specifically drag-editability of a module-synthesized composite element, the one concrete gap D-046 left open).
- **Every fix in this update was verified against a real, running browser** (Playwright, headless Chromium, installed into the working session for exactly this purpose) or the live server itself — this project's standing practice, applied consistently across two very different kinds of code: PHP running on shared hosting, and client-side JS with no local execution environment otherwise available.
