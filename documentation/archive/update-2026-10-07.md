## Four right-click-menu ideas, finished (D-178, D-179, D-180)

Recorded together in the last update as F-054 through F-057, none yet designed; all four finished this session, one after another.

**A plan-picker card gets its own menu (D-178).** Right-clicking (or long-pressing, on touch) a "My plans" card now opens Duplicate/Delete for *that* card specifically, without switching to it first — the header's own existing Rename…/Delete still only ever act on whichever plan is currently open. Scoped deliberately to local plans only; a Cloud plan's own card gets no menu at all, since deleting or duplicating one would mean real server calls, a separate piece of work. Two real integration bugs were caught live before shipping: the card menu sits outside the picker panel's own DOM subtree, so the panel's existing "click outside closes it" listener would have closed the whole picker the instant Duplicate or Delete was clicked; and a touch long-press still fires a synthesized click afterward, which would have also switched to the plan right after opening its menu. Both fixed with a narrow, targeted guard each.

**Rename and Change Style join the element menu (D-179).** Both had nowhere obvious to go — the radial right-click menu was already at its own five-item cap, with none of the three existing groups a natural fit. Asked directly: fold both into a new "Edit" group, or raise the cap to seven flat items? "Edit" was chosen. Building it surfaced a real limit in the menu component itself that hadn't been designed around yet: it only ever supports *one* level of grouping, so nesting "Change Style" as its own sub-group inside "Edit" simply isn't something it can render. Fixed by flattening — every declared style preset gets its own row directly inside "Edit," the same shape the menu's existing "Connections" group already uses for its own per-connection rows. Rename edits an element's own display label (never its id, which other lines in the plan may structurally depend on); Change Style is scoped to presets a plan already declares, not a free-form color picker.

**Selection wins at a stacked point, on click too (D-180).** Right-clicking a point where several elements overlap already preferred whatever was currently selected over whatever happened to be drawn on top (D-146) — reading the code directly confirmed that an ordinary click or drag-start had no such preference at all, always grabbing the topmost shape regardless of selection. The fix is the exact same logic right-click already used, pulled out into one shared helper both now call — not a second copy of the same rule. Deliberately the narrower of two possible scopes: the selection only wins where it's genuinely tied with the topmost hit at that exact point, not everywhere inside its own bounding box.

## A doubled-label bug, fixed (D-181)

Reported directly: an element's name could show up twice at once — once in the little badge that lists what's stacked under the cursor, and again right next to it as the element's own persistent on-canvas label. The badge's "current" line now goes marker-only when that same element already carries a persistent label of its own; every other candidate in the stack still shows its name normally, since its own label (if it has one) sits at a different point on the canvas, not at the cursor, so there's nothing for it to collide with there. A second thing this bug report seemed to imply — that an ancestor shouldn't appear in the badge's list at all — turned out, on a close read of the existing code, to already be intentional and correctly working for a different reason (click-cycling needs it there too) and was left alone.

## Polygon and polyline points become addable and removable (D-182)

A corner's own position was already directly draggable; there was no way to add a new point along an edge or remove an existing one without hand-editing the plan's own source text. Asked directly where "add a point" should live: a small handle at each edge's own midpoint, or a right-click "Add point" option needing a second step to place it? The midpoint handle was chosen — the same convention most vector editors already use. Right-clicking an existing point now offers "Delete Point" instead of the ordinary element menu, disabled once a shape is down to its own structural minimum (3 points for a polygon, 2 for a polyline). A new point is always a plain `[x, y]` pair, never a new shared corner — and deleting one only ever removes that single entry from the shape's own point list, never the corner element itself or any *other* shape's own reference to it, confirmed live against a plan with two parcels sharing a corner.

## Growing a polyline from either open end (D-183)

The natural next step right after the point above: adding a point *between* two existing ones doesn't help when what you actually want is to keep extending a line past its own tip, the way many drawing tools let you lay down a connected path click by click. Confirmed directly before building further: a small handle at each open end — not a continuous "keep clicking to add more" mode — click it once and a new point appears immediately, continuing the line's own last segment at the same length and direction, draggable afterward exactly like any other point. A polygon gets no such handle; it has no open end to extend from. Extending from an end that's a shared corner reference leaves that reference completely untouched, the same guarantee the point above already established for deleting one.

## A warning for a feature used without its own module declared (D-184)

Three built-in rendering modules (grid, annotations, the wall-with-door composite) each need an explicit `module "..."` line in a plan's own source before they'll do anything — a deliberate, previously-made choice, not an oversight. The gap that choice quietly left open: using `settings.grid`, `label`, `dimensions`, `edgeLengths`, or `compose: "wallWithDoor"` without that line rendered nothing at all, with no error and no warning anywhere to explain why. The app's own built-in Grid/Connections/Dimensions buttons always declare what they need automatically, so this never bit the shipped UI — but a plan written or edited by hand, including by an AI, had no such safety net. The load-time validation panel (the same one that already catches things like an unsupported property or an unrecognized shape) now catches this too, naming exactly which module is missing.

## "New Element" lands somewhere that makes sense (D-185)

Inserting a new Line, Rectangle, Circle, or Polygon from the header's "New Element" menu always nested it as the first child of whatever was currently selected — with no check on whether that selection could sensibly contain anything at all. Selecting a line, a circle, or a bare corner point and inserting a new shape buried it "inside" something with no meaningful inside. Asked directly which rule should decide: only `rect` and `polygon` are treated as real containers now — the same two shapes the app's own containment logic already singled out elsewhere as "the only ones with an unambiguous inside." Inserting with anything else selected now lands the new shape one level up, as a sibling, instead.
