# Core Aims

## Vision

A browser-based 2D plan generator: the plan is defined by code, and editing that code changes the plan. In a later stage, the user will also be able to edit the plan directly via drag-and-drop, with the underlying code updating to match.

## Core Aims

1. **Code and plan stay in sync** — editing either one updates the other; there is no view that can drift from the code that defines it. **Code is the single source of truth for every plan feature the viewer or menu reflects — never a separate, independently-tracked flag.** An interaction or button may always write to the code (that's this aim's own bidirectional sync) — but what's actually rendered, and what state a menu item shows, is always read directly from the code itself afterward, never cached or inferred in a way that could drift from it. Applies to plan *content* (modules, settings, element properties) — not to purely ephemeral editing-session state (selection, pan/zoom, which panel/tab is open), which was never part of the plan and shouldn't become part of it just to satisfy this rule. [D-175](decisions.md#d-175-module-loading-reverts-to-explicit-declaration-only--d-173s-content-triggered-detection-reversed-header-action-auto-cleanup-added) already established exactly this pattern for module loading; F-060 (closed — see [D-194](decisions.md#d-194-core-aim-1-sharpened-code-is-the-single-source-of-truth-for-every-plan-feature--resolves-f-060)) asked whether it should extend further than that — this settles it: yes, for plan content generally.
2. **A purpose-built plan language** — the plan is written in its own optimized language, not general-purpose code.
3. **Extensible via modules, core kept as lean as possible** — the plan's view and interactivity can be extended by modules loaded from within the code (e.g. additional JS files); new capability defaults to living in a module rather than growing `docs/index.html`'s own inline core (parser/renderer/`PlanCore`), regardless of which of the module kinds it is — own, community, or external ([language-spec/modules.md#module-kinds](../language-spec/modules.md#module-kinds)) — the boundary that matters is core vs. module, not how trusted the module happens to be. Every module, without exception, loads only because the plan's own code declares it — there's no longer a force-injected exception for any of them ([D-175](decisions.md#d-175-module-loading-reverts-to-explicit-declaration-only--d-173s-content-triggered-detection-reversed-header-action-auto-cleanup-added), extended to the last holdouts by [D-195](decisions.md#d-195-interactivitycode-highlighthierarchy-lose-their-force-injected-exception--the-four-module-kinds-named)).
4. **Built to last, not just to work** — the codebase stays technically sustainable as it grows: new work avoids introducing avoidable technical debt, and debt that does accumulate is tracked ([planning/tech-debt.md](tech-debt.md)) and paid down alongside ongoing feature work, not left to pile up indefinitely.
5. **Findable by search engines** — the public-facing pages (Homepage, Documentation, Blog, the App) are built to actually rank, not just to exist: a single consolidated domain instead of fragmented subdomains, real per-page metadata, a maintained sitemap and `robots.txt`, and signed-in-only or backend-only surfaces (Profile, `auth.`, `api.`) deliberately excluded from indexing rather than left ambiguous ([planning/site-structure.md](site-structure.md#seo--raised-directly-and-it-actually-decides-the-domain-question-below)).
6. **Built toward eventual commercial success, with intellectual property protected accordingly** — this isn't purely an open experiment; a later commercial path is a real, standing goal, so a choice that would freely give away replicable value (repo/source visibility, licensing, a community module ecosystem's own ownership terms) gets made deliberately, not by default just because the opposite was easier or already in place. Not yet designed: the concrete mechanism ([planning/open-questions.md#f-046-how-ip-protection-and-eventual-commercial-success-actually-get-implemented](open-questions.md#f-046-how-ip-protection-and-eventual-commercial-success-actually-get-implemented)).
