# Open Questions

Numbered `F-x` entries — real product/design questions that are genuinely unresolved right now. Distinct from `S-x` (existing-code maintainability gaps, `tech-debt.md`) and `D-x` (decisions already made and built, `decisions.md`). An entry is removed once it's fully resolved — the resolution is recorded as a `D-x` decision, not narrated here as a "built" append. Numbers are stable identifiers, not reused once an entry is retired; a partially-built entry stays, trimmed to whatever's actually still open, with a link to the `D-x` that covers what's already done.

## F-001 Constraint-solving scope: is a general geometric solver ever actually needed?

Unlimited connections + rigid drag propagation can in principle produce over-constrained/conflicting demands on a node — the same class of problem a CAD constraint solver exists for ([decisions.md D-014](decisions.md#d-014-connection-semantics)). In practice, every concrete case asked for so far has been covered by a small, specific, geometry-scoped mechanism instead of a general solver: shared corner-node references for pinned shared points ([D-018](decisions.md#d-018-points-as-node-references-shared-corners)), and the three parent-child placement modes — outside-attached, inside, flush — for constrained sliding ([D-032](decisions.md#d-032-parent-child-placement-modes), [D-071](decisions.md#d-071-f-001-flush-built-closing-d-032s-last-unbuilt-half--the-app-back-on-the-products-own-core-questions-not-just-its-sitedecisioninfra)). Still open: whether a real conflict case will eventually show up that these specific mechanisms can't cover, at which point a real solver (or a hard complexity cap) becomes a live question rather than a hypothetical one. Also still open, unrelated to solving: containment/flush only ever check the *directly dragged* element, never one moved along by a `connection`.

## F-002 Does the composite backward-solve approach generalize past one composition type?

Module-provided compositions (a reusable higher-level building block, e.g. `wallWithDoor`) are built and demonstrated end to end — rendering ([D-046](decisions.md#d-046-f-002s-third-module-promise-finally-tested-module-provided-compositions)) and drag-editability via a per-composition-type backward-solve ([D-072](decisions.md#d-072-f-002-drag-editability-for-a-composite-the-last-open-half-of-d-046)). Only one composition type has ever been built, so whether `composeDragEdits`'s specific approach — or any part of it — actually generalizes to a second one is untested, not assumed either way.

## F-004 Collision checking: only the dragged element, only siblings

[D-041](decisions.md#d-041-collision-checking-built-into-the-interactivity-module-not-core-or-a-third-module)/[D-075](decisions.md#d-075-f-022--f-028-a-load-time-validation-pass-with-duplicate-id-detection-folded-into-the-same-sweep) built collision/containment checking, both at drag-time and at load-time. Two scope limits remain, both deliberate but unaddressed: only the *directly dragged* element is checked, never anything moved along with it via a `connection`; and checking is scoped to same-parent *siblings* only, so two elements under different parents that happen to visually overlap are never checked at all.

## F-005 Public plan viewing

Whether a plan can ever be shown to a non-owner at all (e.g. a public share link) has never been decided as a feature. If it's ever built, the reasoning already worked out: serve it as a server-rendered static snapshot (flattened SVG/PNG) rather than the raw plan-language source — a viewer gets a picture, not an editable structure, protecting the owner's content ([decisions.md D-022](decisions.md#d-022-scraping-protection-content-not-the-language)) and doubling as a performance win. A principle to reuse *if and when* this is decided, not a commitment to build it.

## F-006 Documentation may still describe a broader language than what's actually implemented

A fresh AI agent given only `language-spec/language.md` (no other context) produced a plan that failed to parse — wrong `connection` syntax (the doc showed an object-literal form nothing implements; the real syntax is positional), an unsupported sibling property path guessed by analogy, and a guessed (if correct) nesting syntax with no confirming example. The core, well-documented grammar came out correct on the first try — the gap is specifically in under-documented areas (connection syntax, sibling-path scope), not general ambiguity. Needs a documentation pass reconciling the spec with the current implementation; not re-checked since the language has grown substantially (placement, flush, compose, style presets, settings) since this test was run.

## F-007 Drag performance at scale

The current architecture re-tokenizes/re-parses the entire plan and replaces the entire rendered SVG on every `pointermove` during a drag. Measured directly: fine through 800 objects, over the 60fps frame budget at 2000 ([Prototypes/11-performance-test/](../Prototypes/11-performance-test/)). Fine for a single room or small home; would need incremental/targeted DOM updates (move just the dragged element's attributes) before comfortably handling a large multi-room plan with hundreds of objects. Not yet a real problem at this project's current scale.

## F-008 Live AI integration

Today's workflow is copy-paste from a separate AI conversation ([decisions.md D-023](decisions.md#d-023-ai-integration-mechanism-current-copy-paste)). If/when a live integration is built: where the LLM calls happen (client-side exposes an API key — not viable; realistically server-mediated, a new backend concern), how AI output reaches the editor (streamed vs. a complete diff), and conflict handling if the AI generates while a human is also typing. Lower priority than the questions above — copy-paste is a complete enough stand-in for now.

## F-009 External-module trust model, given who actually picks the URL

External modules run with no sandboxing, trusted by analogy to "a developer choosing an npm package" ([decisions.md D-020](decisions.md#d-020-plan-preamble-modules-and-settings)) — but per D-003, the module URL is typically chosen by an AI, with the human reviewing the result afterward, a different risk profile than the analogy assumes. **Partially mitigated:** a `confirm()` gate before loading any non-shipped module ([D-045](decisions.md#d-045-a-confirmation-gate-before-loading-an-untrusted-external-module)) — moves the exposure from automatic to a deliberate per-URL choice, but adds no sandboxing; accepted code still runs with full page access. Still open: whether real sandboxing is ever worth building, and whether gating behind login + an explicit per-profile opt-in is worth the accounts infrastructure it would need.

## F-010 Shape-agnostic container extent

`parent.size.x` only resolves when the parent is `shape: "rect"` (the one shape kind with a `size` property) — a `circle` parent has `radius`, a `polygon`/`polyline` parent has `points` and no single "size." Whether this is worth a real shape-agnostic accessor (every node exposing a computed `bounds.x/y/width/height`) or whether "only `rect` containers support this" is an acceptable permanent constraint is open.

## F-011 Single-parent hierarchy: is multi-membership ever actually needed?

Nesting (D-013) is the only way to express a parent-child relationship — a node has exactly one parent. This buys real simplicity (no dangling parent references, drag-sync never validates a reference graph) at the cost that a node can't belong to two groupings at once (e.g. "inside the room" for coordinates *and* "part of the kitchen zone" as a non-spatial grouping). Whether this is ever actually needed for this language's target domains, or whether a purely cosmetic grouping already covers every real case, is open — not derived from hitting a concrete blocked case.

## F-015 Settings editable from the viewer, beyond the one case already built

A plan's settings are otherwise purely textual — turning on e.g. `edgeLengths` or `allowCollisions` means typing it. **One concrete case is now built:** the header menu's "Show grid" toggle reads/writes `settings.grid` directly ([decisions.md D-103](decisions.md#d-103-the-app-header-every-distinct-action-flat-and-always-visible-icon-led-export-grouped-as-its-one-deliberate-flyout--plus-a-settings-toggle-and-a-real-sign-in-popup)). Whether this generalizes to a real settings panel covering every setting, or stays a small set of individually-added toggles for the settings that are genuine on/off flags, is open.

## F-024 Domain coverage hasn't been audited against what a real floor plan needs

`rotation` for `rect` is built (D-141) — an angled wall or a non-rectangular footprint no longer forces hand-computed rotated polygon coordinates. Still open: no curves/arcs and no multi-level/floor concept at all, and how far to take either (versus leaving them a stated, permanent limitation) hasn't been decided. Also still open specifically from D-141's own v1 scope: `flush`/`placement: "outside"` against a rotated rect are unsupported (warn and fall back rather than attempt exact edge-projection math), and there's no interactive way to *set* rotation by dragging — only by typing it in the source.

## F-030 A reusable component/sub-plan concept

`compose` lets a *module* generate a structure from parameters (D-046/D-072), but there's no way to reuse a whole hand-authored *subtree* as data — "here's a bathroom layout, drop it into three different van plans." Related to F-027's now-built style presets (both are "define once, reuse without repeating") but at the granularity of a whole composition instead of one style object. Needs real thought before a shape is proposed: what identifies a reusable component, whether it lives inside one plan or is shared across files, how drag-editing a placed instance relates to editing the definition.

## F-034 Sharing a plan with someone else — static view vs. editable plan+code

Distinguishing two things: sharing just the rendered plan (F-005's own static-snapshot proposal, plausibly built on the export mechanism) versus sharing the plan *and* its editable source with a specific person — a fundamentally bigger exposure, handing over everything F-005's own scraping-protection reasoning tries to avoid giving away for free. Not designed: the mechanism for either (a durable share link implies the existing backend; plan+code sharing could be nothing more than exporting and sending source text), whether a shared plan is a live pointer or a frozen snapshot, and how either interacts with F-009's external-module trust question.

## F-038 Style-preset resolution is core-only — making it a module is unexplored

`resolveStyle`/`settings.styles` lives directly inside core's `renderShape`, resolved synchronously while each shape's SVG string is built — unlike every actual module (`annotations-module.js`, `grid-module.js`), which runs via `core.onRendered`, a **post**-render hook reading back an already-built SVG. By the time `onRendered` fires, `fill`/`stroke` are already burned into the string core generated, not still pending. Not designed: whether this would mean core deferring resolution (a placeholder attribute a style module rewrites after the fact) or a genuinely new pre-serialize hook nothing in this codebase offers yet — or whether the value here is purely architectural consistency rather than unlocking a concrete capability.

## F-042 Style modules and settings toggleable from the menu, beyond the one flag already covered

A menu that shows which modules/settings are *actually active in this exact plan* and lets someone flip them on/off, writing back via the same source-splice mechanism drag edits use. **The one setting that's a genuine, clean on/off flag is built** — `settings.grid`'s own presence/absence, via the header menu's "Show grid" toggle ([decisions.md D-103](decisions.md#d-103-the-app-header-every-distinct-action-flat-and-always-visible-icon-led-export-grouped-as-its-one-deliberate-flyout--plus-a-settings-toggle-and-a-real-sign-in-popup)). **Extended twice further:** [D-149](decisions.md#d-149-grid-front-layer-overlay-menu-editable-typesize-decoupled-from-snap) added `type`/`size` menu editing (`setGridSubKey`/`findNestedObjectSpan`, reusable one level into any settings sub-object); D-159 finished the set with a Layer group ("Behind shapes"/"In front"/"Hidden") and an Opacity field, both in the same Grid flyout — every grid sub-setting is now menu-editable, none left source-text-only. `snap` itself has its own header button (D-156), independent of `grid` entirely. Still open, and likely to stay open rather than resolve cleanly: every module (D-195 closed the last force-injected exceptions — interactivity/code-highlight/hierarchy) now does have a real, uniform "off" state at the declaration level (remove the `module "..."` line), but nothing in the menu shows or toggles that directly today, only `settings.grid`'s own flag; style presets aren't a meaningful binary toggle either (a named registry, not a flag). Not designed: how "currently active" would even be shown for a bare declaration that isn't a clean flag, and whether a non-auto external module (its own separate F-009 trust flow already) belongs in the same menu at all.

## F-045 A module store on the site for community modules

**Built at the smallest workable scope** ([decisions.md D-125](decisions.md#d-125-f-045-a-manually-curated-module-store-page)): `planagonia.com/modules`, a manually-curated static list — new entries added by hand (a PR or a direct email), not an open self-serve submission pipeline. Ships with an empty state, since nothing has been submitted yet. Deliberately chosen to sidestep, not resolve, the two harder questions below until there's real submission volume to design against:
- **F-009's external-module trust question stays exactly as open as it already was.** A short disclaimer on the page (third-party code, not covered by this repo's own `LICENSE`, still gated by the existing confirm-before-loading dialog) states the trust posture rather than changing it — whether *listing* something here reads as an implicit endorsement, beyond what the disclaimer already says, is untested with zero real listings.
- **F-046's licensing question is unchanged too** — a listed module is still someone else's code with no ownership terms attached by this project. Revisit both once real submissions start arriving; a one-line PR/email intake has no review or verification step to design in the meantime.

## F-046 How IP protection and eventual commercial success actually get implemented, beyond where the moat lives

**Where the protection comes from is now decided** ([decisions.md D-121](decisions.md#d-121-f-046s-first-concrete-answer-the-hosted-service-is-the-moat-not-client-code-secrecy--a-license-file-makes-todays-default-explicit)): the hosted service (accounts, cloud sync) is the moat, not client-code secrecy — the repo stays public, a `LICENSE` file now makes the existing "all rights reserved" default explicit rather than silent. **Trademark checked and a real Terms & Privacy page now exist too** ([D-191](decisions.md#d-191-f-046-trademark-checked-formal-registration-deliberately-deferred--a-real-patagonia-similarity-risk-recorded-not-dismissed), [D-192](decisions.md#d-192-f-046-a-real-terms--privacy-page-for-the-hosted-accountscloud-sync-service-that-was-already-live-with-no-stated-terms)) — formal trademark registration deliberately deferred (a real, recorded Patagonia-name-similarity risk, not a cleared one), and `homepage/terms/index.html` now governs the hosted service itself (data handling, account terms, acceptable use), linked from every registration form and the site's own footer. Still open:
- **A monetization shape isn't chosen** — free vs. paid, individual vs. team, self-hosted vs. cloud-only — none of the above answers *how the business works*.
- **F-045's module store now exists but is empty** — still needs its own explicit ownership/licensing terms before real submissions arrive; a listed module is someone else's code, not covered by this repo's own `LICENSE` at all. Also still open whether Planagonia itself could be forked using community modules as a shortcut around whatever protects the core.

Not a decision to make preemptively — recorded so the next concrete choice that touches any of this (F-045 itself, a pricing page, opening accounts more broadly) gets weighed against it rather than decided in isolation.

## F-056 Signed-in users authoring their own modules — versioning and real public discoverability still open

**v1 built** ([decisions.md D-201](decisions.md#d-201-f-056-v1-built-signed-in-users-can-create-their-own-modules-from-profile)): a dashboard on `profile/` with a plain paste-in `<textarea>` (not a real authoring environment, matching the original "vorerst nur als Text den Code reinkopieren" ask), backed by a new `api.planagonia.com` storage-service table/endpoints. A module gets a stable URL (`module-code.php?id=X`) to declare in any plan via the existing `module "..."` mechanism — nothing on the app side needed to change at all.

**Deliberately the smallest workable "publish" scope, confirmed directly before building:** `visibility` (`private`/`public`) is a dashboard-only label with zero behavioral effect — no new public-listing endpoint, `/modules/` itself completely untouched. This sidesteps, rather than resolves, the two collisions this entry originally flagged:
- **F-045's module store stays exactly as manually-curated as it already was** — v1 adds no self-serve path onto `/modules/` at all, so the "real submission volume arriving" trigger F-045 was waiting for hasn't actually arrived yet in a form that forces that question.
- **F-046's ownership/licensing gap stays theoretical, not load-bearing** — a module that's merely labeled "public" in someone's own dashboard, with no public listing anywhere, isn't yet "a listed module" in the sense F-046 means.

Whether this is the right permanent answer, or whether published/shared modules eventually need real version pinning, is unresolved.
- **Real public discoverability**, if ever wanted: a public-listing JSON endpoint, and/or actually surfacing user-authored public modules on `/modules/` — both deliberately not built in v1, see D-201.
- **Any validation/safety check on submitted code** — still none, same as every other external module (F-009's existing, accepted posture).

(Live verification against the real WordPress/MySQL instance — create/edit/delete a module, load it in a real plan — is **not** actually open: D-201's own status line already records it done, end to end, against production. A stale line here previously claimed otherwise, citing a tech-debt number — S-043 — that had already been closed for an unrelated fix (D-184) by the time this entry was written; corrected directly rather than left to keep misleading the next read. Re-confirmed live again, lightly, while fixing this: `modules.php` without a token still returns `401`, `module-code.php` with an unknown id still `404`s, a missing id still `400`s, and CORS still allows the main domain — the backend hasn't silently regressed since D-201.)

## F-049 The `<main>` content tabs (Code/Viewer/Layers) aren't a standardized, registrable system

Raised directly while adding a mobile "Layers" tab alongside the existing mobile Code/Viewer tabs (D-006). Today's `.tab-btn`/`data-mobile-tab` mechanism (`docs/index.html`) is a hand-built, mobile-only pane switcher with each pane hardcoded into the same script and CSS — adding Layers as a third tab meant editing that fixed set directly, the same way any future tab would. This is specifically about `<main>`'s own content-pane tabs — the *header's* own equivalent gap (a module couldn't add a button to the toolbar) was F-048, now closed by D-172's `core.registerHeaderAction`. Four related, undesigned questions the user raised together: (1) the tab mechanism itself should be standardized/generalized rather than remaining a one-off per-pane switch; (2) a module should be able to register its own new content tab — hierarchy-module.js's own Layers panel is already the first real example of "a module owns a pane" (unrelated to its own loading timing, which changed twice since this was written — D-174 made it unconditionally loaded, D-195 then put it back behind its own `module "..."` declaration like every other module), just not yet through any registration API; (3) each tab's width should be adjustable on desktop, not just the fixed code/viewer split (F-040) — unclear whether that means a resizable Layers sidebar, a user-chosen tab order/visibility, or something else; (4) "tabs" may not even be the right name for this concept once it's generalized beyond two hardcoded panes. Not designed: any of the above — recorded so the next content-pane addition (or a deliberate pass to generalize this) gets weighed against the whole set rather than another one-off hardcoded addition. **D-157 records a chosen future direction** for point (2) specifically (a `registerContentTab({ id, label, render, destroy })`-style API) without building it yet — deliberately deferred until a second real module (beyond hierarchy-module.js) needs it; D-172 closing the header-action half is itself a small, if indirect, signal this whole direction is worth eventually following through on. Points (1), (3), (4) remain fully open.

**Sharpened directly, live, pointing at a concrete symptom of exactly this gap:** today, with `hierarchy-module.js` undeclared, its own header action/tab button simply never appears — the "stable hidden slot" pattern (D-162's own `core.registerHeaderAction`, the same shape F-048 closed with) means an *un-filled* slot just silently stays hidden, with nothing on screen admitting a feature went missing. Named as a symptom of a bigger, not-yet-stated principle: point (2) above was framed as "a module can register a *new* tab," but the actual ask goes further — Code and Viewer themselves (`<main>`'s two *original*, hand-built panes, never modules at all, unlike Layers) should also be things a module creates or replaces, not fixed core furniture with a registration API bolted on beside them. In this framing, core would own only the skeleton (the pane-switching/layout mechanism itself) — no preset panes of any kind, Code/Viewer included — and every actual pane, including the two that exist today, would be something a module supplies. A considerably larger change than D-157's own planned API (which still assumes Code/Viewer stay core-owned and only *new* tabs are module-registrable) — not designed at all, and not yet weighed against whether `interactivity-module.js`'s own code-editing logic (deeply wired into core's own `source`/`rerender` plumbing) could realistically be relocated into a swappable pane without a much bigger rewrite.

## F-052 How (and whether) user plan data could be used in the future — product improvement, aggregate statistics, or sale

Raised directly as a distinct facet of F-046's own still-open "monetization shape" question, specifically about the data itself rather than the service around it: today every plan a signed-in user saves lives in the cloud-sync storage this app already built (D-105's own account system), with no stated policy on what, if anything, that data could ever be used for beyond storing and returning it to its own owner — improving the product (seeing what kinds of plans people actually build, where they get stuck), aggregate/statistical use, or an outright sale of data itself as a business line. Not designed at all: whether any of these are even directions worth pursuing, what a user would need to be told or asked before any of them could happen (a real Terms of Service is itself still open, per F-046), and whether "the hosted service is the moat, not the code" (D-121) implies the *data flowing through* that service is part of the same moat or a separate question entirely. Recorded now, deliberately unresolved — a business/privacy decision, not an engineering one, and not remotely urgent while the user base is what it is today.

## F-053 Automatic, summed dimension chains along a shape's outer boundary — the bigger half of the arrow-dimension request, deliberately not built

Raised directly, from the same reference image that prompted the arrow-style edge-length dimension lines (D-169): a real architectural floor plan's own dimension strings don't just mark one wall segment at a time — they detect every wall/partition that touches a given outer boundary (say, the top edge of a building), break that boundary into segments at each one, draw a stacked row of individual arrow-dimensioned segments, and add a second, further-offset dimension line spanning the *whole* boundary with a running total ("12.50m Total Width"), often computed independently for more than one side (the reference image shows different segment breakdowns for the top and bottom edges of the same building, since different interior walls happen to align with each). Confirmed directly with the user before scoping D-169 down to exclude this: it needs a genuinely new geometry capability nothing in this codebase has today — grouping sibling elements' own edges by shared axis/alignment (not just "this one shape's own 4 edges," which is all `edgeLengthLines` computes now), deriving ordered breakpoints along that axis, and stacking multiple parallel dimension rows at increasing offsets so nested segment-vs-total lines don't overlap. Not designed at all: what counts as "aligned" for two edges belonging to different sibling elements (exact coordinate match? a tolerance?), which boundaries of a plan get this treatment automatically vs. requiring an explicit opt-in, and how a total row's own arrow-line offset is chosen once more than two levels of nesting exist (a segment breakdown *and* a sub-total *and* a grand total, in principle).

## F-055 Should a module ever be able to cancel another module's in-progress gesture?

Surfaced building D-198 (splitting pan/zoom/pinch/Fit/the scale bar out of interactivity-module.js into `view-module.js`): before the split, a second touch landing mid-gesture cancelled whatever one-touch drag/resize/marquee gesture was in progress and handed off to a pinch — a real, deliberate piece of UX polish (F-036), not an accident. The two modules no longer share gesture state to make that handoff possible, so this was accepted as a known tradeoff rather than solved: a second finger landing now just starts an independent pinch in `view-module.js`, while interactivity-module.js's own gesture (if any) holds in place (ignores further movement without being cancelled) until back down to one touch.

**Not designed at all:** whether this is worth a dedicated mechanism — e.g. a core-level "register/cancel active gesture" registry any module could both claim and query, so a module starting a higher-priority gesture (like a pinch) could cancel another module's lower-priority one without either module knowing about the other's existence directly. Would be the first cross-module (not module-to-core) coordination primitive this project has ever needed — every module interaction today happens via core's own render/settings, never live pointer-gesture arbitration between two independently loaded modules. Deliberately not built speculatively; revisit only if the held-in-place behavior is actually reported as a problem, not because the asymmetry is inherently wrong.

## F-057 The whole profile/auth/cloud-storage stack has no automated test coverage at all

Raised directly: a requested re-audit of `profile/index.html` and everything around it (`storage-service-php/`) found that none of it — sign-in, registration, email verification, password reset, session tokens, or the plans CRUD itself — is touched by the pytest suite, which only drives `docs/` (the app) via Playwright against a `file://` page. Every correctness claim for this entire stack (D-019, D-049, D-055, D-056, D-058, and this pass's own two findings below) rests on manual `curl`/live-browser verification recorded by hand in `decisions.md`, with no regression safety net if `auth.php`/`registration.php`/`plans_repo.php` are touched again. Not a simple gap to close by just "writing tests": this stack's own correctness depends on a live WordPress instance (`auth.planagonia.com`) and a real MySQL database, neither of which the existing Playwright harness spins up — real coverage would need either a test WordPress+MySQL fixture (heavy, and it would have to avoid touching the live `auth.planagonia.com`/`api.planagonia.com` instances this project actually depends on), or restructuring the PHP side so its request-handling logic is unit-testable against a fake `verify_credentials`/WP-REST layer. Which of those (or something else) is worth the effort, and at what point the manual-verification-only approach stops being acceptable, is open.

## F-058 No self-service account management exists in this project's own UI

`profile/index.html`'s own callout already states this plainly — renaming, deleting, or rotating the Application Password isn't handled here, "those live in WordPress's own account tools for now." Confirmed while re-auditing the whole profile/auth stack that this is still completely true: there is no path at all, anywhere in this project's own pages, for a self-registered account holder to delete their own account or data. The only way is `wp-admin` at `auth.planagonia.com` — a domain and a UI (WordPress's own) a self-registered visitor never otherwise sees or needs to know exists, arguably in tension with D-019's own founding principle that "WordPress never renders the app's UI." Overlaps F-052's still-open data-handling/privacy question (what a user would need to be told or asked, including about deletion) without resolving it — this is specifically about the missing *mechanism*, not the policy. Not designed: whether this needs real UI (a "Delete my account" button on `profile/` calling a new storage-service endpoint that also deletes the WordPress account via the bot-admin credential) or whether directing users to WordPress's own forgot-password-style self-service is an acceptable permanent answer.

Reconfirmed live as an actual want, not just a theoretical gap: changing one's own username (the one assigned at registration, F-061) was the first concrete thing asked for while actually using a fresh account.

## F-059 The self-registration bot-admin credential is a single, maximally-privileged point of compromise

Raised directly re-auditing `storage-service-php/app/src/registration.php`. Its own comment already states the reason plainly: WordPress has no role narrower than Administrator capable of creating other users over the REST API, and D-019's "no plugins" constraint rules out adding one — so `config.local.php`'s `bot_username`/`bot_password` is a full WordPress Administrator credential, used by three endpoints (`register.php`, `forgot-password.php`, `verify.php`'s Application Password issuance). If that credential or the PHP app itself is ever compromised, the blast radius is "attacker has full admin control of `auth.planagonia.com`," not just "attacker can create subscriber accounts." Already a known, deliberate tradeoff from D-019/D-058, not a newly-introduced bug — recorded here because re-reading it fresh raised the question of whether it's still an acceptable permanent risk now that self-registration is a live, public-facing endpoint, or whether it's worth a narrower custom WP role (would need a tiny WP plugin, reopening the "zero plugins" constraint itself) or moving account-creation off WordPress entirely.

(This entry originally also covered an email-enumeration asymmetry between `/register.php` and `/forgot-password.php` — fixed, see [decisions.md D-200](decisions.md#d-200-f-059s-email-enumeration-half-fixed-registerphp-no-longer-confirms-an-email-is-already-taken).)

## F-061 The password chosen at registration is quietly replaced by a generated one — confusing even with the existing hint

Raised directly, live, by someone who had just registered and then reached `verify.php`'s confirmation page showing a completely different, generated Application Password ("ich hatte ein anderes passwort gewählt beim registrieren" — a real point of confusion in the moment, not a hypothetical one, despite having designed this exact flow originally). Both register forms already carry a hint explaining this in advance ("you won't need this password again day to day, since signing in here uses a separate credential generated at that point," `profile/index.html`/`docs/index.html`) — so this isn't an undocumented gap, but live-testing it firsthand shows the hint isn't actually landing: a small line among several other form hints doesn't prepare someone for "the password you just typed is now functionally irrelevant, here is a long random string to save instead." Ties into F-060 (the same flow's success message is *also* too easy to miss) — both point at the same underlying handoff being more surprising in practice than its documentation alone accounts for. Not designed: whether the real fix is a more prominent warning right at the password field itself (not just a trailing hint), rewording to make the consequence concrete before someone types a password they'll try to remember for nothing, or a more fundamental rethink of why a password is collected at registration at all if it's never the one actually used here.

(The username being changeable from `profile/` directly — also raised in the same message — is already covered by [F-058](#f-058-no-self-service-account-management-exists-in-this-projects-own-ui)'s existing scope; reconfirmed as a live, first-hand want, not just a theoretical gap.)

## F-062 The browser never offers to save the sign-in credential

Raised directly, live: signing in on `profile/` didn't trigger the browser's own "save this password?" prompt. A likely, found-not-guessed cause: `profile/index.html`'s own sign-in handler clears the password field immediately after a successful sign-in (`document.getElementById("password").value = ""`, right after `setCloudSession(body.token)`) — several browsers decide whether to offer saving a credential based on the field's own value around the time the form's submit resolves, and wiping it programmatically that quickly could be removing the exact signal they look for. `docs/index.html`'s own auth-modal sign-in handler doesn't clear the password field the same way (it just calls `closeAuthModal()`, which resets the whole form via `.reset()` as a separate step), so whether this is specific to `profile/index.html` or affects both is unconfirmed. Not designed: whether removing the early clear (letting the form's own later `.reset()`/navigation handle it) is sufficient, or whether something else (the cross-origin `fetch` to `api.planagonia.com` itself, rather than a same-origin form POST) is what's actually suppressing the browser's own heuristic — not yet isolated.

## F-063 Clicking the verification link should sign the visitor in directly, not just show a credential to copy

Raised directly, live: today's flow (D-058) stops at `verify.php` showing the generated username/Application Password once, with a "Go to Profile to sign in →" link — the visitor still has to manually carry that password over and type it into the sign-in form themselves. Not designed, but the shape it would need is apparent from how session state already works: a session token only ever lives in the signed-in page's *own* origin's `sessionStorage` (D-021), and `verify.php` is served from `api.planagonia.com` — a different origin than `profile/` (`www.planagonia.com` or GitHub Pages) entirely, so it can't set that storage directly. The obvious mechanism would be `verify.php` issuing a real session token (`issue_session_token`, already in `auth.php`) alongside the Application Password, and redirecting to `profile/` with it attached (e.g. a one-time query parameter `profile/`'s own JS reads once, stores into `sessionStorage`, then strips from the URL) rather than a plain link. Whether the Application Password still needs to be shown at all in that case — if the visitor is already signed in, the one remaining reason to show it is so they can reuse it elsewhere (scripted access, a future non-browser client) — is also unresolved.

## F-064 The "Your modules" dashboard should live under the main `/modules/` page, not only `profile/`

Raised directly, before live-testing F-056 v1 (D-201) any further: a signed-in user's own custom modules (today, `profile/`'s own "Your modules" card) and the manually-curated public module store (`/modules/`, F-045/D-125) are two separate destinations for what's conceptually one subject — "modules" — split only because they were built in two different sessions with no information-architecture pass connecting them. The ask: show the custom-module dashboard *under* the main "Modules" menu entry (alongside, not instead of, the public list), so a signed-in visitor lands in one place for both browsing what's available and managing their own, rather than needing to already know `profile/` carries a second, unrelated "modules" concept. Not designed at all: whether this means `/modules/` itself becomes a signed-in-aware page (a static page gaining a dynamic, auth-dependent section is a bigger structural change than anything that page has needed so far), a `profile/`-hosted dashboard merely *linked* prominently from `/modules/`, or restructuring both into tabs/sections of one page. Directly touches F-045's own still-static design and this session's own earlier confirmed choice (D-201) that "public" stays a dashboard-only label with no real listing anywhere — a combined page would put real pressure on that choice, likely reopening it rather than leaving it alone.

## F-065 The account-confirmation email's wording doesn't fit every situation that actually sends it

Raised directly, live, while confirming D-200's own behavior: `send_verification_email()` (`storage-service-php/app/src/registration.php`) has exactly one fixed subject/body — "Confirm your Planagonia account" / "Click the link below to confirm your Planagonia account" — used unconditionally by all three of its own callers: a genuine new registration (where the wording is accurate), `forgot-password.php`'s own reset flow (pre-existing, not introduced by D-200 — the account is typically *already* confirmed, so "confirm your account" is misleading), and now, since D-200, a second registration attempt against an already-registered email (the same mismatch as the forgot-password case). Not designed: the actual fix, but the shape is apparent — `send_verification_email` would need to know *why* it's being called (e.g. an `isNewAccount` flag or an explicit reason string) and choose wording accordingly ("Confirm your account" vs. something like "Here's a fresh sign-in credential for your Planagonia account"), rather than one sentence trying to cover three different situations.

**Live-confirmed directly, not just reasoned about:** using the actual "forgot password" link sends exactly this same fixed confirm-your-account email, not anything describing a password reset — the forgot-password case called out above as a mismatch, now hit firsthand rather than only inferred from reading `forgot-password.php`'s source.

## F-066 Why collect a password at registration at all, if `verify.php` could let the visitor choose one instead?

Raised directly, live, alongside F-061 (the typed registration password being silently discarded in favor of a generated Application Password) and F-063 (the verification link not signing the visitor in): a different shape for the whole flow — register with just an email (no password field at all), and have the verification link itself be where a password gets chosen, at the one moment it's actually needed and guaranteed to stick. Would resolve F-061 outright (there'd be no "password you just typed is now irrelevant" moment, since none would be collected) and pairs naturally with F-063's own already-proposed mechanism (`verify.php` issuing a real session token) — the same page could issue the session *and* host a "choose your password" form in one step. Not designed: what credential (if any) still needs generating server-side for non-browser/API use once a user-chosen password exists, and whether `register.php`'s current synchronous "account exists immediately, pending confirmation" shape would need to change if the account has no usable password until `verify.php` is actually reached.

## F-067 The display-unit toggle (Units: m/ft) doesn't reach Grid/Snap sizing at all

Raised directly: switching the header's "Units: m/ft" toggle (`toggleDisplayUnit`, F-013's own `settings.displayUnit` flag) only ever changes how `formatMeasurement` renders dimension *labels* — confirmed by reading the code, not just observed — every plan number stays internally metric regardless (D-005), and neither the Grid flyout's own `Size (m)` field nor Snap's own identical `Size (m)` field reads `displayUnit` at all: both labels are hardcoded "(m)" text, and both inputs are plain meter values, unaffected by the toggle either way. A visitor working in "Units: ft" still has to think in meters specifically to set a sensible grid/snap increment, with no indication anywhere that these two settings didn't follow the same toggle everything else on screen just did. Not designed: whether the fix is converting the *displayed* number in these two fields only (purely cosmetic, typing "1ft" still stores/means a meter value underneath, matching how `displayUnit` already works for every dimension label) or something that actually changes the stored grid/snap values' own unit — the user's own framing ("global definieren," define it globally) suggests they want one single setting that genuinely governs every unit-facing surface in the app at once, which is a bigger scope than F-013's own original "display-only, plan stays metric forever" design decision (D-005) was ever meant to cover.

## F-068 New elements should attach to the mouse and drop in on click, and always land on top

Raised directly, two related asks about the "New Element" flyout's own insertion flow (`insertStandardElement`, `docs/interactivity-module.js`): (1) on desktop, clicking a preset in the flyout should pick up a ghost/preview of the new element attached to the cursor, with a following click in the viewer actually placing it there — not today's one-click-insert-at-a-fixed-default-position behavior; (2) a newly inserted element should always render in front of its siblings. Both confirmed as real, not already covered: `insertStandardElement` inserts the new element's own source text immediately after its target container's opening brace — the *first* child, not the last — and since later-in-source means later-in-paint-order (the same precedent `bringToFront`/D-086 already established), a freshly inserted element can currently render *behind* existing siblings rather than on top of them, matching the second ask exactly. Not designed at all: what the drag-attached-to-cursor interaction should look like before the first click (a ghost outline following the pointer, presumably, mirroring how an active drag already renders), how it should behave on mobile (the ask is explicitly scoped to desktop, leaving today's click-to-insert behavior as-is there, but not actually resolving what "on top" should mean for a touch-inserted element either), and whether "always in front" means literally last-child-of-container every time, or something smarter if the new element is meant to sit *inside* another specific container.

## F-069 A polyline's own extend-handle distance is reopened — [D-183](decisions.md#d-183-f-051-a-polylines-own-open-ends-become-extendable-from-the-canvas)'s "accepted caveat" pushed back on live

Raised directly: "Verlängerung von Polyline ist noch unintuitiv. Punkt für die Verlängerung viel zu weit entfernt von letztem Punkt" (extending a polyline is still unintuitive — the point for extending it is way too far from the last point). Not a new discovery: `extensionPoint(from, to)` (`docs/interactivity-module.js`) returns `to + (to − from)` — the new point continues the line's *adjacent segment* at that segment's own full length, so the handle for extending a line whose last segment happens to be long renders exactly as far away, by design. D-183 itself already named this exact behavior **"a narrow, accepted UX caveat, not a bug,"** explicitly chose not to special-case it (capping the extension length or re-fitting the view), and reasoned it "only affects a line that already dominates the current view, where the user can simply zoom/pan first." That reasoning is now directly contested, live, rather than confirmed — worth reopening as a real design question instead of re-asserting the original call.

Not designed: what a better default distance would actually be — a fixed length regardless of the adjacent segment's own (matching a typical first-segment default elsewhere, e.g. `STANDARD_ELEMENTS`'s own preset sizing), a capped maximum (continue the real direction, but never further than *n* meters), or something else entirely (e.g. always placing it a fixed screen-pixel distance from the cursor/last point regardless of the plan's own zoom level). Also unresolved: whether this should still be a single parameter-free default (D-183's own stated preference, "WYSIWYG, not a surprise") or whether the handle needs to become draggable/adjustable before commit rather than a one-click-and-done action — a bigger interaction change than just tuning the distance formula.

Not designed at all: what the category/tag set would even be (a fixed, curated list matching this project's own product areas, vs. free-form tags assigned per post), whether a post can belong to more than one category, and how this interacts with the SEO analysis already underway (D-216 onward in [decisions.md](decisions.md)) — a per-category archive page would be more indexable surface area, but also more pages competing for the same limited topical relevance a small site has to begin with.
