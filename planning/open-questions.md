# Open Questions

Numbered `F-x` entries — real product/design questions that are genuinely unresolved right now. Distinct from `S-x` (existing-code maintainability gaps, `tech-debt.md`) and `D-x` (decisions already made and built, `decisions.md`). An entry is removed once it's fully resolved — the resolution is recorded as a `D-x` decision, not narrated here as a "built" append. Numbers are stable identifiers, not reused once an entry is retired; a partially-built entry stays, trimmed to whatever's actually still open, with a link to the `D-x` that covers what's already done.

## F-001 Constraint-solving scope: is a general geometric solver ever actually needed?

Unlimited connections + rigid drag propagation can in principle produce over-constrained/conflicting demands on a node — the same class of problem a CAD constraint solver exists for ([decisions.md D-014](decisions.md#d-014-connection-semantics)). In practice, every concrete case asked for so far has been covered by a small, specific, geometry-scoped mechanism instead of a general solver: shared corner-node references for pinned shared points ([D-018](decisions.md#d-018-points-as-node-references-shared-corners)), and the three parent-child placement modes — outside-attached, inside, flush — for constrained sliding ([D-032](decisions.md#d-032-parent-child-placement-modes), [D-071](decisions.md#d-071-f-001-flush-built-closing-d-032s-last-unbuilt-half--the-app-back-on-the-products-own-core-questions-not-just-its-sitedecisioninfra)). Still open: whether a real conflict case will eventually show up that these specific mechanisms can't cover, at which point a real solver (or a hard complexity cap) becomes a live question rather than a hypothetical one. Also still open, unrelated to solving: containment/flush only ever check the *directly dragged* element, never one moved along by a `connection`.

## F-002 Does the composite backward-solve approach generalize past one composition type?

Module-provided compositions (a reusable higher-level building block, e.g. `wallWithDoor`) are built and demonstrated end to end — rendering ([D-046](decisions.md#d-046-f-002s-third-module-promise-finally-tested-module-provided-compositions)) and drag-editability via a per-composition-type backward-solve ([D-072](decisions.md#d-072-f-002-drag-editability-for-a-composite-the-last-open-half-of-d-046)). Only one composition type has ever been built, so whether `composeDragEdits`'s specific approach — or any part of it — actually generalizes to a second one is untested, not assumed either way.

## F-004 Collision checking: only the dragged element, only siblings

[D-041](decisions.md#d-041-collision-checking-built-into-the-interactivity-module-not-core-or-a-third-module)/[D-075](decisions.md#d-075-f-022--f-028-a-load-time-validation-pass-with-duplicate-id-detection-folded-into-the-same-sweep) built collision/containment checking, both at drag-time and at load-time. Two scope limits remain, both deliberate but unaddressed: only the *directly dragged* element is checked, never anything moved along with it via a `connection`; and checking is scoped to same-parent *siblings* only, so two elements under different parents that happen to visually overlap are never checked at all.

## F-005 Public plan viewing

Whether a plan can ever be shown to a non-owner at all (e.g. a public share link) has never been decided as a feature. If it's ever built, the reasoning already worked out: serve it as a server-rendered static snapshot (flattened SVG/PNG) rather than the raw plan-language source — a viewer gets a picture, not an editable structure, protecting the owner's content ([decisions.md D-022](decisions.md#d-022-scraping-protection-content-not-the-language)) and doubling as a performance win. A principle to reuse *if and when* this is decided, not a commitment to build it.

## F-006 Documentation may still describe a broader language than what's actually implemented

A fresh AI agent given only `language-spec/language.md` (no other context) produced a plan that failed to parse — wrong `connection` syntax (the doc showed an object-literal form nothing implements; the real syntax is positional), an unsupported sibling property path guessed by analogy, and a guessed (if correct) nesting syntax with no confirming example. The core, well-documented grammar came out correct on the first try — the gap is specifically in under-documented areas (connection syntax, sibling-path scope), not general ambiguity. Needs a documentation pass reconciling the spec with the current implementation; not re-checked since the language has grown substantially (placement, flush, compose, style presets, settings) since this test was run.

## F-007 Drag performance at scale

The current architecture re-tokenizes/re-parses the entire plan and replaces the entire rendered SVG on every `pointermove` during a drag. Measured directly: fine through 800 objects, over the 60fps frame budget at 2000 ([Prototypes/11-performance-test/](../Prototypes/11-performance-test/)). Fine for a single room or small home; would need incremental/targeted DOM updates (move just the dragged element's attributes) before comfortably handling a large multi-room plan with hundreds of objects. Not yet a real problem at this project's current scale.

## F-008 Live AI integration

Today's workflow is copy-paste from a separate AI conversation ([decisions.md D-023](decisions.md#d-023-ai-integration-mechanism-current-copy-paste)). If/when a live integration is built: where the LLM calls happen (client-side exposes an API key — not viable; realistically server-mediated, a new backend concern), how AI output reaches the editor (streamed vs. a complete diff), and conflict handling if the AI generates while a human is also typing. Lower priority than the questions above — copy-paste is a complete enough stand-in for now.

## F-009 External-module trust model, given who actually picks the URL

External modules run with no sandboxing, trusted by analogy to "a developer choosing an npm package" ([decisions.md D-020](decisions.md#d-020-plan-preamble-modules-and-settings)) — but per D-003, the module URL is typically chosen by an AI, with the human reviewing the result afterward, a different risk profile than the analogy assumes. **Partially mitigated:** a `confirm()` gate before loading any non-shipped module ([D-045](decisions.md#d-045-a-confirmation-gate-before-loading-an-untrusted-external-module)) — moves the exposure from automatic to a deliberate per-URL choice, but adds no sandboxing; accepted code still runs with full page access. Still open: whether real sandboxing is ever worth building, and whether gating behind login + an explicit per-profile opt-in is worth the accounts infrastructure it would need.

## F-010 Shape-agnostic container extent

`parent.size.x` only resolves when the parent is `shape: "rect"` (the one shape kind with a `size` property) — a `circle` parent has `radius`, a `polygon`/`polyline` parent has `points` and no single "size." Whether this is worth a real shape-agnostic accessor (every node exposing a computed `bounds.x/y/width/height`) or whether "only `rect` containers support this" is an acceptable permanent constraint is open.

## F-011 Single-parent hierarchy: is multi-membership ever actually needed?

Nesting (D-013) is the only way to express a parent-child relationship — a node has exactly one parent. This buys real simplicity (no dangling parent references, drag-sync never validates a reference graph) at the cost that a node can't belong to two groupings at once (e.g. "inside the room" for coordinates *and* "part of the kitchen zone" as a non-spatial grouping). Whether this is ever actually needed for this language's target domains, or whether a purely cosmetic grouping already covers every real case, is open — not derived from hitting a concrete blocked case.

## F-015 Settings editable from the viewer, beyond the one case already built

A plan's settings are otherwise purely textual — turning on e.g. `edgeLengths` or `allowCollisions` means typing it. **One concrete case is now built:** the header menu's "Show grid" toggle reads/writes `settings.grid` directly ([decisions.md D-103](decisions.md#d-103-the-app-header-every-distinct-action-flat-and-always-visible-icon-led-export-grouped-as-its-one-deliberate-flyout--plus-a-settings-toggle-and-a-real-sign-in-popup)). Whether this generalizes to a real settings panel covering every setting, or stays a small set of individually-added toggles for the settings that are genuine on/off flags, is open.

## F-024 Domain coverage hasn't been audited against what a real floor plan needs

`rotation` for `rect` is built (D-141) — an angled wall or a non-rectangular footprint no longer forces hand-computed rotated polygon coordinates. Still open: no curves/arcs and no multi-level/floor concept at all, and how far to take either (versus leaving them a stated, permanent limitation) hasn't been decided. Also still open specifically from D-141's own v1 scope: `flush`/`placement: "outside"` against a rotated rect are unsupported (warn and fall back rather than attempt exact edge-projection math), and there's no interactive way to *set* rotation by dragging — only by typing it in the source.

## F-030 A reusable component/sub-plan concept

`compose` lets a *module* generate a structure from parameters (D-046/D-072), but there's no way to reuse a whole hand-authored *subtree* as data — "here's a bathroom layout, drop it into three different van plans." Related to F-027's now-built style presets (both are "define once, reuse without repeating") but at the granularity of a whole composition instead of one style object. Needs real thought before a shape is proposed: what identifies a reusable component, whether it lives inside one plan or is shared across files, how drag-editing a placed instance relates to editing the definition.

## F-034 Sharing a plan with someone else — static view vs. editable plan+code

Distinguishing two things: sharing just the rendered plan (F-005's own static-snapshot proposal, plausibly built on the export mechanism) versus sharing the plan *and* its editable source with a specific person — a fundamentally bigger exposure, handing over everything F-005's own scraping-protection reasoning tries to avoid giving away for free. Not designed: the mechanism for either (a durable share link implies the existing backend; plan+code sharing could be nothing more than exporting and sending source text), whether a shared plan is a live pointer or a frozen snapshot, and how either interacts with F-009's external-module trust question.

## F-038 Style-preset resolution is core-only — making it a module is unexplored

`resolveStyle`/`settings.styles` lives directly inside core's `renderShape`, resolved synchronously while each shape's SVG string is built — unlike every actual module (`annotations-module.js`, `grid-module.js`), which runs via `core.onRendered`, a **post**-render hook reading back an already-built SVG. By the time `onRendered` fires, `fill`/`stroke` are already burned into the string core generated, not still pending. Not designed: whether this would mean core deferring resolution (a placeholder attribute a style module rewrites after the fact) or a genuinely new pre-serialize hook nothing in this codebase offers yet — or whether the value here is purely architectural consistency rather than unlocking a concrete capability.

## F-042 Style modules and settings toggleable from the menu, beyond the one flag already covered

A menu that shows which modules/settings are *actually active in this exact plan* and lets someone flip them on/off, writing back via the same source-splice mechanism drag edits use. **The one setting that's a genuine, clean on/off flag is built** — `settings.grid`'s own presence/absence, via the header menu's "Show grid" toggle ([decisions.md D-103](decisions.md#d-103-the-app-header-every-distinct-action-flat-and-always-visible-icon-led-export-grouped-as-its-one-deliberate-flyout--plus-a-settings-toggle-and-a-real-sign-in-popup)). **Extended twice further:** [D-149](decisions.md#d-149-grid-front-layer-overlay-menu-editable-typesize-decoupled-from-snap) added `type`/`size` menu editing (`setGridSubKey`/`findNestedObjectSpan`, reusable one level into any settings sub-object); D-159 finished the set with a Layer group ("Behind shapes"/"In front"/"Hidden") and an Opacity field, both in the same Grid flyout — every grid sub-setting is now menu-editable, none left source-text-only. `snap` itself has its own header button (D-156), independent of `grid` entirely. Still open, and likely to stay open rather than resolve cleanly: every module (D-195 closed the last force-injected exceptions — interactivity/code-highlight/hierarchy) now does have a real, uniform "off" state at the declaration level (remove the `module "..."` line), but nothing in the menu shows or toggles that directly today, only `settings.grid`'s own flag; style presets aren't a meaningful binary toggle either (a named registry, not a flag). Not designed: how "currently active" would even be shown for a bare declaration that isn't a clean flag, and whether a non-auto external module (its own separate F-009 trust flow already) belongs in the same menu at all.

## F-045 A module store on the site for community modules

**Built at the smallest workable scope** ([decisions.md D-125](decisions.md#d-125-f-045-a-manually-curated-module-store-page)): `planagonia.com/modules`, a manually-curated static list — new entries added by hand (a PR or a direct email), not an open self-serve submission pipeline. Ships with an empty state, since nothing has been submitted yet. Deliberately chosen to sidestep, not resolve, the two harder questions below until there's real submission volume to design against:
- **F-009's external-module trust question stays exactly as open as it already was.** A short disclaimer on the page (third-party code, not covered by this repo's own `LICENSE`, still gated by the existing confirm-before-loading dialog) states the trust posture rather than changing it — whether *listing* something here reads as an implicit endorsement, beyond what the disclaimer already says, is untested with zero real listings.
- **F-046's licensing question is unchanged too** — a listed module is still someone else's code with no ownership terms attached by this project. Revisit both once real submissions start arriving; a one-line PR/email intake has no review or verification step to design in the meantime.

## F-046 How IP protection and eventual commercial success actually get implemented, beyond where the moat lives

**Where the protection comes from is now decided** ([decisions.md D-121](decisions.md#d-121-f-046s-first-concrete-answer-the-hosted-service-is-the-moat-not-client-code-secrecy--a-license-file-makes-todays-default-explicit)): the hosted service (accounts, cloud sync) is the moat, not client-code secrecy — the repo stays public, a `LICENSE` file now makes the existing "all rights reserved" default explicit rather than silent. **Trademark checked and a real Terms & Privacy page now exist too** ([D-191](decisions.md#d-191-f-046-trademark-checked-formal-registration-deliberately-deferred--a-real-patagonia-similarity-risk-recorded-not-dismissed), [D-192](decisions.md#d-192-f-046-a-real-terms--privacy-page-for-the-hosted-accountscloud-sync-service-that-was-already-live-with-no-stated-terms)) — formal trademark registration deliberately deferred (a real, recorded Patagonia-name-similarity risk, not a cleared one), and `homepage/terms/index.html` now governs the hosted service itself (data handling, account terms, acceptable use), linked from every registration form and the site's own footer. Still open:
- **A monetization shape isn't chosen** — free vs. paid, individual vs. team, self-hosted vs. cloud-only — none of the above answers *how the business works*.
- **F-045's module store now exists but is empty** — still needs its own explicit ownership/licensing terms before real submissions arrive; a listed module is someone else's code, not covered by this repo's own `LICENSE` at all. Also still open whether Planagonia itself could be forked using community modules as a shortcut around whatever protects the core.

Not a decision to make preemptively — recorded so the next concrete choice that touches any of this (F-045 itself, a pricing page, opening accounts more broadly) gets weighed against it rather than decided in isolation.

## F-049 The `<main>` content tabs (Code/Viewer/Layers) aren't a standardized, registrable system

Raised directly while adding a mobile "Layers" tab alongside the existing mobile Code/Viewer tabs (D-006). Today's `.tab-btn`/`data-mobile-tab` mechanism (`docs/index.html`) is a hand-built, mobile-only pane switcher with each pane hardcoded into the same script and CSS — adding Layers as a third tab meant editing that fixed set directly, the same way any future tab would. This is specifically about `<main>`'s own content-pane tabs — the *header's* own equivalent gap (a module couldn't add a button to the toolbar) was F-048, now closed by D-172's `core.registerHeaderAction`. Four related, undesigned questions the user raised together: (1) the tab mechanism itself should be standardized/generalized rather than remaining a one-off per-pane switch; (2) a module should be able to register its own new content tab — hierarchy-module.js's own Layers panel is already the first real example of "a module owns a pane" (unrelated to its own loading timing, which changed twice since this was written — D-174 made it unconditionally loaded, D-195 then put it back behind its own `module "..."` declaration like every other module), just not yet through any registration API; (3) each tab's width should be adjustable on desktop, not just the fixed code/viewer split (F-040) — unclear whether that means a resizable Layers sidebar, a user-chosen tab order/visibility, or something else; (4) "tabs" may not even be the right name for this concept once it's generalized beyond two hardcoded panes. Not designed: any of the above — recorded so the next content-pane addition (or a deliberate pass to generalize this) gets weighed against the whole set rather than another one-off hardcoded addition. **D-157 records a chosen future direction** for point (2) specifically (a `registerContentTab({ id, label, render, destroy })`-style API) without building it yet — deliberately deferred until a second real module (beyond hierarchy-module.js) needs it; D-172 closing the header-action half is itself a small, if indirect, signal this whole direction is worth eventually following through on. Points (1), (3), (4) remain fully open.

## F-052 How (and whether) user plan data could be used in the future — product improvement, aggregate statistics, or sale

Raised directly as a distinct facet of F-046's own still-open "monetization shape" question, specifically about the data itself rather than the service around it: today every plan a signed-in user saves lives in the cloud-sync storage this app already built (D-105's own account system), with no stated policy on what, if anything, that data could ever be used for beyond storing and returning it to its own owner — improving the product (seeing what kinds of plans people actually build, where they get stuck), aggregate/statistical use, or an outright sale of data itself as a business line. Not designed at all: whether any of these are even directions worth pursuing, what a user would need to be told or asked before any of them could happen (a real Terms of Service is itself still open, per F-046), and whether "the hosted service is the moat, not the code" (D-121) implies the *data flowing through* that service is part of the same moat or a separate question entirely. Recorded now, deliberately unresolved — a business/privacy decision, not an engineering one, and not remotely urgent while the user base is what it is today.

## F-053 Automatic, summed dimension chains along a shape's outer boundary — the bigger half of the arrow-dimension request, deliberately not built

Raised directly, from the same reference image that prompted the arrow-style edge-length dimension lines (D-169): a real architectural floor plan's own dimension strings don't just mark one wall segment at a time — they detect every wall/partition that touches a given outer boundary (say, the top edge of a building), break that boundary into segments at each one, draw a stacked row of individual arrow-dimensioned segments, and add a second, further-offset dimension line spanning the *whole* boundary with a running total ("12.50m Total Width"), often computed independently for more than one side (the reference image shows different segment breakdowns for the top and bottom edges of the same building, since different interior walls happen to align with each). Confirmed directly with the user before scoping D-169 down to exclude this: it needs a genuinely new geometry capability nothing in this codebase has today — grouping sibling elements' own edges by shared axis/alignment (not just "this one shape's own 4 edges," which is all `edgeLengthLines` computes now), deriving ordered breakpoints along that axis, and stacking multiple parallel dimension rows at increasing offsets so nested segment-vs-total lines don't overlap. Not designed at all: what counts as "aligned" for two edges belonging to different sibling elements (exact coordinate match? a tolerance?), which boundaries of a plan get this treatment automatically vs. requiring an explicit opt-in, and how a total row's own arrow-line offset is chosen once more than two levels of nesting exist (a segment breakdown *and* a sub-total *and* a grand total, in principle).

## F-054 `wall-with-door-module.js`'s door rendering doesn't read as an architectural door — wants a quarter-circle swing arc, and a rename to match

Raised directly: today's door segment (`expandWallWithDoor`, `docs/wall-with-door-module.js`) is just a short dashed `polyline` between `doorStart`/`doorEnd` with a hover label "Tür" — visually indistinguishable from any other dashed line, nothing that reads as "a door" the way a real architectural floor plan does. **The actual convention this is missing: a quarter-circle arc from the door's hinge point, swept through 90°, showing the leaf's open position and swing direction** — the standard symbol in every real floor plan, and the one piece of information ("which way does this door open, into which room") the current flat gap entirely omits.

**Renaming to `door-module.js` requested alongside the rendering fix** — `wall-with-door-module.js`'s own name ties the concept to being a wall-embedded composite specifically; once the module's job is really "draw a door" (the swing arc is about the *door*, not the wall it happens to sit in), the narrower wall-specific name stops fitting. Not yet decided how far the rename implies a scope change too — still open:

- **Does the swing arc apply only to today's `compose: "wallWithDoor"` composite, or does "door" become its own standalone, placeable thing** (any door-width gap, not necessarily authored via `from`/`to`/`doorAt` on a synthesized wall pair)? The module currently has no concept of a door independent of the wall composite it's embedded in.
- **Swing direction/hinge side isn't in today's schema at all** — `from`/`to`/`doorAt`/`doorWidth` describes where the gap sits along the wall, nothing about which side of the wall the leaf swings into or which end it's hinged at. A real arc needs at least one more parameter to pick a hinge corner and a swing side (into vs. out of the room), not just reuse of what's already there.
- Whether this is a rename of the existing file (`git mv`, updating every `module "wall-with-door-module.js"` declaration across `docs/`'s own `EXAMPLES`, `TRUSTED_MODULES`/`ORDERED_MODULES`, and `language-spec/modules.md`) or a new module alongside the old one, deliberately not decided here.
