## F-001 Constraint-solving scope

[decisions.md](decisions.md#d-014-connection-semantics) accepts that unlimited connections + rigid drag propagation can produce over-constrained/conflicting demands on a node — the same class of problem CAD geometric-constraint solvers exist for. Explicitly deferred: build the simple case (e.g. straightforward chains) first and revisit how far to take it (real constraint solver vs. a hard complexity cap) once that's prototyped and we see how often it actually falls short in practice.

Narrowed by [decisions.md](decisions.md#d-018-points-as-node-references-shared-corners): a shared corner-node reference keeps two lines' endpoints exactly together with no solving needed at all (it's one Node, not two synchronized copies). Real conflict only arises for looser Connection-based attachments (e.g. a door that should stay somewhere along a wall without a pinned shared point), which is a smaller and more specific problem than "any connection graph" — may make a real solver unnecessary rather than just simple-case-first.

**Narrowed further, this time given a concrete shape: [decisions.md](decisions.md#d-032-parent-child-placement-modes)** designs exactly this "door stays somewhere along a wall" case as a connection `placement` mode with constrained-sliding drag, rather than a general conflict-resolution problem — the sliding-drag mechanic itself is now built and confirmed working ([Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/), see D-032's validation note), narrower support for the idea that this stays a small, specific fix rather than a general solver. `placement` moved from a connection property onto the element itself (D-032's revision), and mode 3 ("inside") is now wired into `docs/` too, not just validated standalone (D-044) — narrowed to a rect child in a rect/polygon parent, same scope Prototype 16 validated.

**All three placement modes now built: [decisions.md D-071](decisions.md#d-071-f-001-flush-built-closing-d-032s-last-unbuilt-half--the-app-back-on-the-products-own-core-questions-not-just-its-sitedecisioninfra).** `flush` (mode 3's door-in-wall addition, layering edge-attachment on top of containment) closes the specific gap this entry used to flag — built as a rect-in-rect-only mechanic mirroring mode 2's own outside-attached sliding, not a general solver. An unrecognized `placement` value now warns on drag too, closing the "any parser-level validation" half of the old gap (as a drag-time warning, not a parse-time error — matching this language's existing pattern of surfacing bad values where an author is actually looking, D-044). Still open, unchanged: containment/flush for an element moved along by a `connection` rather than dragged directly (F-004's own gap, shared by both checks), and whether F-001's *broader* question — a real geometric constraint solver, vs. staying a growing collection of specific, geometry-scoped mechanisms like these three — is ever actually needed. Three concrete, narrow mechanisms have now covered every case asked for so far without one; that's evidence toward "maybe not," not a final answer.

## F-002 Module API surface

Since modules can add rendering, interactivity, and new primitives (see [decisions.md](decisions.md#d-013-core-primitives) and [decisions.md](decisions.md#d-011-module-capabilities)), what exactly does the module API expose (hooks into the renderer, the parser/primitive registry, the interaction/drag system)? Needs the core primitives and renderer design settled first.

**First working attempt, rendering-only:** [Prototypes/12-module-loading/](../Prototypes/12-module-loading/) is the first prototype to actually load and run a module — before this, `module "..."` (D-020) was documented syntax nobody had exercised, despite modules being core aim #3. Confirmed working end-to-end by the user: both an internal module (bundled in the page, resolved by bare name) and an external one (fetched at runtime via a dynamically created `<script src>` tag, from a plain adjacent `.js` file) successfully register a new shape-rendering function the core calls exactly like a built-in shape. Still only the rendering slice — nothing about interactivity hooks or new-primitive composition (D-011's other two promises) has been tried. A real bug was caught and fixed while building it: the internal-module path was missing the "already loaded" guard the external path had, so it silently re-registered itself (and re-logged) on every single render, including every drag frame.

**Second attempt, interactivity this time — see [decisions.md](decisions.md#d-031-interactivity-as-a-module) for the full design.** [Prototypes/14-interactivity-module/](../Prototypes/14-interactivity-module/) moves *all* of 13-unified's interactivity (drag, selection, connect/disconnect with snap, hover, the right-click menu) out of the host page and into a module loaded the same way a shape module is. A `window.PlanCore` API had to be designed for this to be possible at all — the first concrete answer to this question's "what does the module API expose" — but it's still one rough attempt, not a settled proposal, and it surfaced real seams rather than a clean cut: icon z-order relative to core's anchors changed, a rendering-level CSS rule (label hover-reveal) needed a higher-specificity override from the module rather than core knowing about drag state, and core had to expose an explicit `preserveViewBox` flag on re-render since it can no longer infer "is this a drag continuation" on its own.

**Third attempt, composition this time — D-011's third module promise, finally tested (D-046).** [Prototypes/17-module-composition/](../Prototypes/17-module-composition/) lets a module offer a reusable, higher-level building block ("wall with a door," language.md's own long-standing illustrative example) built from ordinary Elements. The API answer this time: one new hook, `core.registerBeforeRender(cb)`, letting a module inject synthesized child nodes into the parsed tree before `render()` ever sees it — small and targeted, not a general plugin system, and rendering itself needed zero composition-specific code once it existed. **Real limit found, not assumed:** a synthesized child has no source-text span to write a drag edit back to, so drag-editability of a composite's generated pieces would need a per-composition-type backward-solve into the composite's own parameters — genuinely untried, flagged as its own open question rather than silently out of scope.

**Interactive composition now built too — [decisions.md D-072](decisions.md#d-072-f-002-drag-editability-for-a-composite-the-last-open-half-of-d-046).** `registerBeforeRender` and `wall-with-door-module.js` promoted into `docs/` (not just the prototype), plus the actual backward-solve D-046 had explicitly left untried: dragging a wall segment moves the whole composite (rewrites `from`/`to` together); dragging the door slides `doorAt` along the wall, clamped to its own span. Deliberately **not** a general mechanism — a `composeParentOf`/`composeDragEdits` pair specific to `wallWithDoor`, matching D-046's own framing ("a per-composition-type backward-solve," not a generic one) rather than overclaiming a pattern from a sample size of one. F-002's three module promises (new rendering, new interactivity, new higher-level compositions — D-011) are now all demonstrated end to end, rendering *and* interactive, in the live product, not just a throwaway prototype. Still genuinely open: whether the backward-solve approach generalizes to a *second* composition type at all, untested since only one has ever been built.

## F-004 Collision and realism checks

[decisions.md](decisions.md#d-020-plan-preamble-modules-and-settings) establishes that collision-avoidance between objects and polygon-realism checks are real default behaviors (overridable via `settings`), but not their mechanics: what exactly counts as a "collision" (any overlap? only between certain kinds of nodes?) or an "unrealistic polygon" (self-intersecting? zero-area? non-convex?), and how a violation surfaces to the user — a D-015-style warning, a rejected edit, something else. Needs its own design pass, likely after the module API surface (F-002) since these checks might themselves be implemented as a built-in module rather than hardcoded into the core renderer.

**Both halves now built**, narrowing but not closing this question. [Prototypes/05-polygon-corners/](../Prototypes/05-polygon-corners/) implements `allowUnrealisticPolygons` concretely — "unrealistic" means self-intersecting (not non-convex, since e.g. an L-shaped room is realistic), checked via standard non-adjacent-edge-segment intersection. `allowCollisions` is now built too (D-041, in `docs/interactivity-module.js`, not core) — a rect/circle/polygon overlapping a sibling is a **rejected edit**, the same pattern D-015's unsolvable-expression case doesn't use ("complete visually and flag") — both checks know exactly what's wrong and a valid state is one cursor-step away, unlike an unsolvable expression.

**Still open:**
- **Only the directly dragged element is collision-checked**, not anything moved along with it via a `connection` — a real gap for a drag that propagates (D-014), not yet addressed. D-044 wired D-032's containment check ("inside" placement) in alongside collision checking, sharing this exact same gap: a connected follower isn't containment-checked either, only whatever's directly dragged.
- **Whether collision checking should ever extend beyond siblings** — D-041 scoped it to same-parent elements specifically to sidestep containment (a chair inside a room isn't colliding with the room), but that also means two elements in *different* parents that happen to visually overlap are never checked at all.
- **F-002's module-API question, now partially answered by example rather than resolved in general**: both checks turned out to fit inside `docs/interactivity-module.js` using only D-031's existing API (no new core hook needed) — but that's because both are drag-validation concerns tightly coupled to the module that already owns dragging. Whether *other* kinds of checks a future setting might introduce would fit as easily is untested.

## F-005 Public plan viewing

Whether a plan can ever be shown to a non-owner at all (e.g. a public share link) has never been decided as a feature — moved here from decisions.md (D-022) after a critical review, since that decision had started specifying *how* to protect such a view before the feature itself existed.

If this is ever built, the reasoning already worked out: serve it as a server-rendered static snapshot (flattened SVG/PNG) rather than the raw plan-language source — a viewer gets a picture, not an editable structure, which protects the owner's content (see [decisions.md](decisions.md#d-022-scraping-protection-content-not-the-language)) and doubles as a performance win (render once server-side and cache it, instead of every viewer re-parsing/re-rendering client-side). This is a principle to reuse *if and when* public viewing is decided, not a commitment to build it.

## F-006 Documentation–implementation gap (AI-authoring test)

D-003/D-017 rest on the premise that an AI can author valid plan code from the documentation alone. Tested directly: a fresh agent instance was given *only* `documentation/language.md` (no prototype source, no decisions.md) and asked to write a campervan-interior plan. The result **fails to parse against every existing prototype**:

- It used `connection { from: ..., to: ..., kind: "directional" }` (object-literal form) because that's the only syntax `language.md` shows — but no prototype implements that. 03 is the only one with `connection` support at all, and its actual (only-ever-tested) syntax is positional: `connection wall_a door`, no braces, no fields. Against 05 (the most complete prototype, which dropped `connection` entirely after D-018), the block causes a hard parse error. Against 03, the plan fails earlier still, at `settings { ... }`, since 03 predates D-018/D-020 and has neither `settings` nor `polygon` nor points-as-references.
- It used a sibling property path (`swivel_seat_1.position.x`) reasoning by analogy from `parent.size.x`. This parses (the grammar doesn't distinguish `parent` from any other identifier), but crashes at render time — only `parent.<prop>.<x|y>` and single-segment corner-references are actually implemented; general sibling-to-sibling property paths are not.
- It had to guess the nested-children syntax entirely — `language.md` states nodes can have children, but no example in the doc ever shows one `node { }` containing another. The guess happened to match the real grammar, but nothing in the doc confirmed it; a different equally-plausible guess (e.g. a `children: [...]` list) would have failed.

**To be fair, this also partially validated D-017.** Every failure above was in an under-documented area (connections, sibling paths) — the *core*, well-documented grammar (basic node/property syntax, the `parent.size.x` expression pattern, literal arrays) came out correct on the first try, with no ambiguity errors at all. The low-ambiguity goal seems to be holding up where it's actually been tested; the gap is documentation completeness, not grammar ambiguity.

**Conclusion:** `language.md` currently documents a language broader than what any single prototype implements, and the specific mismatches (connection syntax, sibling-path scope) are exactly the kind of thing that breaks a real AI-authoring workflow, not edge cases. Needs a documentation pass reconciling the spec with what's actually been built — either narrow the doc to match 05 (the most complete implementation) or extend the implementation to match the doc, but the current gap is real and was previously just assumed not to exist.

## F-007 Drag performance at scale

03/04/05 all re-tokenize and re-parse the *entire* plan source, walk the *entire* node tree twice (`computePositions`, `computeCornerUsers`), and replace the *entire* rendered SVG via `innerHTML` — on every single `pointermove` event during a drag, not just at the end of the gesture. Fine at prototype scale (10–20 nodes); at production scale (a full floor plan, potentially hundreds of objects), full-DOM-replacement 60+ times a second during one drag is a known performance anti-pattern likely to cause visible jank, independent of the parsing cost itself. If it holds up, the fix is incremental/targeted DOM updates (move just the dragged element's attributes) rather than full regeneration per move.

**Measured, not just reasoned about:** [Prototypes/11-performance-test/](../Prototypes/11-performance-test/) benchmarks the same unmodified architecture at increasing object counts, timing real parse+render cycles with `performance.now()` and confirming the feel with actual dragging. Result: **800 objects still felt fine; 2000 went over the 60fps frame budget**, confirmed both by the on-page timing numbers and by the drag itself feeling laggy. This narrows the risk from "maybe a problem, unmeasured" to a concrete threshold — the current architecture is fine for a single room or a small home, and would need the incremental-update fix before comfortably handling a large multi-room plan with hundreds of furniture objects. Exact number isn't precise (not bisected between 800–2000, and the benchmark measures parse+render string cost specifically, not full pointer-to-paint latency — see the prototype's own caveat), but "somewhere in the low thousands" is now a real data point, not a guess.

## F-009 External-module trust model, given who actually picks the URL

[decisions.md](decisions.md#d-020-plan-preamble-modules-and-settings) justifies trusting external modules with no sandboxing by analogy to "a developer choosing an npm package" — but per D-003, the module URL is typically chosen by the **AI**, with the human reviewing the resulting code afterward, not actively researching and choosing the package themselves. That's a different risk profile than the analogy assumes. Partially mitigated in practice by D-023 (copy-paste): the human has to actually look at the whole pasted plan to bring it into the app, which is more exposure than a silent auto-apply would give — but this hasn't been examined as a deliberate mitigation, just noted as a side effect. Whether the trust model needs revisiting (e.g. an allowlist, or flagging module declarations for explicit human attention during review) is open.

**One concrete option raised: gate external modules behind login + an explicit per-profile opt-in.** Restricts exposure to identifiable accounts and turns loading external code from "happens automatically whenever a plan declares one" into a deliberate, out-of-band choice — real mitigation, not nothing. But it doesn't make the code itself any safer to execute: no sandboxing is added, so once a user has opted in, an external module still runs with full access in their browser — this narrows *who* is exposed, not *what* they're exposed to. Also depends on D-019/profiles existing as actual code, which they don't yet (decisions-only) — can't be built or tested until then. Internal (bundled) modules wouldn't need this gate at all, only external (URL-loaded) ones, matching D-020's existing internal/external split.

**A first, narrow mitigation shipped (D-045): a `confirm()` gate before loading any module that isn't one of the three the app ships itself.** Doesn't resolve this question — no sandboxing was added, accepted code still runs with full page access, and the gate is a per-session, in-memory choice with no persistence or account tying (D-019 still doesn't exist as code). What it does do: moves the exposure from "happens automatically whenever a plan declares one" (this open question's own original framing) to "a deliberate choice, once per URL per session" — a real, if partial, step in the direction the "gate behind login + opt-in" option below already described, just without needing accounts to exist first.

**A second option considered and mostly rejected: a dedicated module file format instead of plain `.js`.** A different extension by itself changes nothing — a `.planmodule` file that still just gets executed as code is the same trust problem with a relabeled file, not a mitigation. It could matter if paired with an actually restricted execution model (a non-Turing-complete declarative format that's validated/sandboxed rather than run as arbitrary code), but D-031 already shows this can't replace `.js` outright: an interactivity module needs genuine imperative logic (event handling, DOM/state manipulation), which isn't expressible in a safe declarative format. The narrower version that might still be worth something: a *second*, safer format for the pure-rendering-only module case (props → SVG template, no behavior) offered *alongside* `.js`, not instead of it — untested, not designed, just not fully dismissed either.

## F-010 Shape-agnostic container extent

`parent.size.x` (the only concrete example of D-012 solve-backward anyone has actually written) only resolves when the parent happens to be `shape: "rect"` — the one shape kind with a `size` property. A `circle` parent has `radius` instead, a `polygon`/`line` parent has `points` and no single "size" at all; there's no way to express "position me relative to my container's extent" that works regardless of what shape the container happens to be.

Whether this is worth solving with a real shape-agnostic accessor (e.g. every node exposing a computed `bounds.x`/`bounds.y`/`bounds.width`/`bounds.height` derived from its own geometry, independent of `shape`) or whether "only `rect` containers support this" is an acceptable, permanent constraint is open — found during the D-029 naming/syntax review, not evaluated for a fix yet.

## F-011 Single-parent hierarchy: tree, not graph

Nesting a `node { }` block inside another's braces (D-013) is the *only* way to express a parent-child relationship — a node has exactly one parent, whichever block textually contains it, with no separate `parent: X` field to contradict or duplicate it. This buys real simplicity: no dangling/duplicate parent references are even expressible, D-010's local-scope expression rule falls directly out of lexical nesting, and drag-sync only ever has to edit a value, never validate a reference graph.

The cost: a node can belong to exactly one grouping at a time. There's no way to say a piece of furniture is both "inside the room" (for coordinates/containment) and "part of the kitchen zone" (a non-spatial grouping that cuts across the room's own structure) — D-013's Connection is the only other relationship primitive, and it doesn't establish a coordinate space or imply containment, so it isn't a substitute. Whether multi-membership is ever actually needed for the domains D-001 targets (it may not be — a "zone" might be fine as a purely cosmetic grouping, not something the language needs to model) is open; found while discussing the parent-child design directly, not from hitting a concrete case that needed it.

## F-012 Drag-driven reparenting is untested

Every prototype that drags a node keeps it inside its original parent — nothing has ever tested dragging a node out of one parent's block and into another's, i.e. an interactive reparenting gesture. Given F-011's single-parent model, reparenting isn't a simple value edit like a normal drag: it means moving the whole `node { ... }` text block from one location in the source to another *and* recomputing its position, since coordinates are local to whichever parent currently contains it (D-013) — the same absolute point has a different local value under a new parent, so a naive text-block move alone would visibly teleport the object unless the position literal is also rewritten as part of the same edit.

Nothing about this is known to be hard — it's a bigger text splice than today's edits (D-009/D-012's machinery only ever adjusts individual property spans, never cuts and relocates a whole block) plus a coordinate transform, both individually straightforward — but it's genuinely unbuilt and unproven, not just unmentioned. Found from the same parent-child design discussion as F-011, before any prototype attempted it.

## F-014 Viewer background grid

A checkered background in the viewer, each square a stated real-world size (e.g. "1m per square"), as a scale reference — complementary to or possibly overlapping with D-035's scale bar. Pure display, no interactivity dependency, so by the D-039/D-042 test this is a module candidate rather than a core rendering feature. Not designed further than that.

**A second grid style added right after, same session: `settings { grid: { size: 1, type: "lines" } }`** — plain grid lines alongside the original checker (still the default when `type` is omitted, so nothing already using the grid changed appearance).

## F-016 Context menu: Duplicate and Scale

D-030 built the right-click menu with exactly one action, Delete Element. Two more were requested directly, not designed: **Duplicate** (clone an element and its subtree with a fresh unique id, inserted as a new text block) and **Scale** (a resize gesture distinct from move).

**Duplicate is built — [decisions.md D-074](decisions.md#d-074-f-016-duplicate--scale-kept-as-its-own-follow-up-not-bundled-in).** Clones the clicked element's whole subtree with every id renamed (collision-retried), corner-refs inside the subtree repointed at their new counterparts while ones pointing outside stay on the original, and internal (both-ends-inside) connections duplicated too. Found and fixed a real gap along the way: a corner-ref never had its own source span tracked at all, needed to actually rewrite one in place — a small, purely additive parser change.

**Scale remains open, deliberately not bundled into the same batch — asked directly which to do first.** It raises a real design question Duplicate didn't have: for a plain `rect`, "scale" plausibly means adjusting `size` — but for a corner-reference-built polygon/polyline (D-018), scaling would mean moving every referenced corner outward from some pivot, not editing a single property, a materially different mechanism than anything currently built. It also has no existing gesture to hang off of (unlike a move-drag or the outside-attached/flush slide mechanics) — grabbing "scale" as a gesture distinct from "move" likely needs new resize-handle UI, shown only once an element is selected, which is itself new interaction surface this app doesn't have yet.

## F-017 Undo/redo

**Built — [decisions.md D-073](decisions.md#d-073-f-017-undoredo--a-real-design-fork-asked-about-directly-not-assumed).** Every edit (a drag, a context-menu action, typing) used to commit immediately to `sourceEl.value` with no way to undo a programmatic one at all — typed edits got the browser's native textarea undo stack for free, but a drag or context-menu action mutating `.value` directly never registered on it. A real design fork was surfaced and asked about before building: making programmatic edits participate in the *native* undo stack is possible (`document.execCommand("insertText", ...)`) but requires focusing the textarea first, which pops the on-screen keyboard on a touch device on every single drag — checked directly, not assumed, and rejected for that reason. Built instead as a small, explicit app-level history (a plain array of full source-text snapshots), global Ctrl+Z/Ctrl+Shift+Z interception, and toolbar Undo/Redo buttons (asked about directly too — keyboard-only would make undo unreachable on mobile, where Ctrl+Z isn't a concept at all). Scoped to one plan's own session; resets on every plan-load path.

## F-018 Label/annotation layout has no collision avoidance

Found by building and rendering a real, moderately dense example (a Fiat Ducato campervan interior — the first time this session tested a plan closer to real-world density than the shipped examples) rather than by reasoning about the annotations module in isolation. Two `show: "always"` labels positioned near each other (the van's own name, the rear bed's dimension label) rendered directly on top of one another, illegible — confirmed by screenshot, not assumed. D-041 gives every *shape* collision avoidance by default; nothing analogous exists for *text*. `show: "hover"` sidesteps the problem by only ever showing one label at a time (whatever's under the cursor), which is why every shipped example uses `"hover"` almost everywhere and happens to avoid this — but `"always"` is a real, documented, intentionally-offered option (D-026), and it breaks as soon as two always-shown labels are close together, which is a completely ordinary thing to want in a real plan (a room name and a piece of furniture's own dimensions, both worth seeing at a glance).

**Built — [decisions.md D-079](decisions.md#d-079-f-018-always-shown-labels-now-nudge-apart-instead-of-overlapping). Chosen from this entry's own three options: automatic nudging, not a warning or a documented limitation** — a real fix for the failure this entry describes, not a workaround the author has to apply by hand. A real, second bug found and fixed along the way: label/dimensions text and the (much more numerous) per-edge length texts turned out to share one flat markup group, so an early version of the nudge dragged edge-length labels away from the edges they describe too, for a conflict that was never about them — fixed by giving label/dimensions their own nested group specifically so the nudge can move just that.

## F-019 A container whose children fully cover its own footprint becomes unclickable as a unit

Also found via the Ducato test, not predicted. A `kitchen` counter with a `sink` and `stove` nested inside it (an entirely ordinary composition — built-in cabinetry with appliances inset into it) became impossible to select or drag *as the counter* once built: since children render after (on top of) their parent, and the sink+stove together happen to cover nearly the counter's whole footprint, `elementFromPoint` at the counter's own bounding-box center resolves to the stove, confirmed directly, not assumed. Every attempted "drag the kitchen" gesture actually grabbed whichever appliance happened to be underneath the cursor instead. There's no reserved margin a parent keeps clickable, and no rule giving a container drag-priority over which child currently occupies a given pixel.

**Built — [decisions.md D-077](decisions.md#d-077-f-019--f-021-click-cycling-through-stacked-elements-a-single-mechanism-for-both). Asked directly which of the three candidate mechanisms this entry originally listed was the actual long-term-right one, not just the cheapest — chosen because the same mechanism also closes F-021**, the broader version of this exact problem, rather than needing a second, different fix later for the case a parent/child-specific approach wouldn't have reached.

## F-020 `childPlacement` doesn't propagate past one nesting level

The third finding from the same test. `van` sets `childPlacement: "inside"`; its direct child `kitchen` correctly stays contained — but `kitchen`'s own children (`sink`, `stove`, grandchildren of `van`) are entirely unconstrained by it. Confirmed directly: dragged the stove roughly 700px, well outside the van's own 3.1m × 1.87m bounds, and it moved there freely with no clamp and no warning (`placementFor` only ever checks a node's *immediate* parent's `childPlacement`, never a more distant ancestor's). An author setting "keep everything inside the van" on the outermost container has a reasonable expectation that it means everything nested inside it, not "direct children only, nothing nested any deeper" — the current behavior is a real, silent gap between what the property name implies and what it actually checks.

**Built — [decisions.md D-078](decisions.md#d-078-f-020-childplacement-now-searches-upward-through-every-ancestor-not-just-the-immediate-parent).** Resolved the way this entry's own "search upward through every ancestor looking for the nearest one that set it" option described: an inherited `childPlacement` now walks up the ancestor chain for the nearest one that actually made a claim, rather than stopping at the immediate parent regardless of whether it ever set anything. Fixed at both call sites that had the same one-level limitation — the drag-time clamp *and* F-022's load-time validation pass, which shared the exact same bug and would otherwise have kept missing a grandchild escaping its grandparent even in a plan nobody ever dragged.

## F-021 Stacked/overlapping elements have no way to reach whatever's underneath

A broader version of F-019's specific case, requested directly once F-019 itself was recorded. F-019 is one *cause* of overlap (a parent fully covered by its own children); this is the general problem regardless of cause — two elements that happen to overlap at all, parent/child or otherwise (siblings under a relaxed `allowCollisions`, a label's hit area crossing another shape, anything visually stacked). Whichever element is later in render/document order always wins every click, unconditionally — there is currently no way to reach whatever's underneath it: no click-again-to-cycle, no modifier-key to pick a specific z-layer, no visual indicator that something else is even there to be reached. A user (or an AI reviewing a screenshot) has no way to discover a hidden element exists at all short of reading the plan's own source text.

**Reaching it was built as a side effect of F-019's own fix — [decisions.md D-077](decisions.md#d-077-f-019--f-021-click-cycling-through-stacked-elements-a-single-mechanism-for-both).** Click-cycling (`document.elementsFromPoint`-based, front-to-back, wrapping) doesn't reason about the tree at all, so it never needed to know F-021's case was "different" from F-019's — a repeated click at the same point steps through everything actually painted there, ancestor, descendant, or unrelated sibling alike.

**Discovering it — the half that stayed open — is now built too, [decisions.md D-083](decisions.md#d-083-f-021s-remaining-half-a-hover-indicator-for-stacked-elements).** Hovering an element now dims it slightly and shows a small badge naming how many other elements sit at that same point, if any do — an immediate signal that something else is reachable there, rather than requiring someone to already suspect it and try clicking again blind. A real false-positive was found and fixed while building it: a naive version flagged *every* nested element, since a child's own parent (and the plan's own root, always) is geometrically "underneath" it by definition — true, but never a surprise, and it made the hint fire everywhere rather than only for a genuinely hidden container. The plan's own root is now excluded from the count.

**A third refinement, requested directly and built the same session — [decisions.md D-086](decisions.md#d-086-f-021-a-third-refinement-the-selected-element-now-visually-raises-to-the-front).** Once selected (by either mechanism above), an element's whole subtree now visually raises to the front of the SVG, so a just-reached, just-discovered element is also actually *visible* rather than merely functionally selected while still hidden underneath whatever covered it. A real bug found while designing this, not after: raising the DOM on every selection change broke D-077's own click-cycling arithmetic mid-sequence — fixed by freezing the cycle's own candidate list for the lifetime of one cycling sequence rather than recomputing it fresh on every click.

**A fourth refinement, same session — [decisions.md D-087](decisions.md#d-087-f-021s-stack-hint-badge-now-shows-a-small-named-list-not-just-a-count).** The hover badge now names every stacked element (its `label`, or raw id) in a small list, with the currently-selected one marked, instead of only a bare count — requested directly with a concrete mockup. A real bug found while building it: the badge's own list originally excluded the root (matching the trigger check's own reasoning), but click-cycling itself can reach the root, leaving the marker with nothing to point at when it did — fixed by keeping the trigger root-excluded while building the *displayed* list from the same unfiltered set click-cycling actually uses.

**Two more real bugs reported directly and fixed, same session — [decisions.md D-088](decisions.md#d-088-f-021-two-more-real-bugs-reported-directly-the-list-still-reordered-in-practice-and-outside-attached-elements-falsely-counted-as-stacked).** (1) The list could still visibly reorder in practice despite D-087's own fix, since real mouse jitter (unlike an automated test's exact-coordinate clicks) can re-fire `pointerover` mid-cycle and recompute against `bringToFront`'s already-changed order — fixed with a stable-order cache keyed by group membership rather than by hover session, immune to any retrigger. (2) An `placement: "outside"`-attached element (touching its own container, not overlapping it in any meaningful sense) could still falsely register as "stacked" with it — fixed relationally (excluding exactly that relationship from a stacked-hint group) rather than with general overlap-area geometry, which was considered and explicitly deferred as materially bigger than the case actually reported. A genuinely persistent front/back swap remains a separate, not-yet-built right-click action — confirmed directly that ordinary click-cycling must stay visual-only and never itself write to the plan's source.

## F-022 Collision/containment are only ever checked during a drag, never against a plan's own static declaration

Found twice, independently, in the same session: once by auditing the collision/containment code directly (it only ever runs from inside `applyDrag`), then confirmed the concrete way — a plan generated by a different AI (ChatGPT, given the same "Fiat Ducato campervan interior" prompt as a comparison test) had `allowCollisions: false` set and *still* shipped a rug polygon slicing through a table and two elements (`rear_door_left`/`rear_door_right`) declared at the exact same coordinates. Neither was ever flagged, because nothing checks a plan's own initial, as-authored layout — only what happens to something *during* an interactive drag. A setting that looks like it validates the plan doesn't actually do anything until a human or an AI happens to nudge the affected element by hand.

**Built — [decisions.md D-075](decisions.md#d-075-f-022--f-028-a-load-time-validation-pass-with-duplicate-id-detection-folded-into-the-same-sweep).** No new mechanism, as predicted below — a second call site for the already-correct `clampToNoCollision`/`clampToContainment`, run automatically against every freshly rendered plan's resting positions, surfacing every violation found in a dedicated panel rather than only the one a user happens to stumble into by dragging. Re-running it against the original ChatGPT comparison plan found far more than the two spot-checked by hand originally: 36 real pairwise overlaps, not two. Found and fixed a real false-positive bug along the way in the shared `isContained` helper (ray-casting's boundary ambiguity flagging a legitimately `flush` element as a violation) — see D-075 for the full account.

## F-023 No formal grammar or property schema — the parser is the sole, unverifiable spec

Found via an independent review of the language against its own stated goals, not from a specific bug report. There is no grammar file and no declarative registry of what properties a given `shape`/feature accepts — `documentation/language.md` is prose, and the hand-rolled recursive-descent parser in `docs/index.html` is the only precise definition of the language. This has a concrete, repeated cost, not just a theoretical one: every one of the following is really the same failure ("used something the language doesn't define") surfacing differently because nothing centrally validates against a known-good list — an unrecognized `shape` value renders as a silent invisible point with zero warning (confirmed live: `shape: "hexagon"` produces no error anywhere); `rotation: 45` on a `rect` parses fine and silently does nothing, since rotation was never implemented at all (see F-024); `flush: true` alone, without the co-required `placement: "inside"`, silently does nothing either — confirmed live, dragged straight through a wall with no clamp and no warning.

Not designed: whether this becomes an actual schema file consulted by the parser (closing the "which one is the ground truth" gap along the way), a lighter-weight declarative property registry checked separately from parsing, or something else — but whatever form it takes, it should replace the current pattern of each feature's own author remembering to hand-write its own validation (which is exactly how the three examples above went unnoticed for as long as they did).

**Built — [decisions.md D-084](decisions.md#d-084-f-023-a-property-schema-checked-as-one-more-load-time-validation-pass). The lighter-weight registry, not a grammar file** — a per-shape property allow-list checked as three more functions in F-022's existing load-time validation pass (D-075), not a parser rewrite. Covers all three named symptoms (unrecognized `shape`, `rotation`-on-`rect`-style unsupported properties, `flush`-without-`placement:"inside"`) plus two more real instances of the identical gap found while grounding the plan: `dimensions` on `polygon`/`polyline` and `edgeLengths` on `circle` were already documented as meaningless in `documentation/language.md` but never enforced anywhere until now. A formal grammar file — the other option this entry itself named — remains genuinely open if the "which artifact is the real spec" question ever becomes actively painful; not needed for the concrete problem (silent, unflagged mistakes) this closes.

## F-024 No rotation, and domain coverage hasn't been audited against what a real floor plan needs

Found via an independent review, then confirmed concretely: `rotation` isn't a property this language implements anywhere — a `rect` is always axis-aligned, and (per F-023) declaring `rotation: 45` on one parses and is silently ignored rather than erroring. For the language's own stated domain (floor plans, property layouts, campervan interiors — homepage copy names all three), an angled wall or a non-rectangular building footprint is an entirely ordinary case, not an edge case; today it's only reachable by hand-computing rotated polygon coordinates, forfeiting `rect`'s own conveniences (`size`, the exact rect-in-rect containment clamp, `flush`, collision checking's own rect-specific fast paths). No curves/arcs exist either, and there's no multi-level/floor concept for anything beyond a single flat plane. Not designed: whether `rotation` becomes a flat sibling property next to `position`/`size` (the natural fit, matching this language's existing flat, unwrapped style — a `transform: {}` grouping object was considered directly and rejected, since it adds nesting/tokens for no functional gain and breaks from precedent), and how far to take the rest of this list (curves, multi-level) versus leaving them a stated, deliberate limitation.

## F-025 No version marker anywhere in the plan format

Found via an independent review. Nothing — no `settings { version }`, no header line, nothing — identifies which revision of the language a given saved plan was written against, despite the language having already changed shape multiple times in one week (`placement`, `flush`, `compose`, `childPlacement` all added after the first plans existed). Costless today; the only thing standing between a future breaking change and every plan already saved in `localStorage` or the cloud storage service silently starting to mean something different, with no way to tell old from new.

**Built — [decisions.md D-081](decisions.md#d-081-f-025-a-version-marker-settings--version-1--purely-a-forward-compatibility-placeholder). Resolved exactly as scoped: `settings { version: 1 }`, purely a placeholder.** No parser change needed at all — `settings {}` was already a generic object literal, so an unrecognized key parses for free. The app's own three shipped examples now set it; an absent `version` is treated as `1` by convention, not enforced anywhere, since the language hasn't had a breaking change since this field was introduced. Nothing branches on it yet — that's deliberate, matching this entry's own "purely a forward-compatibility placeholder until it's actually needed" framing.

## F-026 The "pinned to an edge, slides along it, clamps, warns at the ends" mechanism has been independently rebuilt three times

Found by noticing the pattern while building the third instance, not by planning for it. Outside-attached (D-032, mode 2), flush (D-071), and the compose module's door-along-a-wall backward-solve (D-072) are all the same underlying mechanic — project the attempted motion onto one axis, ignore the perpendicular component, clamp the along-axis component to a valid span, warn once the end is reached — implemented three separate times, in three separate functions, with no shared code between them. D-018 flagged this exact possibility in advance ("a third, independent need would be a better time to generalize" — noted when only two near-identical implementations existed, for collision-clamping and standalone containment). That third instance has now happened twice over (flush makes four total, counting the original D-041 collision-clamp this pattern is itself descended from). Not designed: what the shared utility's actual interface would look like, or whether unifying these four call sites is worth the risk of a regression across every one of them for a refactor with no user-visible behavior change.

## F-027 No way to share properties (e.g. style) across elements without repeating them

Asked directly ("do we need element groups or property templates — e.g. 3 elements should all have the same color"). Nesting already solves the *spatial* version of grouping (move several elements together, F-026's territory); there is no equivalent for *property* reuse — three elements meant to share a color today just repeat the same `style: {...}` object three times, with the usual copy-paste cost: drift risk (edit one, forget the other two) and, per D-017's own stated goal, real token cost for an AI generating the plan.

**The obvious workaround doesn't actually work — checked directly, not assumed.** Since expressions can already reference a sibling's data (`parent.size.x`, D-008), the natural first guess is `style: { fill: a.style.fill }`. It parses with zero error — and renders completely broken: the SVG's `fill` attribute ends up holding the literal string `"(ctx) => evalAst(ast, ctx)"`, the expression's own unevaluated JS source. `position`/`size` work because `computePositions` explicitly knows to invoke an expression value; `style` is read raw by the renderer (`style.fill ?? "none"`) with no evaluation step at all, since nothing anticipated an expression landing there. Not "unsupported" — silently wrong, with no warning anywhere, the same failure shape F-023 already named.

**A direction sketched, not designed:** a named preset registry in the preamble, parallel to `settings`, referenced by a plain string rather than routed through the general (and, per the above, untested-for-this-case) expression system:

```
settings {
  styles: {
    wall: { stroke: "#444", strokeWidth: 0.1 }
  }
}
element wall_a { shape: "polyline", points: [...], style: "wall" }
```

Deliberately a small, dedicated resolution step rather than reusing expressions, specifically to avoid inheriting the bug found above. `style` accepting either an inline object (as now) or a string naming a preset mirrors an override shape this language already uses elsewhere (`placement` vs. `childPlacement`, `edgeLengths` per-element vs. plan-wide). Not designed: whether presets extend past `style` to other repeated properties, how a preset interacts with an element that sets *some* style properties inline and wants the rest from a preset, or the exact syntax.

**Built — [decisions.md D-082](decisions.md#d-082-f-027-named-style-presets-settings--styles---), resolved exactly as sketched above.** `settings { styles: { name: {...} } }`, referenced via `style: "name"`; no partial merge (an element's `style` is fully inline or fully a preset, never both — matching this language's other full-override pairs). No grammar change needed — `settings {}` was already a generic, arbitrarily-nested object literal. A real bug found and fixed while building it: an unresolvable preset name originally made the whole element fall through to the bare-corner-point rendering branch, silently losing its shape entirely, not just its color — fixed so a declared-but-unresolvable style still renders as whatever shape was declared, just without color, matching how a shape with a merely-incomplete inline style already degrades. Presets extending past `style` to other properties (F-027's own open scope question) remain unaddressed — this covers exactly the case that was asked for.

## F-028 Duplicate element ids silently corrupt the *wrong* element, not just the one reusing the id

Found by testing directly, not by reading the parser. Nothing validates id uniqueness at parse time — two elements can declare the same `id`, both render without error, and both end up with the same `data-id` in the DOM. The real damage: `nodesById[id] = node` in the parser means the *second* declaration silently overwrites the first in the lookup table, so a drag targeting either DOM element resolves through `nodesById` to whichever one was declared *last* — confirmed live: with two same-id elements (a rect declared first, a circle declared second), dragging the **rect on screen** left the rect frozen in place and silently moved the **circle's** position in the source instead, no error, no warning anywhere. This isn't a rendering clash, it's a real data-corruption risk — reusing a generic id (`corner_1`, `wall_a`) across different rooms in a large, AI-generated plan is an easy, realistic mistake, and the failure mode is "your edit silently lands on a different element than the one you dragged," about as bad as a silent bug gets in a tool whose whole premise is trusting the code pane to reflect what you did.

**Built — folded into F-022's load-time validation pass rather than a separate mechanism, [decisions.md D-075](decisions.md#d-075-f-022--f-028-a-load-time-validation-pass-with-duplicate-id-detection-folded-into-the-same-sweep).** Chosen over a hard parse error: still just a reported violation (the plan still loads and renders), not a rejection, matching this language's existing pattern (D-015-style "surface the problem where the author is already looking" rather than blocking). Reports once per duplicated id regardless of how many times it repeats, not once per extra occurrence.

## F-029 No multi-select for bulk actions

Every interaction this language's interactivity module supports — drag, Duplicate (D-074), Delete, connect/disconnect — operates on exactly one element at a time. There's no shift-click, no marquee/rubber-band selection, no "delete these four together" or "duplicate this cluster of unrelated siblings as one action." Nesting already covers the case where the group shares a parent (move the parent, everything inside follows for free); this is specifically the gap for elements that are conceptually a group but don't already share one — a room's whole set of furniture, say, if it were never nested under a sub-container to begin with. A real, missing convenience rather than a correctness risk (F-028's territory) — not designed at all yet, not even a rough shape.

## F-030 A reusable component/sub-plan concept — to be realized later

Raised directly, deliberately left less developed than F-027 through F-029 rather than sketched prematurely — worth recording as a real, live question, not worth designing yet. D-046's `compose` lets a *module* generate a structure from parameters (code defining a shape, e.g. `wallWithDoor`), but there's no way to reuse a whole hand-authored *subtree* as data — "here's a bathroom layout, drop it into three different van plans" — the way F-027 proposes for a single property set, but at the granularity of a whole composition instead of one style object. Related to F-027 (both are "define once, reuse without repeating") and to D-046/D-072's compose mechanism (both are "a compact reference expands into a full structure"), but distinct from each: broader than a style preset, more author-driven than a module's generated composition. Needs real thought before a shape is proposed — what identifies a reusable component, whether it lives inside one plan or is meant to be shared across separate plans/files, how drag-editing a placed instance would relate to editing the definition — none of that is even roughly answered yet.

## F-031 A setting for discrete (grid-snapped) drag positions, paired with F-014's visual grid — to be realized later

Requested directly, deliberately deferred rather than designed now. Two related pieces:

- **A setting that constrains where a drag can land** — e.g. "snap to 1m steps" — so a dragged element's position always lands on a discrete grid rather than wherever the pointer happens to be, the way most CAD/floor-plan tools default to. This is new: F-014 (the existing background-grid entry) is explicitly *pure display, no interactivity dependency* — this is the opposite half, a behavior change to the drag math itself, not a rendering concern.
- **Showing that grid visually** — this is F-014 itself, but the two are more useful paired than either alone: a visible grid whose own square size matches whatever snap increment is actually in effect, rather than a purely decorative reference grid unrelated to how dragging behaves.

Not designed at all yet: whether the snap step is plan-wide (`settings`) or per-element (same override shape as `edgeLengths`/`allowCollisions`), whether it constrains every drag-editable property or just position, how it interacts with the placement/flush/compose mechanisms that already compute a drag's landing point their own way (F-026's territory — a fifth thing that might need to go through whatever snapping logic this becomes), and whether "discrete" should mean hard-snapped (never lands off-grid) or soft (snaps unless a modifier key is held, the common CAD convention).

## F-032 App toolbar/menu redesigned like a familiar office-app menu (icons, not just text buttons)

Requested directly, deliberately recorded as an open question only — not designed or built this round. Today's overflow menu (`toolbar-more`, D-068) is a flat list of plain text buttons — Rename…, Delete, Import…, Export…, Sign in…/Save to Cloud/Sign out — stacked with no icons, no grouping, no visual hierarchy beyond declaration order. The ask: restructure this closer to how a familiar office application (Word, etc.) presents its own actions — icon-led, grouped by what the action affects, discoverable without reading every label first.

Not designed at all yet: which icon set (a small inline SVG sprite, matching this project's zero-dependency policy — D-034 — rather than an icon font or external library), whether this becomes an always-visible ribbon-style bar or keeps today's collapsed-behind-"⋯" shape just with icons added to each row, how actions should group (file-level: Rename/Delete/Import/Export; account-level: Sign in/Save to Cloud/Sign out; edit-level: Undo/Redo, already living outside this menu entirely today), and how it interacts with the mobile-narrow layout this exact menu was collapsed *for* in the first place (D-067/D-068) — an icon-forward redesign could ease that space constraint or worsen it depending on execution, genuinely unclear without a concrete mockup to react to.

## F-033 Export the current plan as a flattened image (PNG/SVG)

Requested directly, recorded only — not designed or built. The existing `Export…` button (D-030-era) exports the plan-language *source text*, not a picture of it; this is the opposite thing, a flattened raster (PNG) or the SVG markup itself, downloaded client-side with no backend involved at all — everything needed to produce it (the live `<svg>` core already renders on screen) already exists in the browser at the moment someone would click it, independent of any account/sharing question (F-034).

## F-034 Sharing a plan with someone else — as a static view vs. as the editable plan+code

Requested directly, distinguishing two different things by name: sharing just *the plan* (someone else sees the rendered drawing) versus sharing *the plan and its code together* (someone else gets the actual editable source, able to open and modify it themselves). Recorded only — not designed or built. [F-005](#f-005-public-plan-viewing) already covers the narrower "public, non-owner viewing" case and the reasoning for why a static flattened snapshot rather than raw plan-language source would protect an owner's content if that's ever built (D-022) — this generalizes the same question to *sharing with a specific person*, not just "public," and makes the two-mode distinction explicit rather than assumed: a view-only share (closer to F-005's own static-snapshot proposal, plausibly built on top of F-033's export mechanism rather than a separate one) is a fundamentally smaller exposure than a plan+code share, which hands over the full, editable source — everything D-022's scraping-protection reasoning was originally trying to avoid giving away for free.

Not designed: the mechanism for either mode (a durable share *link* implies the backend/storage service this app already has, D-047–D-050; plan+code sharing could be nothing more than exporting and sending the source text directly, no new infrastructure at all), whether a shared plan is a live pointer to the owner's own copy (their later edits show up for the viewer) or a frozen snapshot taken at share time, and how either mode interacts with F-009's external-module trust question — a plan+code share is exactly D-023's own "a person pastes AI-generated plan text and trusts it enough to run" workflow, just between two people instead of a person and an AI.

## F-035 Right-click on a child/parent should be able to set the placement relationship directly (inside/outside/…)

Requested directly, recorded only — not designed or built. Today the only way to attach an element to its parent as `placement: "inside"` (D-032/D-044), `"outside"` (D-032's connected-point mode), or `flush: true` on top of either is hand-editing those properties into the source — the right-click context menu (D-030/D-074) only ever offers Duplicate and Delete Element, nothing about an element's relationship to its parent at all. A menu action that writes the relevant property directly (the same source-splice mechanism drag edits already use) would make this a discoverable, no-typing choice instead of something an author has to already know the exact property names for.

Related to F-015 (settings editable from the viewer generally) but narrower and more concrete: this is specifically about the placement/containment relationship between a child and its parent, surfaced right where an author is already looking (a right-click on the element itself), not a general settings panel. Not designed: the exact menu shape (a submenu listing "Inside" / "Outside" / "Free", a toggle per option, something else), what happens to an element's existing position when a relationship is applied via the menu rather than by dragging into place (D-032's mechanics all assume a drag is already in progress, not a value set out of the blue), whether `flush` is a separate toggle or bundled with "Inside", and how — or whether — this interacts with F-020's ancestor-search (setting "inside" via the menu presumably means "inside my immediate parent," matching what an explicit `placement` already means today, not an inherited ancestor's `childPlacement`).

## F-036 Two mobile/touch gaps: pinch-to-zoom, and a touch equivalent for the right-click menu

Requested directly, recorded only — not designed or built. Confirmed by reading the actual event wiring, not assumed: `handleWheel` (the only zoom mechanism that exists) is bound to the `wheel` event alone, which a touch device never fires — there is no multi-touch pinch handler anywhere. Worse than simply "no app-provided zoom on touch": `svg .obj`/`.anchor-hit` both set `touch-action: none` (D-067-era, added specifically so a single-finger drag doesn't fight the browser's own native pan/zoom gestures over a shape), which also suppresses the *browser's own* native pinch-zoom the moment a touch lands on a shape rather than empty canvas — meaning zoom on mobile isn't just unbuilt, it's actively unavailable over most of a plan's own visible area, not merely absent.

The right-click context menu (Duplicate/Delete, D-030/D-074, and F-035's proposed placement actions above) has the same shape of gap: it's wired to the `contextmenu` event, which a touch device can raise via a long-press in some mobile browsers, inconsistently and not verified working here — the mobile pass (D-067/D-068) covered layout (tabs, hamburger menu, toolbar) but never specifically tested or built a deliberate touch trigger for this menu.

Not designed: whether zoom becomes a standard two-finger pinch gesture (tracking two simultaneous pointers' distance, the natural touch equivalent of `handleWheel`'s scroll delta) or something else, whether `touch-action: none` needs to be scoped more narrowly (e.g. only suppressing pan, not pinch) once a real pinch handler exists to replace what it currently blocks, and what a touch-friendly trigger for the context menu would be (a long-press with its own explicit timer rather than relying on the browser's native `contextmenu` synthesis, a persistent small "⋯" affordance on the selected element, or something else) — genuinely unexplored, flagged directly rather than guessed at.

## F-037 Validation violations (F-022/F-023/F-028) should surface directly in the code pane, not only in a separate panel

Requested directly, recorded only — not designed or built. Today every static-validation finding (D-075's collisions/containment/duplicate-ids, D-084's unrecognized shapes/properties/flush-placement) only ever appears in `#interactivity-validation-panel`, a plain list below/beside the code — an author has to read a message naming an element by id, then go find that element in the code pane themselves. The ask: mark the actual offending span directly in the code (an inline indicator, e.g. an underline, the way a real editor's diagnostics work), with the full message available on hover rather than permanently taking up space inline.

**A real prerequisite gap, found while grounding this entry, not assumed:** violations today carry only `{ type, message }` (`docs/interactivity-module.js`, D-075/D-084) — no source position at all. Worse, most of what a violation would need to underline isn't even tracked by the parser in the first place: `parseValue()`'s `STRING` branch (`docs/index.html:502`) returns a bare JS string with no span — meaning `shape: "hexagon"` or `placement: "diagonal"`, exactly the values D-084's own checks flag, have no recorded position anywhere in the parsed tree to point back to, only the *whole element's* own `start`/`end` (`parseElementDecl`, line 481). Only numeric/expression values keep `{ value, unit, start, end }` (`parseExprValue`, line 530-545). Building this would need the parser to start capturing per-property (at least per-value, ideally per-key too) spans generally, not just a targeted fix for one property.

Not designed: whether that parser change captures every property's span unconditionally (simplest, but touches `parseElementDecl`/`parseValue` broadly) or only for values a check might plausibly flag; how a violation, once it has a span, actually renders inline — `code-highlight-module.js` (D-042) already wraps tokens in styled `<span>`s for syntax coloring, a plausible attachment point for a squiggle/tooltip, but nothing here has confirmed that directly; and how an inline marker and the existing panel relate going forward (the panel replaced entirely, kept as a secondary "see everything at once" view, or something else).

## F-038 Style-preset resolution (F-027) is core-only — making it a module is unexplored

Requested directly, recorded only — not designed or built. `resolveStyle`/`settings.styles` (D-082) lives directly inside `docs/index.html`'s own `renderShape`, resolved synchronously while each shape's SVG string is first built — unlike every module this project has actually shipped (`annotations-module.js`, D-039; `grid-module.js`, D-085), which instead runs via `core.onRendered`, a **post**-render hook that reads back an already-fully-built live SVG and layers more markup onto it. Style-preset resolution doesn't fit that existing hook shape today: by the time `onRendered` fires, each shape's `fill`/`stroke` attributes are already burned into the SVG string core generated, not still-pending for a module to fill in.

Not designed: whether this would mean core deferring style resolution — rendering a shape with some marker/placeholder in place of `fill`/`stroke` for anything using a named preset, then a style module's `onRendered` callback finds and rewrites those attributes after the fact (mirroring `window.PlanModules[shape]`'s existing pattern for module-provided *shapes*, but for style resolution instead) — or whether it would need a genuinely new kind of hook (a during-render/pre-serialize transform, not `onRendered`'s after-the-fact one) that nothing in this codebase offers yet. Whether the value is purely architectural (consistency with how every other display-only feature is now structured) or there's a concrete capability this would unlock isn't established either.

## F-039 The grid (F-014) should be able to sit in front of the plan, not just behind it — semi-transparent when it does

Requested directly, recorded only — not designed or built. `grid-module.js` (D-085) always inserts its `<pattern>`/`<rect>` pair via `insertAdjacentHTML("afterbegin")` — literally the SVG's first children, so it paints behind every real shape unconditionally; there is no path today for the grid to render in front of the plan's own content instead. The ask: a plan should be able to choose to have the grid sit *in front*, at reduced opacity, rather than only ever behind — plausibly useful as an alignment/measuring overlay while a plan is dense enough that a background grid gets fully hidden under it anyway.

Not designed: the exact settings shape (a `layer: "front" | "back"` sibling to the existing `size`/`type` keys in `settings.grid`, most consistent with how `type` was added right after the first version shipped — or something else), what opacity a front-layer grid should default to (semi-transparent was specified directly, but not a number), whether "front" means literally the SVG's very last children (`insertAdjacentHTML("beforeend")`, the mirror-image of today's `afterbegin`) or needs to stay behind the connect/disconnect icons and other interactivity-module overlay elements that also land at the end of the SVG, and whether a front-layer grid needs `pointer-events: none` reconfirmed for correctness (today's implementation already sets it, but a front grid sitting visually above shapes makes an accidental pointer-event regression far more noticeable than a background one would be).

## F-040 The code/viewer pane split should be resizable, not a fixed width

Requested directly, recorded only — not designed or built. Confirmed directly, not assumed: `docs/index.html`'s own CSS hard-codes the split — `textarea { flex: 0 0 420px; ...; resize: none; }` — a fixed 420px code pane with the browser's own native textarea resize handle explicitly disabled, and `.viewer-pane { flex: 1 1 auto; ... }` simply taking up whatever's left. There is no draggable divider between the two panes anywhere in this codebase.

Not designed: the mechanism (a thin draggable handle between `textarea` and `.viewer-pane`, tracking pointer events the way `interactivity-module.js`'s own canvas-pan dragging already does, versus reviving the browser's native `resize` on the textarea and giving `.viewer-pane` a matching `min-width` instead), whether the chosen width should persist (`localStorage`, matching how a plan's own source already persists there) or reset every session, and how this interacts with the existing mobile layout (D-067/D-068's tabs/hamburger-menu breakpoint, where the two panes aren't shown side-by-side at all — a resizable split is presumably a desktop-only concept).

## F-041 Alternatives to the drop-shadow "glow" used for selection and hover

Confirmed by reading the actual CSS, not assumed: selection (`svg .obj.selected { filter: drop-shadow(0 0 2px rgba(124,58,237,0.55)); }`) and plain hover (`svg .obj:hover { filter: drop-shadow(0 0 2px rgba(51,119,255,0.55)); }`, `docs/interactivity-module.js`) both use the identical technique — a colored `drop-shadow` filter, differing only by hue — established back at D-030 and reused since (connection-highlight and corner-preview, elsewhere in the same file, both do the same thing in orange/red). ## F-042 Style modules and settings should be toggleable directly from the menu — which means the menu has to read the plan's own code first

Requested directly, recorded only — not designed or built. Overlaps two existing open questions without being either of them: F-015 already names "settings editable from the viewer" in the abstract; F-032 already names "the toolbar/menu redesigned with icons." This entry is more specific than either — it's about a menu that shows which modules/settings are *actually currently active in this exact plan* and lets someone flip them on/off right there, which means the menu can no longer be the static, plan-independent action list it is today (Rename…/Delete/Import…/Export…/Sign in…, D-068) — it would need to inspect the live parsed `program` (`program.modules`, `program.settings`) on every render and redraw itself to match, then write any change back into the source via the same splice mechanism drag edits already use.

**A real complication, found while grounding this, not assumed away: "module" doesn't mean one consistent thing to toggle.** `AUTO_MODULES` (`annotations-module.js`, `interactivity-module.js`, `code-highlight-module.js`, `grid-module.js`) are unconditionally re-injected on every render regardless of what a plan's own `module "..."` lines say (`withAutoModules`/`rerender`'s `requiredModules = [...new Set([...AUTO_MODULES, ...parsed.modules])]`, `docs/index.html`) — so there is no real "off" state for any of them at the module-declaration level today. For something like the grid or style presets, what a menu toggle would actually be flipping isn't the module's own load state at all, but whether `settings.grid`/`settings.styles` exists or is populated — a materially different mechanism (editing `settings { }`) than toggling an actually-optional, non-auto module (the kind F-009's external-module trust question already covers), even though both would show up in the same conceptual "menu of modules" a user sees.

Not designed: how the menu would visually represent "currently active" state per item (a checkmark, a toggle switch, something else), what happens to an element's existing property values if a style preset or setting gets turned off and back on (does turning `settings.grid` back on remember its previous `size`, or reset to a default), how this interacts with F-038 (if style-preset resolution ever does become a real loadable module rather than core-only code, toggling it would then also mean the module-declaration-level "off" this entry's own AUTO_MODULES finding says doesn't currently exist for anything shipped), and whether a non-auto, externally-loaded module (F-009's trust-prompt territory) belongs in the same menu at all given it already has its own separate accept/decline flow.
