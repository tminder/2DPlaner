# Decisions

## D-001 Domain

The tool targets general spatial/interior layout plans, not just building floor plans — includes floor plans, interior layouts, outdoor plans, and campervan/vehicle interior designs. The plan language and renderer should not bake in assumptions specific to one of these (e.g. "rooms" as a required concept) — see D-013 Core primitives below.

**First domain outside a room's interior, actually built:** every prototype through 14 modeled interior furniture layout (a studio apartment). [Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/) is the first to model something else — a property boundary, a house, and a utility connection line — using exactly the same primitives (polygon, rect, polyline, Connection) with zero core changes, only new content. A real, if narrow, confirmation that the "no room-specific assumptions" goal is holding, not just stated.

## D-002 Planning approach

We plan the full concept/vision before committing to build stages or an MVP. Exploratory prototypes (see [Prototypes/](../Prototypes/)) are fine to build along the way to test ideas, but they're throwaway experiments, not a staged rollout plan — the formal implementation sequencing (what gets built first, in what order) is deferred until the full concept is worked out. See [open-questions.md](open-questions.md).

## D-003 Primary user

**Revised.** The primary author of plan code is an AI (e.g. Claude), generating and editing it on the human's behalf; the human reviews the result and makes small manual tweaks directly in the code and/or via drag-and-drop. This supersedes the original framing below, which assumed a human developer as the primary hands-on-keyboard author — see D-017 for how this reshapes the syntax design goals.

## D-004 Rendering technology

SVG, chosen by Claude (user deferred). Rationale: the core aims call for drag-and-drop editing and module-based interactivity later — SVG elements are DOM nodes, so they get free hit-testing, CSS styling, and native event handling (click/drag) for that future work. Canvas would need hit-testing and a scene graph built by hand to support the same interactions. Revisit only if element count becomes a real performance problem.

Validated: [Prototypes/01-node-connection-render/](../Prototypes/01-node-connection-render/) renders a Node/Connection plan to SVG successfully.

## D-005 Units

Plan code specifies real-world measurements (e.g. meters/cm); the renderer scales these to fit the screen. Needed since plans are meant to be usable for actual spatial layout (floor plans, campervan interiors, etc.), not just abstract diagrams.

## D-006 Code editing

**Revised** to resolve a contradiction with D-003 (the original wording assumed a human primary author, written before D-003 was revised to make the AI the primary author).

Code and rendered preview are shown **simultaneously and equally live**, side by side — an in-browser code editor (e.g. Monaco/CodeMirror) on the left at roughly 1/3 width, the rendered plan on the right at roughly 2/3 width. Neither pane is secondary or hidden-by-default: the human can intervene directly in either the code or (later, per core aim #1/D-009) the rendered view, and both stay in sync regardless of who made the last edit. The wider preview pane reflects that the visual result is what's being judged moment-to-moment, without demoting the code to a hidden diff/review-only surface.

**Correction (D-023):** "the AI's edits appear in the code pane as it writes" described a live-integration scenario that isn't how this actually works right now — see D-023. Currently the human pastes AI-generated code into the editor pane (from a separate AI conversation) rather than watching it stream in; the rest of this decision (both panes live, either editable, always in sync) still holds regardless of how the code got there.

## D-007 Persistence

Plans can be saved/loaded via browser local storage and/or downloaded and loaded as files, so work isn't lost between sessions. Extended by D-021 for logged-in users: server-side cloud sync via a separate storage service.

## D-008 Plan language style

Declarative core with expressions: the plan is fundamentally a tree/data structure describing what exists (matches [core-aims.md](core-aims.md) aim #1 and #2), but individual values can be small expressions/formulas (e.g. `width: 3 * bay_width`) rather than plain literals. Not a full scripting language with loops/functions — kept close to a directly-editable data model so it stays compatible with drag-and-drop sync (see D-009 Drag-and-drop scope below).

## D-009 Drag-and-drop scope

Every visual element in the plan must be representable and editable via drag-and-drop, not just a subset — there is no code-only visual element. This is a hard constraint on the language design: whatever the language looks like, its structure has to map cleanly to/from direct manipulation of the rendered view.

Validated (partially): [Prototypes/03-drag-sync/](../Prototypes/03-drag-sync/) drags rewrite the plan-language source text directly (via source-span splicing, not a full re-serialization), closing the loop in both directions. Covers plain literal positions/points and one level of D-012 solve-backward; doesn't yet cover per-endpoint connection constraint-solving (see F-001).

Correction: the initial version of this prototype (and 04) called `setPointerCapture` on the dragged SVG element, which every subsequent `pointermove` then destroyed via a full `innerHTML` re-render — silently breaking drag after the first tiny movement in most browsers. Fixed by dropping capture and listening on `window` instead of the element, since nothing in the drag logic actually needed capture semantics.

**Known risk, now measured:** 03/04/05 all re-parse the entire plan text and replace the entire rendered SVG on every `pointermove`, not just at drag-end. [Prototypes/11-performance-test/](../Prototypes/11-performance-test/) benchmarked this directly: fine through 800 objects, over the 60fps frame budget at 2000 — both in the measured numbers and in how the drag actually felt. See [open-questions.md](open-questions.md#f-007-drag-performance-at-scale) for the fix this points to (incremental DOM updates) once it's actually needed.

Correction: since 03 introduced editable-literal objects (`{value,unit,start,end}`) for bare numeric literals, `style.strokeWidth` became one of these objects rather than a plain number — but the renderer in 03, 04, and 05 multiplied it by the meters-to-pixels scale directly (`style.strokeWidth*M`) without unwrapping via the existing `numOf()` helper, producing `NaN` (browsers silently fall back to a default stroke-width rather than erroring, so this rendered wrong without any visible error). Fixed in all three by wrapping with `numOf()`.

## D-010 Expression scope

Expressions (see D-008 Plan language style above) can only reference values within their own local scope (e.g. siblings within the same area), not arbitrary elements anywhere in the plan. Keeps dependencies simple to reason about and keeps drag-and-drop sync tractable.

## D-011 Module capabilities

Modules (core aim #3) can add new rendering and new interactivity. "New primitives" from a module means new *reusable, higher-level compositions* built from the two core primitives (Node, Connection — see D-013 Core primitives below), not new fundamental geometric kinds — the core primitive set itself is meant to stay fixed and minimal. The module API needs to expose enough of the core (renderer, interaction system, and a way to register/compose Nodes and Connections) for a module to build such compositions; see [open-questions.md](open-questions.md#f-002-module-api-surface).

## D-012 Drag edits on expressions

When the user drags/resizes an element whose value is an expression (e.g. `width: 3 * bay_width`), the system tries to solve backward — adjusting the referenced variable(s) so the expression still holds — rather than overwriting it with a literal. This preserves the author's intent/formula. Not always solvable (e.g. underdetermined or non-invertible expressions); see D-015 Unsolvable drag fallback below for what happens then.

Validated (narrow case): [Prototypes/03-drag-sync/](../Prototypes/03-drag-sync/) linearizes a `parent.<prop>.<x|y>` expression through `+ - * /` and rewrites the *parent's* literal so the expression still holds when dragged. Only one path reference per expression, one level of nesting — real solve-backward for arbitrary expressions is out of scope for this throwaway.

**A real composition of this turned out to be a bad idea, not just an untested one:** [Prototypes/13-unified/](../Prototypes/13-unified/) originally gave a desk's position as `parent.size.x - 1.2m - 0.2m`, specifically to demonstrate solve-backward. In practice, dragging the desk silently resized the entire room — reported back (correctly) as nonsensical: moving a piece of furniture shouldn't move a wall. Solve-backward through a parent's *position* (D-012's original, still-valid case: a wall segment shifting) and solve-backward through a parent's *size* (this case) are not equally reasonable — resizing a container is a much larger, more structural change than repositioning it, and doing that silently as a side effect of dragging something small inside it is surprising in a way the original decision didn't anticipate. Fixed pragmatically for now by not authoring that composition (the desk's position went back to a plain literal) rather than by changing the engine — the underlying mechanism is untouched and still does what D-012 describes. Whether solve-backward should be restricted from ever targeting a `size` property (as opposed to `position`) is now a real open question, not resolved here — the engine still allows it.

**Bug found and fixed while building [Prototypes/13-unified/](../Prototypes/13-unified/):** the parser's "is this a plain editable literal" check only ever matched a bare number token (`5m`), never a unary-negated one (`-5m`) — a negated literal parsed as a `neg` node wrapping a `num` node, which fell through to plain evaluation and lost its editable `{value,unit,start,end}` span. Harmless-looking until a drag actually produced a negative coordinate: the literal round-tripped through source text fine (`formatNumber` writes `-0.5m` either way), but on the *next* parse it silently stopped being draggable, since it was now a plain JS number with nowhere to write an edit back to. 09/10's examples never dragged anything past zero, so this sat latent. Fixed by also recognizing `neg(num)` as an editable literal, with the span extended to include the minus sign.

## D-013 Core primitives

The plan language has exactly two core primitives, deliberately minimal and domain-agnostic (see [Prototypes/language-sketch-01.md](../Prototypes/language-sketch-01.md) for the reasoning):

- **Node** — a generic element with coordinates/position, optional shape and style properties (shape kind, size, color/stroke, etc., all set directly as plain properties), an optional user-defined label/name, and optional children (a node with children acts as a container/area; a node without is a leaf/object). There is no separate "area" vs. "object" primitive, and no built-in "type" catalog (e.g. no built-in "bed" or "tree" type) — appearance and meaning come entirely from the properties and structure the user writes, or from reusable compositions a module provides on top.
- **Connection** — an attachment/relationship link between two nodes (e.g. a door attached to a wall segment, a chair attached to a table). It's semantic/relational, not merely a drawn line, though it may be rendered as one and may constrain the connected nodes' positions.

There is deliberately no built-in "boundary/wall/door/window" concept in the core language — those are expected to emerge from user-composed hierarchy (nesting) and connections, or from a reusable composition a module provides, rather than being reserved keywords.

## D-014 Connection semantics

- **Drag propagation:** dragging a node rigidly drags every node it's connected to, so connected nodes stay joined — the same "preserve the relationship" spirit as D-012 Drag edits on expressions above, just applied to connections instead of expressions.
- **Multiplicity:** a node can participate in any number of connections at once (e.g. a door connected to the wall segment on each side). This means dragging can produce conflicting/over-constrained demands on a single node — see D-015 Unsolvable drag fallback below for what happens then. **Caveat:** unlimited connections + rigid propagation is, in general, the same problem a CAD geometric-constraint solver solves — worth being deliberate about scope so this doesn't turn into building a full constraint solver by accident; see [open-questions.md](open-questions.md#f-001-constraint-solving-scope) for how far to take it.
- **Direction:** a connection can be either symmetric ("these two are joined", no dependency direction) or directional (one node is anchored to / depends on the other) — this is a property of the individual connection, not a global rule.

**Status: unproven for its actual remaining purpose.** D-014's own motivating example was a door connected to the wall segment on each side — but D-018 later solved exactly that case better, via shared corner-node references instead of Connections. Every prototype that touched Connections either used them for this now-superseded case (03) or dropped them entirely in favor of shared corners (04, 05). What Connections are actually left to model — loose attachments, e.g. a door that stays *somewhere along* a wall without a pinned point — has never been prototyped. There's real reason to doubt the mechanic above is even right for that case: "stays along a wall" sounds like constrained sliding, not rigid translate-together. Treat this decision as a placeholder pending a dedicated prototype for the loose-attachment case, not as validated design.

**Given a concrete design, now partially built and dragged:** [D-032](#d-032-parent-child-placement-modes) proposes exactly the constrained-sliding mechanic this status note called for — a `placement` mode on a connection between a child and its own parent, with an edge-attached child sliding along the parent's boundary when dragged rather than translating rigidly. The sliding drag mechanic itself is now real (see D-032's validation note), built directly into a prototype rather than waiting for the full `placement`-property syntax — this decision's "unproven purpose" concern is narrower than it was, though the syntax/declaration side of D-032 (and its "inside" mode) remain undone.

**First concretization:** [Prototypes/06-kitchen-connection/](../Prototypes/06-kitchen-connection/) tests the rigid-propagation mechanic on two solid, adjacent rectangles (`herd`/`ablage`, a stove and counter) connected via `connection herd ablage` — the first time this decision has been exercised on solid objects rather than line endpoints. Deliberately minimal (no expressions, no points-as-references) to isolate the question. Normal drag moves both rigidly together; Shift+drag moves one alone so the two visibly drift apart, making the tradeoff tangible. Whether "always rigid together" is actually the right feel for this kind of case is left to be judged by using it, not asserted here.

**Correction (methodological, not specific to Connections):** this prototype initially appeared completely broken — dragging did nothing visible — even though the underlying data was updating correctly (confirmed via step-by-step diagnostic logging added to the page). Cause: the viewBox was recomputed from the content's bounding box on *every* render, so when a drag moves everything in the scene together (as rigid connection propagation does by design), the auto-fit "camera" re-centers by the exact same amount and cancels the visible motion — the data changes, nothing appears to. Fixed by computing the viewBox once, from the first render, and reusing it rather than re-fitting every frame. [Prototypes/05-polygon-corners/](../Prototypes/05-polygon-corners/) uses the same auto-fit-every-render pattern; it doesn't fully cancel out there (only one of four corners moves at a time) but shares the same underlying flaw and would benefit from the same fix. General lesson: an auto-fit viewBox is the wrong choice for any prototype meant to demonstrate *whether* something moved.

**That fix was applied too broadly in [Prototypes/13-unified/](../Prototypes/13-unified/), found from feedback:** "compute once, reuse forever" froze the viewBox for the entire page lifetime, not just for the duration of a drag — so an element added by directly editing the source text (e.g. pasting a duplicated node block) at a position outside the original bounding box rendered into the SVG correctly but sat outside the frozen viewBox, invisibly. The freeze is only actually needed to survive a drag's own repeated re-renders (`pointermove` → `applyDrag` → `run()`); a plain textarea edit isn't part of a drag and was never at risk of being visually cancelled by a re-fit. Fixed by resetting the cached viewBox specifically on the textarea's `input` event (so a real edit gets a fresh fit) while leaving `applyDrag` untouched (it sets `sourceEl.value` programmatically, which never fires `input`, so a drag in progress is unaffected).

**How a connection actually gets created — two approaches tried, one kept for now:** [Prototypes/07-connection-drag-create/](../Prototypes/07-connection-drag-create/) tried an explicit Ctrl+drag-from-node-to-node gesture, connecting any two nodes regardless of distance, plus node-wise (anchor-point) connections as children of an object rather than the object itself — it also surfaced that an anchor dragged alone detaches visually from its parent, since a plain drag only edits the dragged node's own position, not its parent's. Both real findings, but the *scope* was wider than wanted. [Prototypes/08-proximity-connect/](../Prototypes/08-proximity-connect/) narrows this deliberately: no explicit gesture, no node-wise anchors, no connecting non-adjacent objects at all — a connection can only be *offered* between whole objects that are actually touching (axis-aligned bounding-box test with a small tolerance). This is the current preferred direction; 07's broader gesture and anchor-level granularity remain there as explored-but-not-adopted alternatives, not deleted.

**Refined further: creation and removal are explicit, gated by selection, not automatic.** The first version of 08 auto-created a connection the instant two objects touched on drop. Revised: dragging near another object creates nothing by itself — only *selecting* an object (click, or release after a drag) reveals connect/disconnect controls for it. The connection line itself is also gated by selection — it only renders while one of its two endpoints is selected, not as a permanent fixture of the drawing, so an unselected plan doesn't show connection lines at all. A separate hover effect (highlighting both connected objects together, independent of selection) gives a lighter-weight preview of the relationship without requiring a click. This resolves the "moving apart doesn't remove the connection" limitation noted in the first version — now there's an explicit action for that, rather than it being simply unhandled.

**Refined once more: in-place icon buttons, not a separate list.** The connect/disconnect controls moved from a text button bar below the canvas into small icon buttons (a filled circle with a white +/× symbol) rendered directly in the SVG, positioned at the actual contact point between the two objects — computed from which axis has the smaller overlap (side-by-side vs. stacked adjacency), not just a fixed offset. Icons are painted after everything else so they're never buried under an object (the same "paint interactive elements last" fix already needed once before, in 04 — see D-018's correction above). A click on an icon is checked before the drag-start logic, so clicking it never gets misread as grabbing the object underneath.

**Bug found and fixed while building [Prototypes/13-unified/](../Prototypes/13-unified/):** 08's adjacency test (do two bounding boxes overlap, within a small tolerance) implicitly assumed the two objects are always siblings that merely sit next to each other — true in 08's herd/ablage example, but not in general. 13 introduces a room that is itself a rect *and* the parent of every piece of furniture inside it; a plain overlap test called every piece of furniture "adjacent" to the room, since full containment also satisfies "boxes overlap." Selecting the room offered a spurious connect-icon to nearly everything in it. Fixed by requiring genuine edge contact — one axis's gap between the two boxes must be near zero (an edge touching, not a deep overlap) while the other axis's ranges actually overlap — rather than any overlap at all.

**Extended: connecting now snaps the objects flush, not just adds the relationship.** Feedback on 13: clicking the connect icon only ever added the `connection A B` statement — if the two objects were left with a small gap or slight overlap from a manual drag (anything within the icon's own `TOUCH_TOLERANCE`), connecting them didn't change that, so "connected" and "visually flush" could disagree. Fixed by having the connect action also compute and apply a small positional correction — closing the residual gap on whichever single axis they're touching across, leaving the other axis (where they already share extent) untouched — before appending the connection statement. The disconnect action and the drag-propagation mechanic are unchanged.

**That snap fix initially had its own sign bug, caught by testing it, not by re-reading the code:** the gap-closing distance was computed correctly, but applied in a fixed direction (always "move the second object toward negative x/y") rather than toward whichever direction the first object actually was — so connecting two objects where the second happened to be the one positioned further left/up moved it *away* instead of closing the gap, visibly making things worse. Fixed by comparing which object's center is actually further along the touching axis and choosing the correction's sign from that, instead of assuming a fixed relative order.

**Related, found from the same round of feedback:** dragging one object across a polygon's corner lit up that corner with the same visual preview used for actually hovering it (see D-018's anchor-hit correction), even though the user wasn't interacting with the corner at all — just passing over it mid-drag. Root cause is the same one behind this decision's own D-009 correction: without `setPointerCapture`, the browser still fires `pointerover`/`pointerout` for whatever element is actually under the cursor, regardless of which element initiated the drag. Fixed by suppressing the JS hover-preview handlers while a drag is in progress.

**That fix was incomplete — reported again after the first attempt:** guarding the JS `pointerover` handler stopped the corner-preview and connected-highlight classes from being added mid-drag, but the plain blue "hovering an object" glow (`.obj:hover` in CSS) kept appearing for whatever the cursor passed over, since that's a native CSS `:hover` pseudo-class, entirely independent of any JS event handler — the earlier fix addressed the JS-driven effects and missed the CSS-driven one causing the same symptom. Fixed by giving `#plan-root` a `dragging` class for the duration of a drag (added in `pointerdown` alongside setting `drag`, removed unconditionally in `pointerup`) and scoping every native-`:hover` rule (object glow, anchor-hit fill, icon-button grow, label hover-reveal) behind `#plan-root:not(.dragging)`.

Validated (simple case only): [Prototypes/03-drag-sync/](../Prototypes/03-drag-sync/) propagates a drag as a uniform translation across every node reachable in the connection graph (BFS), which is the "simple chain" case F-001 asked to build first. It does not implement per-endpoint constraint solving or honor the symmetric/directional distinction — everything propagates both ways, uniformly.

**Extended: connect/disconnect now works for a bare point, not just rects.** 08's adjacency/icon system only ever computed bounding boxes for `shape: "rect"` nodes — a shapeless position-only node (D-016's corner/anchor pattern) could never appear in it at all, connected or not, since it had no box to test adjacency or place an icon with. [Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/) needed exactly this: a point (`haus_anschluss`) connected to a rect (`haus`), detachable and reattachable through the UI. Fixed by treating any shapeless position-only node as a degenerate zero-size box, with dedicated math for the point-vs-rect case — a point has no extent to slide flush the way two rects do, only one coordinate to correct against whichever edge it's already aligned with (rect-vs-rect behavior is untouched, same code path as before). Reconnecting also now always moves the point side, regardless of which of the two was selected first — the old logic always moved whichever node wasn't currently selected, which for a point-vs-rect pair could mean snapping an entire house onto a small attachment point.

**Immediate follow-up bug, found by using it, not by re-reading the fix above:** placing the icon exactly at the point's own coordinates — geometrically correct, that genuinely is the contact point — meant every click meant to grab and drag the point instead hit the icon sitting on top of it, re-firing connect/disconnect and never starting a drag. Invisible on a rect (plenty of clickable area elsewhere), total on a point with no other clickable area to reach. Fixed by rendering the icon offset ~0.35m away from the point along whichever edge it's nearest, outward from the rect — clearing both the icon's and the point's own hit radius while staying visibly at the attachment site. The underlying connect/disconnect/snap logic is unaffected; only where the icon is drawn changed.

## D-015 Unsolvable drag fallback

When a drag can't be solved backward — an unsolvable expression, or conflicting/over-constrained connections — the drag still completes visually, but the UI warns and flags the affected expression(s)/connection(s) so the user can decide how to resolve it (edit the code, accept a literal override, etc.) rather than the system silently picking a resolution or rejecting the drag outright.

**Deliberately different from F-004's rejected-edit behavior (not an oversight):** an unrealistic polygon (D-020/F-004) gets its drag rejected outright, not warned-and-allowed like this decision. The distinction is what the system actually knows at the moment of the drag. Here, there is no correct fallback value to compute — the expression genuinely has no solution, so the least-bad option is to let the edit through and flag it for a human to resolve later. For an unrealistic polygon, the system knows exactly what's wrong and a valid state is one cursor-step away (don't cross the shape) — rejecting costs nothing and avoids ever landing in a genuinely broken geometric state. Two different failure situations, two different correct responses; not meant to read as one general "how drags fail" rule.

## D-016 Default node rendering

A Node with coordinates but no shape/style properties renders as nothing in the plan output by default (fully customizable — the user opts in to a visible appearance by giving it shape/style). In the editor specifically (not the rendered plan itself), an otherwise-invisible node still shows a visible affordance on hover, so it stays discoverable and draggable even with no styling.

## D-017 Syntax design goals

Following the D-003 revision (AI is the primary author), the concrete textual syntax is optimized for AI generation, weighing two things roughly equally:

- **Low-ambiguity / easy to generate correctly** — a grammar an LLM rarely produces a non-parseable file with (minimal deeply-nested bracket/quote balancing, few ways to say the same thing).
- **Token-efficient** — compact on the wire, minimal punctuation/keyword overhead, since plan code will often sit in an LLM's context window as both input and output.

These two goals mostly pull the same direction (less punctuation tends to mean both fewer tokens and less to get wrong), so no major tension is expected in practice.

The language is its own dedicated file format/syntax (matches [core-aims.md](core-aims.md) aim #2), not a superset of an existing format like JSON — free to shape itself around the Node/Connection primitives rather than around a general-purpose format's constraints.

**Next deliverable:** a throwaway parser prototype (in [Prototypes/](../Prototypes/)) that turns actual plan-language text into a Node/Connection tree. The concrete syntax gets settled by building this, not by writing a spec first.

Validated: [Prototypes/02-text-parser/](../Prototypes/02-text-parser/) is a hand-rolled recursive-descent parser + live SVG renderer for a first concrete syntax guess — `node`/`connection` blocks, unit-suffixed numbers (`1.2m`, `160cm`), local-scope path expressions (`parent.size.x - 1.2m`), inline style objects. Not finalized syntax, but proves the concept end-to-end (text → Node/Connection tree → render) and gives something concrete to react to.

**Tested and found wanting:** the "AI can author from documentation alone" premise (D-003) was tested directly — an agent given only `documentation/language.md` produced a plan that fails to parse against every existing prototype (wrong connection syntax, an unsupported sibling property path, a guessed-but-unconfirmed nesting syntax). See [open-questions.md](open-questions.md#f-006-documentation–implementation-gap-ai-authoring-test).

## D-018 Points as node references (shared corners)

A `points` entry (used by line-shaped Nodes, e.g. for a wall segment) can be either a literal `[x, y]` pair in the node's local coordinate space, or a reference to a sibling Node's id — in which case that Node's own resolved position supplies the coordinate. This lets two lines share an exact endpoint (e.g. two wall segments meeting at a corner) by both referencing the *same* corner Node, instead of each storing its own independent copy of that coordinate.

A "corner" is not a new primitive — it's just a plain Node (D-013) with a position and, per D-016, no shape/style, so it renders as nothing but stays a first-class, individually draggable thing (same pattern as `window_center` in the prototypes). Reference resolution stays local-scope only (siblings within the same parent), consistent with D-010, even though this is a direct reference rather than an arithmetic expression.

This narrows what Connections (D-014) are for. A shared corner-node reference already keeps two lines' endpoints exactly together with no Connection needed — dragging the corner moves both lines' shared point by construction, which is a cleaner mechanism than [Prototypes/03-drag-sync/](../Prototypes/03-drag-sync/)'s current approximation (rigidly translating whole connected nodes together). Connections remain for looser attachments — e.g. a door that should stay somewhere along a wall without being pinned to one exact shared point. [open-questions.md](open-questions.md#f-001-constraint-solving-scope) narrows accordingly: real geometric conflict only arises for these looser, non-shared-point relationships, not for shared corners, which are trivially consistent (it's one Node, not two synchronized copies).

Validated: [Prototypes/04-shared-corners/](../Prototypes/04-shared-corners/) implements this end-to-end — `wall_a`/`door`/`wall_b` share `corner_1`/`corner_2` instead of duplicating coordinates, and dragging a corner moves every line that references it with no explicit propagation code (it falls out of always re-deriving the render from source). It also confirms the D-014 narrowing above in practice: a line with an endpoint pinned to a shared corner can't have that endpoint dragged as part of the line — only the corner moves it — so this prototype implements no Connections at all, only shared corners.

Confirmed generic over point count and shape kind: [Prototypes/09-more-shapes/](../Prototypes/09-more-shapes/) uses this exact same mechanism for a 5-point polygon (a pentagon garden bed) and an open 4-point line (a bent path) — neither the renderer, the F-004 self-intersection check, nor the drag logic ever assumed a fixed number of points or a closed shape; they were written generically from the start and this is the first time that was actually exercised. The one genuinely new thing this prototype adds is a `circle` shape (center position + radius) — the first shape kind with no vertex-based geometry at all, requiring one new render branch and a fix to the viewBox's bounding-box calculation (previously derived only from node *positions*, which happened to cover every polygon/line vertex since each is its own node, but missed a circle's radius entirely).

Correction: initially the corner circles were ungrabbable, because a shared corner sits exactly where its lines meet, and SVG paints later-declared elements on top — since `corner_1`/`corner_2` are declared *before* the walls that reference them, the walls' strokes painted over them and captured the click first. Fixed by rendering anchor-hit circles in a separate pass always appended last, so they're always on top regardless of declaration order.

Extended to closed shapes: [Prototypes/05-polygon-corners/](../Prototypes/05-polygon-corners/) applies the same points-as-node-reference mechanism to a closed `polygon` (not just open line segments) — a shape starts as an axis-aligned rectangle, but each of its 4 corners is its own draggable Node, so dragging one deforms it into a general (non-right-angled) quadrilateral while the other 3 stay fixed. No new primitive or mechanism needed; the existing D-018 machinery applies unchanged to a closed shape.

**Correction, raised directly: corner elements had become the reflexive default way to write *any* polygon/polyline, even where nothing is shared — worth stepping back on.** Both shipped `docs/` examples used corner elements for every point of every polyline/polygon, including `rug` (a standalone decorative shape) and `grundstueck` (a plot boundary), where **no other element references any of those points at all**. The pattern almost certainly propagated from the one prototype that genuinely needed it (04's `wall_a`/`door`/`wall_b`, sharing `corner_1`/`corner_2`) rather than being deliberately chosen each time. Examined end to end:

- **The actual cost of an unneeded corner element isn't just verbosity.** A shape built entirely from corner references needs its own drag machinery to move as a whole — D-036 exists specifically because dragging such a shape means moving every referenced corner together, which took real, bug-prone work (`wouldSelfIntersect`'s batch realism check, since checking one corner at a time misreads a rigid translation as the shape deforming). A shape written with literal points never needed any of that: the plain per-point shift in `core.nodeDragEdits` already handled it, unconditionally, before D-036 was ever written.
- **The actual benefit — drift-free sync — only exists when something is shared.** With nothing else referencing a corner, "keeping it in sync" isn't a thing that's happening; the indirection buys nothing. D-003's own premise (an AI is the primary author) narrows this further: an AI writing coordinates once isn't prone to the copy-drift a corner element guards against the way manual re-typing would be — the real risk that benefit protects against is a *human* dragging one connected shape interactively and the other not following, which is exactly D-018's original wall/door case, not a shape authored once and dragged only as a whole.

**New rule, requested directly and now the language's stated default (see [language.md](../documentation/language.md#shared-corners)): literal points unless a point is actually referenced by more than one element.** Fixed in `docs/`'s own shipped examples: `rug`'s 5 points and `grundstueck`'s 4 corners are now literal; `stromanschluss`'s first two points (`strasse_anschluss`, `kabel_knick`, referenced nowhere else) are now literal, but its third stays a corner reference to `haus_anschluss`, which is *also* the target of `connection haus_anschluss haus` and has to remain a real element for that regardless — points and mixed arrays (literal alongside a reference) already worked correctly together, no new capability needed. `wall_a`/`door`/`wall_b`/`corner_1`..`corner_4` are untouched — genuine sharing, the case this decision was built for.

**Also asked directly: why isn't this expressed through `connection` instead, given the language already has a relationship primitive?** Because `connection`'s own semantics (D-014) are whole-element rigid propagation — drag one element, the other moves by the same delta — with no notion of "just this one point of one element should track just this one point of another." Extending Connection to do that would need either indexed sub-element references (more syntax) or a real geometric constraint (*solving* point coincidence rather than representing it) — exactly the general constraint-solving this project has repeatedly and deliberately declined to build (F-001). Corner-reference sharing avoids needing a solver at all: there is only ever one point element, referenced twice, so "keep these in sync" isn't a constraint to satisfy, it's a fact of the representation. This is the same category of feature as D-008's expressions (a property value referencing another element's data, e.g. `parent.size.x`) applied specifically to `points` entries — not a third relationship primitive alongside Element and Connection (D-013).

**A related generalization considered and deliberately deferred, not built: extracting a shared "clamp the attempted drag against a predicate, sliding along whatever's blocking it" utility.** D-041's collision-avoidance and the standalone containment prototype ([Prototypes/16-parent-child-placement/](../Prototypes/16-parent-child-placement/)) independently ended up needing near-identical binary-search-based clamping logic — a real duplication signal. Not extracted now: doing so while collision-avoidance's own general (circle/polygon) case remains genuinely unvalidated would risk consolidating an unresolved bug into a shared abstraction rather than fixing it, and two occurrences don't yet justify guessing at the right general interface — a third, independent need would be a better time to generalize. Recorded here as a deliberate deferral, not an oversight, should this come up again.

## D-019 User auth / data hosting

**Sequencing note (from a critical review):** this and D-021 were decided before F-001/F-002 (the two genuinely unresolved core-product questions), which runs against D-002's own principle of settling the concept before infrastructure. The content isn't in doubt — auth/hosting has no real dependency on how constraint-solving or the module API turn out — but the *order* was off, and effort has skewed toward infrastructure over the harder open product questions. F-001/F-002 take priority from here; see [open-questions.md](open-questions.md).

The product itself stays a standalone web app — not a WordPress plugin or theme, and WordPress never renders any of the app's UI. For user accounts, a **self-hosted WordPress instance runs headless**, used purely as a credential-verification backend via its REST API: **WP core only — no third-party auth plugin at all.** Credential verification uses WP's own built-in **Application Passwords** (core since WP 5.6), not a third-party JWT plugin. WP's database is where user accounts/credentials actually live.

**Why WordPress specifically, given the app itself has no other WP dependency:** the requirement is user data hosted on the user's own server (self-hosted, not a third-party managed auth provider), and it must be secure with regular automatic updates. Of the self-hosted options considered (self-hosted WordPress headless, self-hosted Supabase, a custom Node auth backend), WordPress core is the only one with a mature, turnkey automatic-update mechanism (background security/minor updates on by default since WP 3.7). Running WP with zero plugins (not even one) keeps the *entire* auth-relevant surface limited to WP core itself, which is what actually gets that strong auto-update treatment.

**Revised from a third-party JWT plugin:** the original version of this decision used WP core plus one JWT-auth plugin. On review, that plugin — not WP core — would have been the part actually deciding authentication outcomes, and it wouldn't have inherited core's auto-update track record (third-party WP JWT plugins have had real CVEs, e.g. predictable fallback signing secrets enabling auth bypass). Application Passwords remove that dependency entirely: the whole credential-verification path is WP core, full stop. See D-021 for how this changes token issuance downstream.

**Tradeoff:** this means running and maintaining a second stack (PHP/MySQL) alongside the app's own JS/TS stack, solely for auth. Accepted as the cost of the self-hosted + auto-updating requirement.

## D-020 Plan preamble: modules and settings

Every plan can start with a preamble, before the root node, containing:

- **Module declarations** — `module "<name-or-url>"`. If the string is a bare name, it resolves against a built-in registry (an "internal" module); if it's a URL (has a scheme, e.g. `https://...`), it's fetched and run from there (an "external" module). One statement form covers both — no separate keyword needed, since the string's shape already disambiguates it. This is the concrete loading mechanism for core aim #3 ("plan view and interactivity can be changed/added by modules") and [decisions.md](decisions.md#d-011-module-capabilities) — it doesn't resolve what a module's API surface looks like once loaded (still [open-questions.md](open-questions.md#f-002-module-api-surface)), only how a plan declares that it wants one.
- **A `settings { ... }` block** — plan-level configuration flags. Extensible, not a fixed list; the first two concrete examples are `allowCollisions` and `allowUnrealisticPolygons`.

Example:

```
module "wall-tools"
module "https://example.com/campervan-kit.js"

settings {
  allowCollisions: false
  allowUnrealisticPolygons: false
}

node room { ... }
```

**External modules are trusted by default — no sandboxing.** Loading a module from a URL means fetching and running that code inside the plan editor/renderer with no isolation (no sandboxed iframe/worker, no permissions prompt, no allowlist). This matches D-003: the primary author is an AI generating code with a technical human reviewing it, closer to a developer choosing what npm package to install than an end user clicking an untrusted link. Revisit if the audience broadens beyond that.

**Validated: modules can actually be loaded and run, for the first time.** [Prototypes/12-module-loading/](../Prototypes/12-module-loading/) is the first prototype to exercise this at all — every earlier one only had the syntax documented. Confirmed working by the user for both paths: an internal module (bundled in the page, resolved by bare name against a small built-in registry) and an external one (fetched at runtime via a dynamically created `<script src>` tag pointing at a plain adjacent `.js` file). Both register a new shape-rendering function the core renderer calls exactly like a built-in shape — see [open-questions.md](open-questions.md#f-002-module-api-surface) for what this does and doesn't prove about the module API surface.

**Settings encode real default behaviors, not just examples.** Collision-avoidance between objects and polygon-realism checks (e.g. rejecting self-intersecting/degenerate shapes) are intended to be actual default behaviors of the renderer/editor, not hypothetical — `allowCollisions`/`allowUnrealisticPolygons` opt out of them per-plan, defaulting to `false` (i.e. checks on, "realistic" behavior by default). The precise mechanics of these checks (what exactly counts as a collision or an unrealistic polygon, and how a violation surfaces — a warning like D-015, a rejected edit, something else) are undecided — see [open-questions.md](open-questions.md#f-004-collision-and-realism-checks).

**`allowCollisions` is materially harder than `allowUnrealisticPolygons`, and this wasn't recognized when both were decided together.** Polygon self-intersection has a standard, cheap algorithm (checked, see the validation note below). General collision detection between arbitrary — possibly rotated, possibly concave — objects is a real, unsolved-here computational geometry problem, not a small implementation detail. `allowCollisions` remains a genuine intended behavior (it wasn't invented for this decision, it's specifically what was asked for when settings were introduced), but treat it as unentworfen: no algorithm has been chosen, unlike its sibling setting.

Validated (partial — `allowUnrealisticPolygons` only): [Prototypes/05-polygon-corners/](../Prototypes/05-polygon-corners/) implements the `settings { ... }` preamble parsing and a concrete self-intersection check on `polygon` shapes, rejecting a corner drag outright (before committing the edit) rather than letting it happen and flagging it after. `allowCollisions` remains unimplemented.

## D-021 Plan storage backend

Logged-in users can save plans server-side (cloud sync across devices), via a **separate, minimal storage service — not WordPress**. This extends D-007 (which so far only covers local storage/file export) now that D-019 introduces user accounts; auth without anything user-specific to persist would be nearly pointless.

**Why not store plans in WordPress:** D-019 deliberately keeps the self-hosted WP instance to core only (no plugins at all) specifically to limit its attack surface. Adding plan storage there (e.g. a custom post type and REST endpoints) would undo that. A plan is fundamentally just a named text blob per user — it needs none of WordPress's content-management machinery (revisions, taxonomies, media library), so routing it through WP would be pure overhead for no benefit.

**The storage service** is a separate, minimal API plus database: essentially CRUD for "plan text under `{userId, name}`" (save/load/list/delete) — nothing more. Runs self-hosted on the same server infrastructure, consistent with D-019's self-hosting requirement.

**Token flow, revised alongside D-019's move to Application Passwords:** WP Application Passwords are verified via HTTP Basic Auth directly against WP's own REST API — they aren't a self-contained signed token a separate service can validate independently. So: on login, the app verifies the user's credentials against WP's REST API once; the **storage service then issues its own short-lived signed session token** (HMAC-signed with a secret it controls) for that session. Subsequent storage requests validate that token locally, with no round-trip to WP — WP is only contacted at login/token-refresh, not on every storage call. This keeps the earlier performance property (no per-request WP dependency) while moving token issuance into code the team controls, rather than a third-party WP plugin's.

Marketplace listing/discovery — WordPress's other usual draw — is explicitly not a factor here.

## D-022 Scraping protection: content, not the language

Scraping protection targets **user content** (saved plans), not the plan language/parser/renderer itself. The language and its client-side implementation are not treated as something to hide.

**Why the language isn't protected:** doing so would mean moving parsing off the client, since any client-side JS is inherently inspectable — but that directly conflicts with already-decided live editing (D-006, D-009, core aim #1 "code and plan change together"), which requires the parser to run locally with no network round-trip per keystroke/drag. Minification/obfuscation (or even compiling the parser to WASM, which stays fully client-side and is harder to reverse-engineer than plain JS) would raise the bar somewhat, but doesn't address the deeper issue: D-003 and D-017 require the language's *specification* to be publicly documented so an AI can author it at all — once the grammar itself is public knowledge, hiding one particular implementation of a parser for it protects little, since anyone can write their own parser from the spec. The implementation was never really the asset; the openly-documented spec has to exist for the product to work.

**What is protected — user content:**
- The storage service (D-021) gates all access to a plan beyond its owner behind auth. **Correction:** this decision previously also asserted rate-limiting as already covered by D-021 — it isn't; D-021 never actually committed to it. Rate-limiting (so even an authenticated account can't bulk-scrape other users' plans) is an intent/recommendation here, not a decided feature. Needs its own concrete decision before being relied on.
- **Superseded by D-056: rate limiting is now built**, closing this gap for real rather than leaving it as an intent.

**Moved to open-questions.md (from a critical review):** this decision previously also specified how a plan shown to a non-owner should be protected (server-rendered snapshot instead of raw source) — but public/shared viewing was never itself decided as a feature. Designing the protection for a feature that doesn't exist yet got ahead of the actual decision. See [open-questions.md](open-questions.md#f-005-public-plan-viewing) — the reasoning is preserved there, not lost, just no longer stated as settled.

## D-023 AI integration mechanism (current: copy-paste)

For now, using an AI to write/edit a plan works by **copy-paste**: the human converses with an AI (e.g. Claude) in a separate chat/session, then copies the plan code it produces and pastes it into the app's code editor (D-006). There is no live API integration — no server-mediated LLM calls from within the app, no streaming of AI output directly into the editor, and consequently nothing to design yet for concurrent AI+human edits, since the human is always the one physically pasting, one paste at a time.

This was previously an unaddressed gap (D-003/D-006 assumed "the AI writes" without ever specifying the mechanism) found in a critical review. Copy-paste resolves the immediate question cheaply and sidesteps real complexity that doesn't need solving yet: no API key exposure to worry about, no streaming/conflict-handling design needed.

**Deferred to [open-questions.md](open-questions.md#f-008-live-ai-integration):** a real, live API integration — if and when it's wanted — is a separate future decision, not made here.

## D-024 Embeddability

The app is built as a standalone product (D-019), but designed from the start so a **single plan is embeddable elsewhere** — e.g. a web component or iframe snippet a third-party site (a real-estate listing, a campervan seller's page) can drop in without a custom integration. This was discussed early on but never actually recorded as a decision; recorded now after the gap surfaced while writing [architecture.md](../documentation/architecture.md).

**What this actually commits to right now:** not building an embed feature immediately, but not designing the renderer/editor split in a way that would make embedding hard later — e.g. the rendered-plan piece (D-004's SVG output) should stay meaningfully separable from the code-editor chrome around it, rather than the two being tightly fused. A concrete embed mechanism (web component vs. iframe, what's configurable, whether it's read-only or interactive) isn't designed yet.

## D-025 Deployment topology

WordPress (D-019) and the storage service (D-021) run on the **same server, same domain** — different paths or ports behind the same origin, not separate subdomains. This resolves two things at once: no CORS configuration needed anywhere (same-origin requests throughout), and the storage service's session-token signing (D-021) can rely on a locally-shared secret/key rather than fetching WP's public key over the network, since both processes live on the same machine.

## D-026 Labels and dimensions, per element

**Renamed by D-029:** `showDimensions` below is now `dimensions` — kept as originally written here since this decision predates that rename; see D-029 for why.

Two plain properties on any node — no new primitive, same "just properties" pattern as everything else: `label: "text"` shows a name; `showDimensions: true` shows the shape's own computed size (width × height for a rect, diameter for a circle) rather than a hand-typed value that could drift out of sync with the actual geometry. Visibility is controlled per element via `show: "always" | "hover"` (defaulting to `"hover"` when a label/dimension is present but `show` is omitted). `label` was already part of D-013's Node definition ("an optional user-defined label/name") but no prototype had ever actually rendered it before this.

**Scope:** `showDimensions` only computes a value for `rect` and `circle` — shapes with an unambiguous single "size". `polygon`/`line` support `label` only; per-edge lengths or perimeter would be a reasonable extension, not built. Nodes with no shape at all (D-016's invisible corner/anchor nodes) can't carry a label yet either — a real gap in "every element individually," not a deliberate exclusion, since it wasn't clear what a label should look like with no shape to attach it to.

Validated: [Prototypes/10-labels-dimensions/](../Prototypes/10-labels-dimensions/) implements this across all four shape kinds from D-018/09 (rect, circle, polygon, line), with hover-reveal done via a CSS adjacent-sibling selector (`.obj:hover + .annotation[data-show="hover"]`) rather than JS — deliberately `+` and not `~`, so hovering one object can never reveal a different object's annotation; this relies on the annotation always being pushed as the shape's immediate next sibling in the render output, a real ordering constraint on the renderer, not something structurally enforced.

## D-027 Unified prototype: everything combined into one plan

[Prototypes/13-unified/](../Prototypes/13-unified/) is the first prototype that isn't isolating one question — it combines everything validated in 01–12 into a single, realistic frontend-only plan (a small studio apartment), confirming the pieces actually compose rather than just each working alone:

- Full expression grammar + `settings` + `module` preamble + `connection` statements, all in one parser (09/10's expressions and points-as-references, 12's module loading, 08's connections).
- All four shape kinds (rect, line, polygon, circle) plus a module-provided shape (`star`, from the bundled `star-tool` module), in the same plan.
- Shared corner-node points (D-018) for walls-with-a-door and a 5-point polygon rug, *and* a real Connection (D-014) between two whole rects (stove/counter) — both relationship mechanisms exercised side by side, each in the scenario it actually fits.
- D-026 labels/dimensions, D-012 solve-backward (the desk's position is written as `parent.size.x - 1.2m - 0.2m`, so dragging it resizes the room rather than moving the desk relative to a fixed room), and F-004's realism check (dragging a rug corner into a self-intersecting shape is rejected), all live in the same drag path.

Several real problems surfaced only by this combination, and only by actually using it — not by any single-feature prototype in isolation, and not by code review alone: a parser bug (negative-literal editable spans), a connection-adjacency bug (containment vs. touching) and a UX gap (connecting didn't snap objects flush) both found from user feedback on the running prototype, a hover-during-drag glitch also found the same way, and one case (the desk's expression-backed position resizing the room) that wasn't a bug at all — the code did exactly what D-012 says — but was still the wrong thing to build, which no amount of tracing the logic in isolation would have caught. See the notes under D-012 and D-014 above. That's the actual value of building a unified prototype and putting it in front of the user rather than trusting that individually-validated pieces compose for free.

**Still explicitly out of scope here, unchanged from before:** no backend (D-019/D-021 remain undesigned in code), no real constraint solver beyond D-012's linear case (F-001), modules still only contribute a shape renderer (F-002). This prototype is an integration checkpoint, not a claim that F-001/F-002/F-004's remaining open questions are resolved.

Clicking an element in the rendered plan should highlight its corresponding span in the code editor and scroll it into view — not yet built anywhere, recorded as a decision for when the real editor exists. ## D-029 Naming/syntax review — six changes

A critical review of the language's naming and syntax (requested directly, not found incidentally) turned up two real inconsistencies and several smaller frictions. All six adopted immediately, applied to [Prototypes/13-unified/](../Prototypes/13-unified/) and [documentation/language.md](../documentation/language.md):

1. **`connection` gets an optional trailing `{ ... }` for properties.** [decisions.md](decisions.md#d-014-connection-semantics) has always described a connection's `kind` (symmetric/directional) as "a property of the individual connection" — but the only implemented syntax, bare `connection A B`, had no way to express any property at all. This is exactly the mismatch [open-questions.md](open-questions.md#f-006-documentation–implementation-gap-ai-authoring-test) caught: an AI guessed an object-literal connection syntax with a `kind` field, because the documentation implied properties existed where the grammar had none. Fixed by allowing `connection A B { kind: "directional" }`, mirroring how a Node's `style` is already written. The drag/render logic still treats every connection uniformly regardless of `kind` — only the ability to write the property now exists, not any behavior keyed on it.
2. **Shape `"line"` renamed to `"polyline"`.** "Line" conventionally implies a single 2-point segment; the shape has supported any number of points since [Prototypes/09-more-shapes/](../Prototypes/09-more-shapes/). `"polyline"` matches both the actual capability and the SVG element it renders as.
3. **`showDimensions` renamed to `dimensions`.** It shared the word "show" with the unrelated `show` visibility property, despite meaning something different — `showDimensions` was "include this content at all" (boolean), `show` is "when to reveal already-included content" (enum). Only `show` now carries "show" in its name.
4. **`style.dash` renamed to `style.strokeDash`.** Consistent with `strokeWidth` — both are inherently stroke-only properties (a fill can't be dashed), so both now carry the prefix; previously only one did.
5. **The `.x`/`.y` array-access rule is now stated as a general rule, not left implicit in one example.** Any 2-element `[a, b]`-valued property (`size`, `position`, a literal `points` pair) can be indexed via `.x`/`.y` — `evalAst` already implemented this generically, but [documentation/language.md](../documentation/language.md) only ever showed the one `parent.size.x` case, reading as a `size`-specific special case rather than the general mechanism it actually is.
6. **`parent.size.x`'s real precondition is now stated explicitly.** It only resolves when the parent has a `size` property at all — in practice, only a `rect`. Previously implicit (and only discoverable by hitting the unresolved-reference error against a `circle`/`polygon` parent). Whether a shape-agnostic "container extent" accessor should exist instead is a new open question, not resolved here — see [open-questions.md](open-questions.md#f-010-shape-agnostic-container-extent).

## D-030 Right-click context menu

Right-clicking an object in the rendered plan opens a small custom menu, replacing the browser's default one — the first editor-chrome interaction beyond drag/select/connect. [Prototypes/13-unified/](../Prototypes/13-unified/) implements a first item, **Delete Element**, with the menu itself built as a plain data-driven list (`{label, action}`) specifically so later items don't require restructuring it — more are expected ("weitere folgen") but not yet specified.

**Delete semantics, decided alongside the syntax:** deleting a node removes its own source block (children included) plus any `connection` statement mentioning it — a dangling reference would otherwise just silently do nothing at render time, which is more confusing than removing it outright. Two cases are refused rather than allowed to silently break something else: deleting the plan's root (nothing to render in its place) and deleting a node still referenced as a shared corner (D-018) by some `polyline`/`polygon`'s `points` — the latter surfaces as a message naming which shapes reference it, matching F-004's established "reject with a message" pattern rather than letting the reference dangle.

This needed the parser to track a whole node declaration's own source span (`start`/`end` covering `node id { ... }` through its matching close brace), not just individual property values' spans as before — the first time the parser has needed to address a *block*, not a value, for an edit.

**Bug caught while tracing through this, before it was ever reported:** the existing `pointerdown` handler didn't check which mouse button was pressed, so right-clicking an object fired the same drag/selection logic as a left-click, in addition to opening the new context menu — a right-click alone (no movement) would silently select the object as a side effect of what looked like "just opening a menu." Fixed by ignoring any `pointerdown` where `e.button !== 0`.

## D-031 Interactivity as a module

[Prototypes/14-interactivity-module/](../Prototypes/14-interactivity-module/) moves every interactive behavior from 13-unified — drag-to-move (solve-backward, realism check, connection propagation), click-to-select, connect/disconnect icons with snap, hover previews, the right-click context menu (D-030) — out of the host page entirely and into [interactivity-module.js](../Prototypes/14-interactivity-module/interactivity-module.js), loaded the same way a shape-rendering module is (`module "interactivity-module.js"` in the plan's own preamble, D-020). This is the first test of D-011's second promise: every earlier module prototype (12, reused in 13) only ever contributed a shape renderer. One rough attempt, like 12 was for rendering — not a settled proposal for F-002.

**The `window.PlanCore` API this required, concretely:** `parse`/`render` (render now takes no selection state at all — pure AST-to-SVG, no icons, no `.selected` class); the editable-literal helpers `numOf`/`isEditable`/`formatNumber`; the parsed-tree helpers a drag needs (`computePositions`/`computeCornerUsers`/`resolvePointAbs`/`nodeDragEdits`/`connectedNodeIds`); `rootEl`/`sourceEl`/`dragmsgEl`/`modlogEl` as DOM mount points; the scale constant `M`; and `rerender(opts)`/`onRendered(cb)` to trigger a render cycle and react once it's done. Adjacency/contact-point math, icon markup, the context menu's own DOM/CSS, and generic text-splice helpers are **not** in this API — the module brings its own copies, on the judgment that these are interactivity-specific, not things core should need to know exist.

**Three real seams found, not hidden by treating the split as cleaner than it is:**
- **Icon z-order changed.** Connect/disconnect icons are now the module's own overlay, appended into the rendered SVG *after* core's own output — which already ends with anchors painted last (D-018's correction). Icons now sit on top of anchors, a reversal of 13-unified's ordering. Harmless in this example (no icon and anchor ever actually coincide), but a real, undecided question for a plan where they would — core has no hook for a module to insert content *between* two of its own render passes, only *after* all of it.
- **A rendering-level CSS rule needed a module override, not core awareness.** D-026's label hover-reveal (`svg .obj:hover + .annotation[data-show="hover"]`) is core's own rule — a rendering feature, unrelated to whether any interactivity module is even loaded. Suppressing it during a drag (D-014's hover-during-drag correction) needed the module to inject a higher-specificity rule scoped to its own `dragging` class, rather than core ever mentioning drag state in its stylesheet. Correct, but not obviously "clean" — core's presentation and the module's interactivity state aren't as separable as the architecture pretends.
- **"Is this a drag continuation" became an explicit parameter instead of an inferred fact.** 13-unified's core distinguished a drag's own repeated re-renders from a fresh edit by checking whether the textarea's `input` event had fired (drags write `sourceEl.value` programmatically, which never fires `input`). With rendering triggered through one shared `rerender()` entrypoint regardless of caller, core can no longer infer *why* it was asked to re-render — so `rerender({ preserveViewBox: true })` makes the caller say so explicitly. Arguably a cleaner API than the implicit heuristic it replaced, but it exists only because the inference core relied on before stopped being available once interactivity moved out.

**Still open, unchanged by this experiment:** F-001 (constraint solving beyond simple chains), the rest of F-002 (new-*primitive* composition — D-011's third promise — hasn't been tried by any prototype yet), and whether "interactivity is enabled per-plan by declaring a module" (this prototype's choice, reusing D-020's mechanism unchanged) is actually the right default versus interactivity being an always-on host feature.

**A real gap found from testing, not from reading the code: removing `module "interactivity-module.js"` from the plan left interactivity running anyway.** Every module-loading prototype before this one (12, reused in 13) tracked "loaded" as permanent — once fetched and registered, a module stayed available for the rest of the session regardless of whether later edits still declared it. That's the *right* behavior for a stateless shape renderer (nothing to undo — a `shape:"star"` node either exists in the current plan or it doesn't, independent of whether the module that taught the renderer about "star" is still declared). It's the *wrong* behavior for a module with persistent side effects — event listeners, injected DOM, injected CSS — which is exactly what an interactivity module is made of: those don't stop existing just because a later render's module list omits the declaration.

Fixed by giving `PlanCore` a `registerModuleCleanup(name, cleanupFn)` hook. Before loading each render's declared modules, core now diffs the current module list against every module that previously registered a cleanup; anything no longer declared gets its cleanup run and is evicted from the loaded-module cache, so re-declaring it later loads it fresh rather than silently doing nothing. `interactivity-module.js` uses this to precisely undo everything it set up (every event listener removed via the same named-function reference it was added with, the injected `<style>` and context-menu DOM removed, drag/selection state cleared) — and, since `onRendered` callbacks would otherwise keep firing forever, `onRendered` itself had to start returning an unsubscribe function. `star-tool` was given the same treatment for consistency (its cleanup deletes `window.PlanModules["star"]`), even though nobody had reported a problem with shape modules specifically — leaving that inconsistent while claiming "removing a module deactivates it" would have been dishonest.

This is arguably the single most useful finding from building 14: module loading and module *activation* turned out to be two different things once a module has state, and D-020's original design only ever had a story for the first one.

## D-032 Parent-child placement modes

A child's placement relative to its own parent (F-011's single-parent hierarchy) can be one of three modes:

1. **Free** — no constraint at all. The current, only-ever-implemented default: a child's `position` is just local coordinates, unconstrained by the parent's own geometry.
2. **Outside, attached** — the child must sit outside the parent's boundary while touching it directly (e.g. a mailbox on the outside of a house wall).
3. **Inside** — the child must stay within the parent's boundary; where it also needs to sit flush against the boundary itself (e.g. a door built into a wall, as opposed to free-floating furniture), that attachment is approached from the inside, the mirror case of mode 2's outside attachment.

This is the concrete shape D-014/F-001's long-standing "loose attachment" gap needed and never had: D-014's original motivating example (a door attached to the wall on each side) was superseded by D-018's shared corners for the *pinned-to-one-exact-point* case, but F-001 explicitly kept noting a second, harder case — "a door that should stay somewhere along a wall without a pinned shared point" — as real, unaddressed, and possibly not even needing a full constraint solver. Modes 2 and 3's edge attachment are exactly that case, finally given a concrete mechanism instead of staying a description of the gap.

**Resolved design questions (asked directly, not assumed):**
- **Dragging an edge-attached child slides it along the parent's boundary**, rather than the constraint merely rejecting an otherwise-free move (F-004's rejected-edit pattern). Chosen because constrained sliding is what "attached to a wall" actually means experientially — a door that can only be nudged back into place after every invalid drag doesn't feel attached, it feels blocked.
- **This extends Connection (D-013/D-014), it isn't a separate node property.** A placement mode is a property of a *connection between a child and its own parent* (`connection door_id room_id { placement: "inside" }`, syntax illustrative), reusing D-029's connection-properties syntax rather than inventing a second mechanism. Only meaningful when the two connected nodes are actually in a parent-child relationship (F-011) — a placement-mode connection between unrelated nodes has no coordinate space to be "inside" or "outside" of, and should be rejected, not silently ignored.
- **Scoped to `rect`/`polygon` parents only**, which have an unambiguous boundary. `circle`/`polyline` parents don't have a closed "inside" in the same sense — this mirrors F-010's already-open question about shape-agnostic container geometry, and isn't solved by this decision; a parent with the wrong shape kind for the requested mode should be a rejected declaration, not a silent no-op.

**Resolved, asked directly:** mode 3 ("inside") is **containment as the baseline, edge-flush attachment as an independent, optional addition on top** — not something "inside" always implies. A sofa placed inside a room only needs the containment half (free to sit anywhere within the parent's bounds); a door built into a wall needs both halves at once (stays within bounds *and* sits flush against one specific edge from the inside, D-032's original motivating case). Confirmed the earlier reading, which had been recorded as likely but explicitly not assumed settled. Concretely: `placement: "inside"` alone means containment only; a combinable second property (`flush: true`, syntax illustrative) layers the edge-seeking behavior on top for the door case — not a fourth mode, an addition to the third.

**Status: partially built.** No parser support for a `placement` property driving this (still using a plain `connection`, not a declared mode), and no containment check against a parent's own boundary (mode 3's "inside," distinct from F-004's sibling-vs-sibling collision idea) — but the core constrained-sliding mechanic behind mode 2 ("outside, attached") is now built and working, see the validation note below. F-001 stays open until the syntax and the "inside" case are also addressed.

**Superseded by D-044: mode 3 ("inside") is now wired into `docs/`, not just validated standalone in Prototype 16.**

**A real, not hypothetical, case for it turned up almost immediately:** [Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/)'s power line has a point that must stay attached to the house's outside wall (a plain rigid `connection`, at the time the only option) — dragging the house correctly kept the point flush, but dragging the point alone also dragged the whole house, since D-014's Connection has no direction and this design's "outside, attached" mode didn't exist yet.

**Mode 3 ("inside") gets its own first validation:** [Prototypes/16-parent-child-placement/](../Prototypes/16-parent-child-placement/) — a standalone local test (not wired into `docs/`), requested directly rather than built straight into the product given D-041's own collision-sliding is still imperfect and this reuses the same approach. A `connection child parent { placement: "inside" }` clamps the child to stay within the parent's boundary when dragged, sliding along whatever wall it hits — `clampToStayInside()` is structurally the same binary-search-then-tangent-slide as D-041's `clampToNoCollision()`, just retargeted from "don't overlap a sibling" to "don't leave the parent," reusing the insight that the tangent-computing part of that algorithm doesn't care which direction is "outside." Deliberately narrow: only a `rect` child with a literal `position` against a `rect`/`polygon` parent, no `flush` (the door-in-wall half from the "resolved" note above — not attempted here), no corner-refs, no other connections. `placement` parses for free (connection properties were already a generic bag, D-029) — no parser changes needed for this test.

**Correction, requested directly after actually using the prototype: "extends Connection" (above) was the wrong call — reversed.** The friction the user hit was real, not just verbose syntax: a room with ten furniture pieces would need ten separate `connection child room { placement: "inside" }` lines, all saying the identical thing, with a real risk of an eleventh child silently getting forgotten. Re-examining *why* D-032 reached for Connection in the first place: Connection exists to establish a relationship between two elements that the tree doesn't otherwise encode (D-013/014) — but a child's parent is *already* unambiguous, encoded directly by nesting (F-011's single-parent hierarchy, which this very decision's opening line already invokes). Routing "my relationship to my own parent" through a mechanism built for "the relationship between two otherwise-unrelated elements" added a redundant identifier (the parent's own id, restated on every child) without encoding any information the structure didn't already have — the actual source of the repetition, not an incidental syntax cost.

**Revised design: `placement` moves onto the element itself, plus a parent-level default.**
- **On the child directly:** `element sofa { placement: "inside" }` — no connection, no restating the parent's id; "my parent" is already whatever element this one is nested inside.
- **On the parent, as a default for every direct child that doesn't say otherwise:** `element room { childPlacement: "inside" }` — the one-line fix for the actual motivating case ("everything in this room stays inside it"), instead of one connection per child. A child's own `placement` always overrides this when set — same override shape as D-038's `edgeLengths` and D-041's `allowCollisions`, now a third feature following the identical pattern.
- **Deliberately a *different* name at the two levels (`placement` vs. `childPlacement`), not the same name reused like `edgeLengths`.** The two aren't the same concept at different scope, they're genuinely different claims — "my own placement relative to my parent" vs. "the default I hand down to whatever's nested in me" — reusing one word for both would be exactly the kind of collision D-033's principle #2 exists to catch, not an application of it.

`flush` (the door-in-wall addition from the "resolved" note above) still applies per-element only — it never made sense as a container-wide default (not every child of a room is a door), so it isn't part of this revision.

**Validated (the drag mechanic, not the syntax):** built directly into [Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/)'s interactivity module rather than waiting for D-032's full design (a `placement` property on connections) to be implemented first — a bare position-only node rigidly connected to a rect, while actually resting on one of its edges, now slides along that edge on drag instead of dragging the rect. Motion perpendicular to the edge is ignored; motion along it is clamped to the edge's own span (dragging past a corner stops there with a message, rather than jumping to a different wall or dragging the rect). Dragging the rect itself is untouched — a connected point still follows it rigidly, which is still the wanted behavior in that direction. This is deliberately keyed off "connected + geometrically resting on an edge" rather than an explicit `placement: "outside"` declaration — the syntax D-032 describes doesn't exist yet, so the behavior currently just always applies whenever a point/rect pair happens to meet that geometric condition, with no way to opt out and get D-014's old undifferentiated rigid dragging back for such a pair.

## D-033 Naming principles for the plan language's syntax

D-017 already set two goals for the concrete syntax (low-ambiguity for AI generation, token-efficiency), but never defined what specifically makes a name ambiguous — that got tested only reactively, first in D-029's naming review, then again here. This decision makes the underlying principles explicit, derived from patterns across both rounds, rather than leaving "is this name good" to be re-litigated from scratch each time:

1. **No implied scope beyond actual behavior ("no false-friend names").** A name must not suggest broader, narrower, or different behavior than the feature actually has. Test: would someone judging only the name misjudge what it does? Violations found and fixed: `"line"` implying exactly 2 points when it accepts any number (D-029); `allowUnrealisticPolygons` implying general realism-checking when only self-intersection is checked (this decision, below).
2. **One concept, one name.** Distinct properties shouldn't share a word that implies a relationship between them that doesn't exist. Violation found and fixed: `show`/`showDimensions` (D-029).
3. **Consistent structural patterns.** Properties that are structurally or semantically parallel (e.g. both stroke-only) should be named with the same pattern (prefixed or not), not a mix. Violation found and fixed: `strokeWidth`/`dash` → `strokeWidth`/`strokeDash` (D-029).
4. **Plain, widely-known vocabulary over specialized jargon, when a plain description is equally precise.** Prefer a term any technically literate reader can correctly infer without already knowing a specialist term, even at some cost in length — especially for names that appear at most once or twice per plan (settings, keywords), where the extra tokens are negligible. A precise technical term is not automatically the better choice: "complex polygon" is the exact computational-geometry term for self-intersecting, but reads to a general reader as "complicated," which is a different (and wrong) claim.
5. **Borrow precedent from adjacent, well-known formats — but only where the precedent doesn't itself mislead.** Preferring SVG/CSS conventions for style properties, XML/HTML/scene-graph conventions for hierarchy and element terms, and standard computational-geometry/game-dev terms for geometric checks reduces what an AI or human author has to learn from scratch. But a borrowed term's *other* common connotation can conflict with what it needs to mean here — weigh that conflict, don't adopt precedent automatically.
6. **A name is judged on what the thing does, not on the words used to request it.** How a feature happened to be described in conversation when it was built is not evidence for or against a name — an AI regenerating similar functionality later starts from the thing's actual behavior, not this session's phrasing, so the name has to be independently re-derivable (ties to D-003: the AI is the primary author going forward, not a participant in this specific conversation).
7. **Priority when these conflict:** unambiguity (1–3) outranks plain-vocabulary preference (4–5), which outranks D-017's token-efficiency goal. Token-efficiency is a tie-breaker between two names that are otherwise equally clear, and matters more for properties repeated per-node (`strokeWidth`, `position`) than for keywords/settings appearing at most once per plan.

**Audit against these principles, requested directly:**

| Name | Verdict | Notes |
|---|---|---|
| `allowUnrealisticPolygons` | **Fails #1** | "Unrealistic" implies general realism-checking; only self-intersection is checked (F-004 already says so explicitly). Renamed to `allowSelfIntersectingPolygons` — plain, exact, no jargon needed (principle #4 over the equally-precise but jargon-dependent `allowComplexPolygons`). |
| `node` | **Fails #1/#5** | Same keyword names both a shaped/container element *and* a bare position-only point (D-016's anchor pattern) — but "node" carries a strong graph/network connotation of "a point," which is right for the second case and wrong for the first. `object` doesn't fix this (implies "has visible shape," implies "leaf," fits the container case worse). Renamed to `element` — neutral on visible/invisible and container/leaf, with precedent in exactly the domain this language's hierarchy already resembles (XML/HTML/SVG: a `<div>`, a `<rect>`, and an empty `<g>` are all "elements"). |
| `connection`, `module`, `settings`, `style`, `fill`, `stroke`, `strokeWidth`, `strokeDash`, `label`, `show`, `dimensions`, `points`, `position`, `radius`, `parent`, `.x`/`.y` | Pass | No implied-scope mismatch, no jargon barrier, consistent with SVG/CSS/markup precedent. |
| `shape` | Pass (deliberate) | Not named `type` on purpose (D-013) — avoids implying a semantic type catalog the language explicitly doesn't have; matches its literal meaning (how it's drawn). |
| `allowCollisions` | Pass, unimplemented | The name doesn't overpromise — "collisions" is standard, well-understood terminology — but nothing checks it yet (D-020), so its precision against real behavior can't be fully judged. |
| `kind` (proposed connection property, D-032/D-029) | **Undecided, not yet built** | Never actually implemented — `type` was avoided for `shape` on principled grounds (D-013), and reusing `kind` without checking it against these same principles once D-032's syntax is actually built would be exactly the un-audited naming this decision exists to stop. |
| `placement` mode values `"free"`/`"outside"`/`"inside"` (D-032) | **Blocked on semantics, not naming** | D-032 itself leaves open whether `"inside"` means pure containment or also implies edge-attachment (see D-032's own "not yet resolved" note) — naming it precisely has to wait until what it *does* is actually settled, not the other way around. |

**Scope of the fix:** `allowSelfIntersectingPolygons` and `element` are applied going forward — [Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/) and [documentation/language.md](../documentation/language.md) use the new names. Earlier prototypes (01–14) keep their original syntax unchanged, consistent with how D-029's renames were handled — they're throwaway snapshots of the language *as it stood when built*, not living documents kept in sync forever; each carries a short pointer note to the newer terminology instead of being rewritten.

## D-034 First real product: a hosted, frontend-only app

Everything before this was explicitly throwaway (D-002) — one self-contained HTML file per question, living in `Prototypes/`, never meant to be used as a tool. `docs/` is different: the first version meant to actually be used and kept working, not rebuilt from scratch next time something changes. Concretely:

- **Frontend-only, no accounts.** Reuses D-007's baseline (local storage + file export/import) rather than waiting for D-019/D-021's auth/storage backend, which remain decisions-only, not code. This was a deliberate scope cut, not an oversight — the backend adds real infrastructure (a second stack, D-019's tradeoff) for a benefit (cross-device sync) a first hosted prototype doesn't need yet.
- **`docs/` as the location, not `Prototypes/`.** Matches GitHub Pages' "serve from a branch's `/docs` folder" option — the simplest deployment path (a Settings toggle, no GitHub Actions workflow needed) — and signals structurally that this folder is the product, not another disposable experiment.
- **Architecture reused verbatim from [Prototypes/15-utility-connection/](../Prototypes/15-utility-connection/):** core (parse/render only) plus `interactivity-module.js` (drag/select/connect/context-menu) loaded through the same `PlanCore` API D-031 designed. The interactivity module's logic is unchanged from 15 (only comments were tightened for a production codebase, not narrated around the debugging history that produced them) — this is the first time that architecture has been reused rather than rebuilt per prototype, some evidence D-031's API surface generalizes past the one plan it was designed against.
- **Every plan gets interactivity by default**, new here: earlier prototypes required a plan to explicitly declare `module "interactivity-module.js"` to get any drag/select/connect behavior at all (matching D-020's "modules are opt-in per plan" design). For a product where the built-in editor *is* the point, requiring every example (and everything a user writes from scratch) to remember that declaration is pure friction with no offsetting benefit — the app injects it automatically for any loaded plan that doesn't already declare it, rather than changing D-020's underlying opt-in mechanism itself (a hand-written plan still has to declare any *other* module it wants).
- **New, not present in any prototype:** a small toolbar (new-from-example, open file, save file) and automatic persistence to `localStorage` on every change (parse-successful or not, so a syntax error mid-edit never loses keystrokes on refresh) — the concrete implementation of D-007's "local storage and/or file" persistence, previously only a plan-language example living in one in-memory `EXAMPLE` constant per prototype with no save/load at all.

**Deliberately still missing:** any build step (still plain static files, zero dependencies, matching every prototype so far — nothing here needed a bundler), the backend (D-019/D-021), and F-002/F-006's remaining gaps (module API surface beyond rendering+interactivity, and the documentation-vs-implementation mismatch F-006 found). This is a hosted prototype, not a claim that those are resolved.

**Live:** [tminder.github.io/2DPlaner](https://tminder.github.io/2DPlaner/), confirmed working via GitHub Pages (branch `master`, `/docs` folder) — the first thing built in this project that a URL points at instead of a local file.

**First real layout bug, found from actually using the hosted app:** every prototype through 15 sized the SVG from the plan's real-world dimensions (meters × `M`) with no relationship to available screen space, and nothing constrained the page to the viewport — fine for a prototype opened as a local file, wrong for an app meant to be used. Fixed with a full-height flex layout (fixed-width code pane, viewer pane `flex: 1`) and the SVG's own `width`/`height` attributes overridden by CSS (`100%`/`100%`) so it fills its container instead of rendering at its native meters-times-scale size.

That CSS override has a real consequence the fix had to account for, not just a styling detail: once the SVG's on-screen size no longer matches its `viewBox` 1:1, a screen pixel of mouse movement during a drag no longer equals `1/M` meters — the drag math (`interactivity-module.js`) was silently assuming native, unscaled rendering. Fixed by reading the SVG's actual `getBoundingClientRect()` against its `viewBox.baseVal` on every drag frame to compute the real effective scale (accounting for `preserveAspectRatio`'s default "meet" behavior — the *smaller* of the width and height ratios, since that's the axis that actually constrains the fit), rather than assuming `core.M` still holds. Icon placement and all rendering math are unaffected — those already operate purely in viewBox units, which the CSS resize doesn't touch.

## D-035 Viewer zoom/pan and a scale bar

Second round of feedback on the hosted app (D-034), after confirming the layout fix worked: the viewer needed a scale bar (bottom-right, the map/floorplan-reading convention) and the ability to zoom. Both live entirely in `interactivity-module.js`, not core — matching D-031's boundary (core only parses/renders a fit-to-content `viewBox`; everything interactive, now including how the viewer's `viewBox` can be overridden, is the module's problem) even though a scale bar is arguably "just display": it's tightly coupled to zoom state that only the module tracks, so splitting it into core would mean core needing to know about zoom anyway.

**Mechanism, without changing core's API:** the module tracks `viewState` (a `{x,y,width,height}` override on top of whatever core just rendered, or `null` to mean "use core's own fit as-is") and `lastCoreFit` (core's own fit-to-content box, read fresh from the live SVG's `viewBox.baseVal` on every render, *before* any override is applied). Comparing this render's fresh fit against the previous one answers "did core actually re-fit the content this time" (e.g. an edit changed the bounding box) versus "core just reused its cached box" (e.g. a drag's `preserveViewBox:true`) — entirely from the DOM, with no core change needed. Content actually re-fitting drops `viewState` back to `null` (matching D-034's existing re-fit-on-edit behavior); an unchanged fit keeps whatever zoom/pan the user had, so a drag or an edit that doesn't move the bounding box doesn't visibly reset the view.

- **Zoom:** mouse wheel over the viewer, zoom-to-cursor (the viewBox point under the pointer stays under the pointer — the behavior every map/canvas tool has already trained people to expect), clamped to 1/8x–2x of `lastCoreFit`'s own size so zoom can't run away in either direction.
- **Pan:** click-drag on empty canvas. A 3px movement threshold distinguishes a pan from a plain click-to-deselect, since both start the same way (`pointerdown` with no `data-id` target).
- **Scale bar:** bottom-right, a bracket shape plus label, picking the largest "nice" round distance (0.1 m … 5000 m) whose current on-screen length is still ≤140px — same idea as a paper map's scale bar. Recomputed on every render, every zoom/pan step, and via a `ResizeObserver` on the viewer pane (so a plain window or pane resize with no render/zoom/pan action still keeps it correct).
- **Fit button:** top-right, resets `viewState` to `null` and reapplies `lastCoreFit` directly — an explicit way back to "core's own fit" beyond just re-triggering a re-fitting edit.

**Bug found while tracing through the design before shipping it (per this project's standing practice of hand-tracing, since no browser execution is available here):** the scale bar and fit button were originally appended to `core.rootEl` (`#plan-root`) exactly once, at module-init time. But every `rerender()` replaces `#plan-root`'s entire `innerHTML` with the freshly-rendered SVG — which destroys *any* existing child of that container, not just old shape markup. That would have destroyed both overlay elements immediately after the very first render, before a user ever saw them, and left them gone for good (nothing re-adds what's already been removed once). Fixed by moving the `appendChild` calls into `handleRendered()` — the module's existing per-render hook — so they run after every render, not just the first; `appendChild` on an already-attached node moves it rather than erroring or duplicating it, so this is safe to call unconditionally on every render.

**Deliberately simplified, not addressed:** zoom/pan state isn't persisted across a page reload (only the plan text is, via D-034's `localStorage` autosave) or across loading a different example/file (a fresh load always shows core's own fit); no distinction between a mouse wheel and a trackpad pinch-to-zoom gesture (both arrive as the same `wheel` event); touch/pointer gestures beyond a single mouse drag (pinch-zoom, two-finger pan) aren't handled.

## D-036 Three drag bugs found from actually using the hosted app

Third round of feedback on the hosted app, all in `interactivity-module.js`. Traced by hand (no browser execution available here), same as every other fix in this project — but this time against real, reported symptoms rather than a design review, so each fix below is a concrete before/after rather than a judgment call.

**1. Polygons/polylines couldn't be dragged at all.** Every shape example in this project's own shipped plans (`grundstueck`'s outline, `rug`, every wall, `stromanschluss`) defines its `points` as references to sibling corner elements (`points: [ecke_1, ecke_2, ...]`, D-018's shared-corner pattern) rather than literal `[x,y]` pairs — and `core.nodeDragEdits` has never generated an edit for that case, only a warning ("endpoint is pinned to X — drag that corner directly"). Dragging the shape itself therefore always produced zero edits and never moved. Fixed with a new `dragEditsFor()` in the module: when a node's `points` reference sibling corners, dragging it now moves every one of those corners by the same delta instead (any literal points mixed in still move directly, as before) — consistent with D-018, since a shape's corners already drive everything else that references them.

**2. Dragging or panning could leave a stray text selection, or trigger the browser's own drag behavior.** `handlePointerDown` never called `e.preventDefault()`, so a plain mousedown-and-move over the SVG was, as far as the browser could tell, indistinguishable from starting a native text selection — every drag or pan gesture risked leaving a blue selection highlight across the page alongside (or instead of) the intended plan interaction. Fixed with `e.preventDefault()` at the top of `handlePointerDown`, plus `user-select: none` on `#plan-root` as a second line of defense.

**3. A child connected to its own structural parent moved at the wrong rate (e.g. roughly double) when the parent was dragged.** Structural nesting already carries a moved parent's shift to every descendant for free — `computePositions` resolves a child's position relative to its parent's, recursively, so nothing needs to touch the child's own source text at all. But `connection` is *also* how this language lets a child stay attached to its own parent (D-013/014's whole reason for existing, e.g. a wall-mounted point that must stay flush) — a reasonable thing to add on top of nesting for reinforcement, or by habit. When both existed for the same pair, dragging the parent applied the shift twice: once for free through the nesting, and once more explicitly through the `connection` propagation loop in `applyDrag`, which had no idea the "connected" node was already being carried along. Fixed by skipping any connected node in that loop that's a structural ancestor or descendant of the node actually being dragged (`isAncestorOf()`), in either direction — nesting alone already moves it correctly; the connection no longer double-counts.

**Not the same bug, still open:** a *shape-only* container — an element with no `position` of its own, positioned purely by its `points` (e.g. `grundstueck`) — still doesn't give its own children any translation to inherit: `computePositions` falls back to `[0,0]` for a missing `position`, so a child nested inside such a shape sits in raw world coordinates regardless of where the shape's own points currently are. Fix 1 above makes dragging that shape's outline work; it does not make the shape's own children follow it. Neither shipped example currently nests a real child under a points-only container (`grundstueck`'s children are positioned independently already), so this hasn't been confirmed as the reported symptom — flagging it here since it's a real, adjacent gap the tracing above surfaced, not a fix.

**Correction to fix 1 — it wasn't actually complete.** Reported still broken after the above shipped. The real remaining cause: moving every corner of a shape by the same delta means calling `core.nodeDragEdits` once per corner, and *each* of those calls independently runs core's own realism check (`checkRealism`, D-020/F-004) against a snapshot where every *other* corner is still at its old position — which, with both shipped examples setting `allowSelfIntersectingPolygons: false`, reads as the shape violently deforming on almost any real drag and gets rejected, even though a pure rigid translation of every one of a shape's own points can never actually change whether it self-intersects (translation preserves every pairwise distance and angle). Fixed with `wouldSelfIntersect()`: before generating any edits, the module now computes where *all* of a dragged shape's corners would end up together and checks the real, fully-translated result once — for the shape's own corners this now always passes, as it should; a *different* shape that happens to share one of those corners without moving along with the rest of it is still correctly checked against what actually happens to it, since that really would be a deformation. The per-corner `nodeDragEdits` calls that then generate the actual edits run against a locally relaxed copy of `base.settings` (this drag frame's own throwaway parse, discarded afterward) so core's now-redundant one-at-a-time check doesn't re-reject what's already been validated correctly. Required exposing `polygonSelfIntersects` on `window.PlanCore` — the one addition to the module API surface this fix needed (see [modules.md](../documentation/modules.md)).

## D-037 Viewer fills the pane; status messages overlay it instead of reserving a row

Fourth round of feedback: the viewer pane was visibly shorter than the code textarea beside it, and parse errors lived in a fixed status row below the viewer.

**Root cause of the height mismatch:** `.status` (holding `#error`/`#dragmsg`/`#modlog`) was a normal, in-flow flex child of `.viewer-pane`, sitting below `#plan-root` — and its children each carried a `min-height` so the row reserved visual space even while completely empty (the overwhelmingly common case). The textarea beside it has no such sibling eating into its height, so it always ran the pane's full height while the viewer never did.

**Fix:** `#error`/`#dragmsg`/`#modlog` moved into `.status-overlay`, `position: absolute` over `.viewer-pane` rather than a flex sibling of `#plan-root` — so `#plan-root` alone now fills the pane exactly like the textarea does. Each line only renders when it actually has content (`.status-overlay > div:empty { display: none }`), so an idle viewer never loses anything to it, and a shown one appears as a small banner over the plan (opaque background, so it stays legible over the SVG) rather than pushing anything around. Positioned top-left with a capped width to stay clear of the interactivity module's Fit button (top-right, D-035) and above it in stacking order (explicit `z-index`), even though the two live in entirely separate CSS (core's own page styles vs. the module's injected stylesheet) — this only works by coincidence of layout, not a designed contract between them; a future core-owned overlay and a module-owned one could still collide if the module ever anchors something to the same corner.

**The 5-second auto-hide is `#error`-specific, not applied to `#dragmsg`/`#modlog`.** Only errors were asked for. A stale drag warning or module-load message sitting under a banner until the next one replaces it is unchanged, existing behavior — genuinely revisiting whether those should also expire wasn't part of this request, so left alone rather than guessed at. Implemented as a `showError()` helper wrapping `errorEl.textContent` with a `setTimeout` that clears it after 5s, reset on every new error (so a persistently-invalid plan re-shows the banner on every failed edit rather than it flickering) and cleared on a successful parse (so fixing the error doesn't leave a stale timer to clear an already-empty banner later).

## D-038 Per-edge side lengths, global and per-element

Requested directly: side lengths should be showable both plan-wide and per element, with a per-element choice of always-visible vs. hover-only. This is a genuinely new capability, not a variant of an existing one — `dimensions` (D-026) already shows a *whole-shape* computed figure (width × height, diameter), but only for `rect`/`circle`, and language.md already flagged "per-edge lengths... would be a reasonable extension, not built" as a known gap. This closes that gap.

**New element property, `edgeLengths: true`.** Renders one length label per edge, not one figure for the whole shape — the length of each individual wall segment or plot-boundary side, not a single aggregate. Scoped to `rect` (all 4 sides, derived from `size` since a rect has no explicit `points`), `polygon` (every side including the closing edge), and `polyline` (every segment, no closing edge) — not `circle` (no straight edges to measure) and not a shapeless element (nothing to measure). Setting it on an unsupported shape is a silent no-op, matching `dimensions`' own existing precedent on `polygon`/`polyline` rather than introducing validation this language doesn't otherwise have.

**Reuses the existing `show: "always" | "hover"` property (D-026) rather than a second visibility mechanism.** The request's own framing ("bei Objekt entweder immer oder nur bei hover") is exactly D-026's existing enum — inventing a parallel one would violate D-033 principle #2 (one concept, one name) in the other direction, two names for the same idea. Concretely: label, dimensions, and edge lengths for one element now share a single rendered group and a single `data-show` value, so they always appear/hide together — matching the request's granularity (per object, not per property on that object) rather than over-building.

**Also settable plan-wide, as `settings { edgeLengths: true }`, reusing the identical property name at both scopes.** An element's own `edgeLengths` (`true` or `false`) always overrides the plan default when explicitly set; leaving it unset inherits whatever the plan default is. Considered and rejected: a differently-named settings flag (e.g. `showEdgeLengths`) to avoid the two scopes sharing a name — rejected because the two really are the same concept at different scope levels (a plan-wide default vs. a per-element override, the way a CSS property cascades), and D-029/D-033 already went through exactly this reasoning once before renaming `showDimensions` → `dimensions` specifically *because* it wrongly shared the word "show" with the enum property despite meaning something unrelated ("include this at all" vs. "when to reveal it") — reusing that same mistake's shape here, just to keep two scopes textually distinct, would be worse than the collision it avoids. `edgeLengths` at the settings level is a *display default* to opt into, not a check to opt out of like its two settings-block neighbors (`allowCollisions`/`allowSelfIntersectingPolygons`) — a real difference in kind, called out explicitly in [language.md](../documentation/language.md) rather than left for a reader to assume from the shared block.

**Rendering:** each edge's label sits at that edge's own midpoint, nudged a short distance along the edge's normal so it doesn't sit directly on the stroke — lands consistently to one side (inward, for every shipped example's winding direction) rather than a controlled inside/outside choice, since nothing about point ordering is currently tracked as clockwise/counterclockwise on purpose. Demonstrated live on the utility example's `grundstueck` boundary (`show: "hover"`, matching its existing label).

**Revised, requested directly: labels moved outside the shape, reading direction now parallel to each edge.** The initial "inward, whichever side the winding direction happens to land on" placement above was replaced with an actual outward check — for a closed shape (`rect`/`polygon`), each edge's two possible normal directions are compared against `centroid → edge midpoint`, and whichever one points *away* from the centroid is used, so labels land outside regardless of point ordering rather than by winding-direction coincidence (an open `polyline` has no enclosed area to be outside of, so this only applies to the two closed cases). Each label also now carries an SVG `rotate()` matching its own edge's angle, flipped 180° whenever the raw angle would otherwise render the text upside down — parallel to the line and still readable, rather than parallel-but-inverted for roughly half of any shape's edges.

**Status: built**, in `docs/index.html`'s renderer (`edgeLengthsEnabled()`, `edgeLengthLines()`, `renderAnnotation()` extended to accept a list of edge lines alongside its existing single-anchor label/dimensions text). No module/interactivity changes needed — this is pure rendering, orthogonal to drag/selection/connections.

**Superseded by D-039: this logic no longer lives in `docs/index.html`.** All of it (`edgeLengthsEnabled`/`edgeLengthLines`/the label+dimensions+edge-length markup) moved into a new `docs/annotations-module.js`, unchanged in behavior — see D-039 for why and how. This entry's description of *what* the feature does and *why* it's named/scoped the way it is still stands; only *where the code lives* changed.

## D-039 Annotations (label/dimensions/edgeLengths) split into their own module

Asked directly, after discussing it as an open question first rather than being told to build it: should size/label display move out of core into its own module? Recommended yes, for two reasons, both borne out once actually built:

1. **Core is meant to stay minimal (D-011/D-013); annotation display isn't a core-primitive requirement.** `label`/`dimensions`/`edgeLengths` are computed, read-only facts *about* an element's geometry, not needed for Element/Connection to function at all — the same category of thing that justified pulling interactivity out of core in the first place (D-031). Left in core, this is exactly the kind of feature that accretes indefinitely (area, perimeter, angle labels, unit conversions — all plausible future asks) inside a file meant to stay small.
2. **D-024 (embeddability) already wants a mode this split makes possible and a merged module wouldn't:** a read-only embed with no drag/select/connect at all, but that still might want dimension labels (a real-estate listing embed showing room sizes, say). Folding annotations into `interactivity-module.js` would make that combination — display without interactivity — impossible to opt into separately.

**No new core API needed — D-031's existing surface already generalizes to this.** Core's parser never special-cased `label`/`dimensions`/`edgeLengths`/`show` in the first place (`props[key] = parseValue()` accepts any property name); only the *renderer* interpreted them. Moving that interpretation out needed nothing beyond what `docs/interactivity-module.js` was already using: `core.onRendered(cb)` to run after core's own render, `core.computePositions`/`resolvePointAbs` to re-derive each element's absolute geometry, `core.numOf`/`M` to read/scale values the same way core does. This is the same "read the rendered result, layer more SVG on top" pattern the interactivity module already uses for its connect/disconnect icons and scale bar — just the first time it's been used for *display* content instead of *interactive* overlays, which is good evidence the pattern itself generalizes rather than being interactivity-specific.

**A real integration seam found doing this, not obvious in advance:** appending every annotation in one batch at the end of the SVG (the natural first way to write this) silently breaks core's own `svg .obj:hover + .annotation[data-show="hover"]` hover-reveal CSS rule, which depends on an annotation being its shape's *immediate* next DOM sibling — every rendered shape is a flat sibling directly under `<svg>`, not nested per element, so batching the inserts puts every annotation after every shape instead of each one right after its own. Fixed by walking the same tree core rendered and inserting each element's annotation individually via `querySelector('[data-id="…"]')` + `insertAdjacentHTML("afterend", …)`, recreating the exact interleaving core used to produce directly when it rendered shape and annotation together in one pass. Recorded in [modules.md](../documentation/modules.md) as a "known seam" — any future module injecting markup that a core CSS rule expects to be DOM-adjacent has to place it explicitly; nothing makes this automatic.

**Auto-injection (D-034) extended, order made significant.** `docs/`'s `AUTO_MODULES` now lists `["annotations-module.js", "interactivity-module.js"]` — both get declared automatically for any plan missing them, in that order, because `onRendered` callbacks fire in registration order: annotations has to finish inserting its labels *before* interactivity's own icons/scale-bar/fit-button get appended, so those still end up on top, matching the stacking that existed before this split (interactivity's icons were always appended after core's full output, annotations included).

**Status: built.** `docs/annotations-module.js` is a new file; `docs/index.html`'s `renderShape` no longer computes or renders any annotation content at all (dropped `renderAnnotation`/`dimensionText`/`edgeLengthsEnabled`/`edgeLengthLines`/`escapeXml`/`fmtMeters`, and the `settings` parameter threaded through `renderShape` for D-038, since none of it is needed once annotations are entirely module-owned). Behavior is unchanged from the user's perspective — this was a pure architectural move, not a feature or rendering change.

## D-041 Collision checking: built into the interactivity module, not core or a third module

`allowCollisions` (D-020) has existed as a documented setting since early on, flagged as "materially harder" than its self-intersection sibling and left genuinely unimplemented (D-020's own correction, F-004). Picked up now, requested directly, with the architecture question asked and answered before building: **should this live in a module, like D-039 just did for annotations?**

**Answer: yes, but folded into `interactivity-module.js` itself, not a third separate module.** The reasoning that justified splitting annotations out doesn't transfer here. Annotations are pure post-render decoration (D-039's `onRendered` pattern) with a real independent use case — a read-only embed (D-024) wanting dimension labels with no drag at all. Collision checking has no such use case: it only matters at the moment something is *dragged*, to validate a proposed move before committing it — the exact same shape D-036's self-intersection fix (`wouldSelfIntersect`) already took, living inside the same file. A separate "collisions module" would need the in-progress drag's own delta and candidate edits, which are `applyDrag`'s own private state, not anything exposed (or sensibly exposable) via `window.PlanCore` — the module boundary would be artificial, not a real seam.

**No new core API needed** — same as D-039, and for the same underlying reason: `core.computePositions`/`resolvePointAbs` (already exposed for D-031) are sufficient to compute both a sibling's current geometry and the dragged element's proposed geometry. All new geometry code (`polygonsOverlap`, `circlePolygonOverlap`, `pointInPolygon`, etc.) is module-local, mirroring how the module already keeps its own adjacency/contact-point math rather than asking core to expose more primitives than it strictly needs to.

**Scope, settled before writing any code:**
- **Only `rect`/`circle`/`polygon` participate.** `polyline` (walls) and shapeless elements are meant to touch/connect by design (D-014/D-018) — collision-checking those would fight the language's own connection model, not complement it.
- **Siblings only (same direct parent).** Without this, a chair inside a room would permanently "collide" with the room's own boundary — that's containment, a different relationship (D-032, itself still only partially built) this doesn't touch. A real, accepted consequence: two elements in *different* parents that happen to visually overlap are never checked, even if that overlap is real on screen.
- **Zero-tolerance geometry (proper edge crossings, or a point strictly inside the other shape), not an epsilon buffer.** Two shapes resting exactly flush — which D-014's whole adjacency/connection system already treats as a legitimate, common state, not an edge case — read as non-colliding without needing one; only genuine overlapping area counts.
- **A rejected edit** (drag simply doesn't apply, with a message), the same treatment as the self-intersection check — not D-015's warn-and-flag pattern, since (like self-intersection) the system knows exactly what's wrong and a valid state is one cursor-step away. **Superseded almost immediately, see the correction below.**
- **Per-element `allowCollisions: true | false` overrides the plan-wide setting**, identical override shape to D-038's `edgeLengths`: unset inherits the plan default; an explicit value on either side of a pair always wins, since a collision is inherently pairwise — one element not caring is enough to exempt that pair.
- **Only the directly dragged element is checked, not anything moved along with it via a `connection`.** Extending this to a whole propagated group is real future work, not done here — recorded as still-open in F-004 rather than silently out of scope.

**Status: built**, entirely in `docs/interactivity-module.js` (`shapesOverlap`, `solidGeometryFor`, `proposedGeometryFor`, `collidesWithAnySibling`/`clampToNoCollision`, wired into `applyDrag` before any edits are computed). No changes to `docs/index.html` or `window.PlanCore` at all.

**Correction, reported from actual use as "laggy," then narrowed to "unintuitive — every direction gets blocked":** a hard reject on the full attempted `(dx, dy)` was the wrong shape for this specific check, unlike self-intersection where the same pattern is fine. `dx`/`dy` are cumulative from the drag gesture's original mousedown point, not incremental frame deltas (the whole codebase re-derives every drag frame from the pristine pre-drag source text, to avoid drift) — so rejecting the whole move outright freezes the shape wherever it last fit while the mouse cursor keeps drifting arbitrarily far past that point. Every direction then reads as "blocked," because a small mouse movement right after getting stuck barely changes the *total* delta from the original start, which is still deep in colliding territory.

First fix: clamp instead of reject — scale the whole `(dx, dy)` vector down by the largest shared factor `t ∈ [0,1]` that doesn't collide. This unstuck most directions, but introduced a second, immediately-reported problem: **movement no longer tracked the cursor even in directions that weren't blocked.** Pushing into a wall while also trying to slide alongside it (the ordinary way to get past an obstacle) throttled the *sliding* axis down to the same shared factor as the *blocked* axis — sliding sideways along a wall moved at only a fraction of the mouse's own sideways speed, since one shared `t` was solving for both axes' collision simultaneously.

Second fix, replacing the shared-factor scale: **resolve X and Y independently**, the standard "slide along the wall" collision response — X is only clamped at all if moving in X *alone* (Y held at zero) would itself collide; Y is then resolved the same way, holding X at whatever it just ended up at. An axis the obstacle doesn't actually block is left completely unscaled, so it stays exactly in sync with the cursor, while the blocked axis alone gets binary-searched down to the boundary.

**Third correction, reported next: still couldn't slide along a circle or a polygon's diagonal edge.** The X/Y-separated fix above only produces real sliding when the obstacle's own boundary happens to run parallel to an axis — true for a rect's straight walls, never true for a circle's curve or a polygon edge that isn't axis-aligned (e.g. the utility example's plot boundary). Replaced with a general version: binary-search the point along the attempted straight-line move where collision first begins (same idea as the very first, since-abandoned uniform-scale fix, but now only used to *locate* the contact point, not to scale the whole move), then slide the *remaining* attempted movement along the tangent of whatever was hit there — a circle's radial direction at the contact point, or a rect/polygon's nearest-edge normal (`contactNormal()`), oriented outward from that shape's own centroid so it points the right way regardless of the point list's winding. This reduces to exactly the X/Y-separated behavior for a rect wall (its nearest-edge normal *is* an axis-aligned unit vector), so it's a strict generalization, not a rewrite that risks the already-working case. A second, smaller clamp catches the case where the straight-line tangent step itself curves back into the same obstacle (a large slide along a tight circle, say) — re-clamped the same way as the main move rather than assumed always safe.

**Fourth correction, requested directly: `allowCollisions` should default to off (collisions allowed), not on.** Unlike its settings-block neighbor `allowSelfIntersectingPolygons`, silently blocking every geometric overlap by default breaks a common, legitimate authoring pattern this language has no other way to express — a rug positioned under a table, artwork over a wall, anything meant to visually sit on top of something else. `collisionsAllowedFor()` now returns `settings.allowCollisions !== false` instead of `!!settings.allowCollisions` — unset (or explicit `true`) means allowed/checking-off; only an explicit `allowCollisions: false` (plan-wide or per element) turns checking on. This makes collision checking and self-intersection checking opposite defaults on purpose, not an oversight — they're genuinely different in kind (D-041's own scope note already said as much: "not a check to opt out of, but a display default to opt into" was `edgeLengths`' framing, and collision checking turns out to belong on that same "opt-in" side, not alongside `allowSelfIntersectingPolygons`).

**Status: paused here, not fully working.** After four rounds of fixes (reject → uniform-scale clamp → X/Y-separated clamp → general surface-normal slide, plus the default flip above), sliding against a circle or a polygon edge is still reported as imperfect — the user's own words, "funktioniert noch nicht perfekt" — and the session stopped there rather than continuing to iterate blind. No specific remaining symptom was captured before stopping, so the exact gap isn't documented beyond "not fully working" — likely candidates, unconfirmed: the single-tangent-step approximation only re-clamps once if it curves back into the *same* obstacle (a tight circle or sharp polygon corner could plausibly need more than one iteration within a single frame to settle correctly); the contact-point binary search and the tangent are both computed once per frame from the drag's fixed original start, not re-solved iteratively toward the actual mouse position, so a fast mouse movement across a curved boundary may not track as smoothly as a straight wall does. Pick this back up by asking for a concrete repro (which shape, which direction, what it does instead of what's expected) rather than re-guessing from this list.

**Prototype 16 hit the same corner-normal instability, confirming the diagnosis above wasn't specific to collision-checking.** Reported as the sofa "springt manchmal" (jumps sometimes), then confirmed with a screenshot showing the sofa sitting mostly *outside* the room's top-left corner while the status line still said "stays inside" — not just a jump, an actually wrong, still-escaping result. First attempt: iterate the boundary-then-slide step a few times, each pass starting from the previous one's own result, hoping repetition would converge toward the corner. The screenshot showed this wasn't enough, and pointed at the real bug: the tangent is built from the nearest parent edge *to the child's own center*, not from whichever corner of the child is actually escaping — at a room corner, the child's center can stay fully inside the parent while one of its actual corners pokes out, so the computed slide direction has nothing to do with the violation that's really happening.

**Root-caused, not just mitigated: added an exact, closed-form clamp for the specific case this prototype actually tests — an axis-aligned rect child inside an axis-aligned rect parent.** `clampRectToStayInsideRect()` clamps each axis completely independently against the parent's own bounds (`Math.min(Math.max(target, parentMin), parentMax - childSize)` per axis) — no binary search, no tangent, nothing that can misfire at a corner, because a corner isn't a special case here at all: it's just both axes landing at their own clamp simultaneously. This is exact, not an approximation, for two axis-aligned rects specifically. The general nearest-edge/tangent-slide approach (`clampToStayInside`, still iterated) is kept only as the fallback for a circle/polygon parent, where no equally simple exact alternative exists — that path remains genuinely unvalidated, unlike the now-fixed rect/rect case.

**Separately, a real bug found while testing this prototype: the core renderer's auto-fit viewBox only ever considered each node's own reference point, never its actual size.** `render()`'s fit-box computed `min`/`max` purely from `positions` (a rect's top-left, a polygon's own — often irrelevant — anchor), with a circle-radius special case bolted on but nothing for a rect's `size` or a polygon/polyline's `points`. Every shipped example happens to also declare explicit corner-anchor child elements (D-018's shared corners) whose own positions coincidentally span the room's full extent, which is the only reason this was never noticed — Prototype 16's room has no such children, and rendered into a box roughly a third the room's actual size. **This is a real, unnoticed production bug, not just a prototype issue**: `docs/`'s own "Blank" example (a lone rect, no children at all) hits the exact same case and was rendering cut off on the live site. Fixed in both places: the fit-box now also expands over each rect's own `bboxes` entry (already computed by `renderShape`, just never consulted here) and each polygon/polyline's resolved `points`, not only every node's bare reference point.

**Fifth correction, prompted by revisiting Prototype 16's fix above: reverted the general tangent-slide approach back to X/Y-axis-separated clamping.** The tangent-slide version (fourth correction) was built to generalize past axis-aligned walls, but Prototype 16's own corner bug showed the *specific* weakness in that family of approach — a contact normal/tangent is only well-defined relative to a single chosen blocker, and near a corner (or between two nearby obstacles) which blocker gets chosen can flip discontinuously, producing exactly the instability both D-041 and the prototype independently hit. Re-examined: the X/Y-separated version isn't actually an *approximation* for the common case (rect furniture against rect furniture) — it's exact, and identical to sliding along the wall, because a rect's own boundary is never anything but horizontal or vertical; the axis decomposition it does isn't a simplification there, it's precisely what "slide along this wall" means. It's also exact for *any number* of simultaneous colliding siblings, since the same `collides()` predicate checks all of them together, unlike a tangent computed against one chosen blocker. The tradeoff, unchanged and honestly still a limitation: against a circle or a diagonal polygon edge, it stays *safe* (never lets an overlap through) but doesn't track the boundary as smoothly as a true tangent would — accepted, not solved, matching the prototype's own containment fallback for a circle/polygon parent.

**Status revised: exact and validated for the common rect-vs-rect case (the D-041 v. tangent-slide instability this decision spent four corrections chasing doesn't apply to it), still an accepted, un-smoothed limitation for circle/polygon blockers.** `contactNormal`/`shapeCenter`/`polygonCentroid` removed as dead code along with the tangent-slide version they only existed for.

## D-042 Code highlighting: syntax colors and selected-element marking, a third module

Requested directly, with the "should this be a module?" question already applying the same framework as D-039/D-041: syntax coloring has no interactivity dependency at all (a pure display feature of the code pane), a clean case for a separate module — but marking the *selected* element's own span needs `interactivity-module.js`'s `selectedId`, which only that module owns. Since both features need the *same* DOM overlay (see below), splitting them into two separate modules each trying to manage it independently would conflict; built as one module, `docs/code-highlight-module.js`, covering both.

**No new core API shaped specifically for this — the same story both prior modules already established.** `tokenize()` already existed inside core, purely for `parse()`'s own use; exposing it on `window.PlanCore` (alongside `parse`/`render`/`polygonSelfIntersects`) was the only core change needed. For the selection signal, rather than growing `PlanCore` with something selection-specific (selection is squarely `interactivity-module.js`'s own concern, not core's), `interactivity-module.js` got one line added to its already-existing per-render logic: alongside the `.selected` CSS class it already applies, it now also sets `core.rootEl.dataset.selectedId` — a loose, optional signal any other module can read, with `interactivity-module.js` having no idea whether anything is listening.

**Mechanism: an invisible `<textarea>` over a colored `<pre>` backdrop, not a code-editor dependency.** A plain textarea can't color individual characters. Rather than reaching for CodeMirror/Monaco (breaking D-034's "zero dependencies, plain static files" scope for the first time), this uses the standard lightweight alternative: the real, fully native textarea (typing, caret, undo, native selection — all untouched) gets its text made transparent and is layered on top of a `<pre>` rendering the same text with colored `<span>`s, kept in exact pixel sync (scroll position, font, padding, border — read from the textarea's own computed style rather than copied by hand, so they can't silently drift out of sync with `docs/index.html`'s CSS later). The textarea itself is never replaced, only moved into a new wrapper alongside the backdrop, so every other module's reference to `core.sourceEl` and every listener already on it keep working.

**A real bug caught before it shipped, not after: copying `getComputedStyle(textarea).height` for the new wrapper would have frozen it at whatever pixel height the page happened to be on module load**, no longer tracking `.layout`'s real height (and so the viewer pane beside it) across a later window resize — `flex: 0 0 420px` resolves to a fixed pixel value either way so was fine to copy computed, but `height: 100%` is meant to stay relative; caught while reviewing the draft and fixed by keeping the wrapper's height a literal `"100%"` instead of the resolved value.

**A second real bug, this one from testing the auto-injection this module needed to join:** `docs/`'s own `AUTO_MODULES` order requires code-highlight to load *after* interactivity (it reads interactivity's selection signal) — but `docs/`'s `utility` example already explicitly declared `module "interactivity-module.js"` on its own (a leftover from before D-034's auto-injection existed), and `loadPlan()` only ever *prepends* whatever's missing — meaning annotations and code-highlight would land ahead of that existing declaration, code-highlight now loading *before* interactivity, backward. Fixed by removing `utility`'s now-redundant explicit declaration entirely, letting all three auto-inject consistently like the other two examples, rather than teaching the injector to interleave with a partially-declared list. Documented in [modules.md](../documentation/modules.md) as a real limit of the auto-injection mechanism: it only produces the intended order when a plan declares none of the three itself.

**Status: built.** `docs/code-highlight-module.js` is a new file; `docs/index.html` gained `tokenize` on `window.PlanCore` and a third `AUTO_MODULES` entry; `interactivity-module.js` gained the one-line `dataset.selectedId` signal (and its own cleanup for it). No changes to the plan language or the parser's grammar — purely an editor-chrome feature.

**Correction, reported immediately after shipping: syntax colors worked, the selection highlight didn't.** Static re-reading of `onRendered`'s registration order, the signal-setting code, and the highlight-rendering logic didn't turn up a conclusive bug — plausible but unconfirmed candidates were a genuine ordering issue between the two modules' `onRendered` callbacks, or the highlight color (`#fff3b0` on whatever showed through the wrap's transparent background, which turned out to be `docs/index.html`'s own page background, not white) simply being too low-contrast to notice. Rather than keep guessing at a single root cause with no way to execute and observe the actual DOM here, made the design more robust on both fronts at once: the wrap now has an explicit white background instead of relying on transparency-through-to-the-page, the highlight color is more saturated with its own outline, and — the more structural fix — the module now also reacts to `core.rootEl`'s `data-selected-id` attribute directly via a `MutationObserver`, rather than depending solely on its own `onRendered` callback having fired after `interactivity-module.js`'s. Whichever of the original candidates was the actual cause, watching the attribute directly removes the dependency on an inter-module ordering assumption entirely, which is a better design regardless.

**Also added, requested directly: scrolling the code pane to bring the selected element's span into view**, not just marking it. Guarded to fire once per *selection change*, not once per render — a drag's own repeated re-renders reach the same code path, and scrolling unconditionally there would yank the code pane's position on every drag frame of an already-selected element.

**The scroll itself then reported not to work, even though nothing wrong turned up reviewing the math.** First attempt hand-computed the target `scrollTop` from the highlight span's own `offsetTop`/`offsetHeight`. The likely culprit, unconfirmed but consistent with the symptom: a selected element's span is a *multi-line* inline `<span>` (a whole `element foo { ... }` block spans several source lines) — `offsetHeight` on a multi-line inline element is inconsistently defined across browsers, typically describing only one line box rather than the element's true extent, which would make an "is this in view" check unreliable. Replaced with `marked.scrollIntoView({ block: "center" })`, delegating the actual visibility/positioning geometry to the browser instead of re-deriving it — it scrolls `backdrop` (the nearest positioned ancestor scrollIntoView finds), read back onto `textarea` afterward, the reverse direction of every other sync in this module.

**Separately, unrelated to D-042 but reported in the same round: the *viewer's own* selection indicator — pre-existing since D-030/D-031, never previously examined — had the same class of bug the collision-clamp work kept running into: a value that doesn't scale with the thing it's modifying.** `svg .obj.selected { stroke-width: 3px !important; }` set an *absolute* stroke width regardless of the shape's own — a wall already stroked thicker than 3px (a plausible, common case: several shipped examples use 0.06–0.1m strokes, 3.6–6px at this app's scale) actually looked *thinner* once selected, the opposite of what a selection indicator should do. Fixed by switching to the same `filter: drop-shadow(...)` glow technique already used for hover and `connected-highlight` just above it in the same stylesheet, in its own color (`#7c3aed`, distinct from hover's `#37f` and connected's `#e80`) — a glow never touches `stroke-width` at all, so it reads consistently no matter how thick or thin the shape's own stroke already is. Sized to match hover's own 2px exactly (was 3px), on request, once it was confirmed the glow itself never touched `stroke-width` — a glow's blur can still visually *read* as thickening even though it isn't one, which was worth asking directly about rather than assuming the technical fix alone settled the visual question.

**Two more corrections, both requested directly after using the shipped highlight:**
- **The code-side selection background showed a faint seam around every separate word.** The original implementation put a `tok-selected` class directly on each individual token/gap `<span>` within the selection — syntactically reasonable, but many adjacent inline elements each painting their own identical background color show a visible seam at the boundary between them, a real rendering artifact, not a styling choice (softening the color, tried first, didn't remove it since the seam is structural, not a contrast issue). Fixed by separating concerns: `colorRange()` now renders ordinary syntax coloring with no selection awareness at all, and `renderHighlighted()` wraps each selected range in exactly one outer `tok-selected` span around that coloring — one background-painting element per range instead of dozens, nothing left for a seam to form between.
- **Selecting a parent element marked its children's own text too, since a parent's raw `[start, end)` span textually contains every child's own declaration.** `ownRanges()` walks a node's direct children (already in source order from parsing) and returns the gaps between them instead of the raw full span — before the first child, between each pair, after the last — so a parent selection now marks only its own properties/braces, never a nested child's own block. A leaf element is the degenerate case (no children → one range → its full span, unchanged from before this existed). This also fixed the seam-around-every-word case incidentally for parents specifically, since `renderHighlighted()` was reworked for both fixes together — but the seam existed for leaf elements too and needed its own fix regardless.

## D-044 D-032's "inside" containment mode, promoted from Prototype 16 into the live product

The direct follow-up after D-043: with the multi-plan gap closed, [project-overview.md](project-overview.md)'s other flagged item was that D-032's mode 3 ("inside") was validated standalone in [Prototypes/16-parent-child-placement/](../Prototypes/16-parent-child-placement/) but never wired into `docs/` — a concrete, already-validated gap, chosen over starting something more exploratory (F-002's untested module-composition promise) precisely because it closes an existing gap rather than opening a new one.

**Wired in as a second constraint alongside D-041's collision clamp, not a replacement for it.** `applyDrag`'s existing "checked before any edits, clamps dx/dy in place" block (previously collision-only) now runs `clampToNoCollision` then `clampToContainment` in sequence on the same delta. This is a heuristic, not a jointly-solved optimum — F-004's existing "multiple simultaneous constraints on one element are unhandled" gap now technically covers this pairing too — but since each clamp only ever shrinks the attempted move, never grows it, running both in either order still lands somewhere both agree is safe, just not necessarily the exact same point a true joint solve would find. Both checks share the same collision-section helpers (`pointInPolygon`, `pointToSegmentDistance`, `rectCorners`, `solidGeometryFor`) rather than duplicating them — the one thing the standalone prototype file, with everything copied verbatim into one page, couldn't do.

**One behavioral refinement beyond a direct port: a node that only *inherited* `"inside"` from its parent's `childPlacement` default, but isn't itself a `rect`, is silently left unconstrained rather than warned about.** Prototype 16 never had to face this, since its own test plan had no non-rect children under a `childPlacement`-bearing parent. The live product's shipped `apartment` example does — walls (corner-ref polylines), `rug` (a polygon), and `side_table` (a circle) all sit inside `room`, which now sets `childPlacement: "inside"`. Warning on every drag of any of those (as a naive direct port would, via the prototype's `else` branch pushing a warning whenever the shape isn't a rect) would mean a constant, un-actionable message on ordinary furniture drags — `childPlacement` is an ambient default, not a specific promise about every child, so an unsupported shape silently opts out of it. **Demonstrated live:** `docs/`'s `apartment` example's `room` now sets `childPlacement: "inside"` — `bed`/`desk`/`stove`/`counter` (all rects, all already positioned within bounds, so no visible change on load) are now clamped to stay inside the room when dragged; `rug`/`side_table`/the walls are unaffected, per the scoping above.

**Status: built**, closing F-001's "D-032's 'inside' mode hasn't been touched at all" note (see D-032's own status note, now superseded by this entry). Still not built: `flush` (the door-in-wall addition), containment for an element moved along by a `connection` rather than dragged directly (F-004's existing gap, now shared by both checks), and any parser-level validation of `placement`/`childPlacement` values (an unrecognized string is silently treated as "not \"inside\"," same as an absent one — matching this language's general lack of property-value validation elsewhere). Not yet tested in a real browser, same caveat as D-043 — verified by hand-tracing and re-reading the modified file, consistent with this project's standing practice with no execution environment available here.

**Confirmed working in a real browser** shortly after shipping — the first genuine runtime verification this session (D-043 through this entry were all hand-traced only, see [project-overview.md](project-overview.md)'s risk assessment). Reported back as "pretty good," some minor unspecified issues noted but deliberately set aside rather than detailed yet.

## D-045 A confirmation gate before loading an untrusted external module

Requested directly, as the concrete follow-up to [project-overview.md](project-overview.md)'s risk assessment: risk #2 there named live, unsandboxed external module loading (`docs/index.html`'s `loadExternalScript`, reachable from any plan's own `module "url"` declaration, with D-003's actual workflow being a human pasting AI-generated plan text they haven't necessarily audited line-by-line) as the next thing worth an explicit decision rather than staying an open question (F-009) indefinitely on a live, public URL. Agreed scope: a small, cheap mitigation, not a sandbox — moving the behavior from "runs automatically" to "a deliberate per-URL choice," nothing more.

**Mechanism:** `ensureModulesLoaded()` now calls `isTrustedModule(name)` — true only for the three modules this app ships and auto-injects itself (`AUTO_MODULES`, whether a plan got them via auto-injection or wrote them out explicitly by name; those run with the same trust as core) — before fetching anything URL-like. Anything else triggers a native `confirm()` naming the exact URL, once per session per module name (reusing the existing `loadedExternal` dedup for the accept path). Declining throws, same as any other unresolved parse/render error (D-015): the plan doesn't render past that point and the error banner names why, rather than silently degrading or silently loading anyway.

**A real bug caught before it shipped, not after — same "trace before trusting" practice this project has followed throughout.** A first draft only tracked *accepted* modules (`loadedExternal`), not declined ones. Since `rerender()` re-runs `ensureModulesLoaded()` on every single keystroke (any edit triggers a rerender, D-034), and a declined module is never added to `loadedExternal`, that draft would have re-shown the native `confirm()` dialog on *every subsequent keystroke* anywhere in the plan for as long as the declined module's declaration stayed in the text — not a one-time question but a nagging loop, likely bad enough that a browser would start throttling/blocking the repeated dialogs outright. Fixed with a second set, `declinedExternal`: a declined module stays declined (throwing without re-prompting) until its declaration is actually removed from the plan and re-added (`deactivateRemovedModules` already clears per-module state when a name drops out of the current module list — extended to clear this too) or the page reloads (all these sets are in-memory, session-only, by design — matching `loadedExternal`'s own existing lifetime).

**Explicitly not attempted:** an actual sandbox (iframe/worker isolation), a persistent cross-session allowlist, or any change to what a module can *do* once accepted — accepted code still runs with full, unrestricted page access, exactly as before. This narrows *whether the user was asked*, not *what they're exposed to once they say yes* — the same distinction F-009's own "gate behind login + opt-in" option already drew, just applied without needing accounts/profiles to exist first (D-019 remains undecided-and-unbuilt either way).

**Status: built.** `docs/index.html` gained `isTrustedModule`, the `confirm()` gate, and `declinedExternal`; `documentation/modules.md`'s "Trust model" section updated to describe it (and a stale reference to the pre-D-043 `loadPlan()` function, found while editing the same section, corrected to `withAutoModules()` in passing). No change to the module API surface (`window.PlanCore`) or to any shipped module. Not yet tested in a real browser — same standing caveat as every change this session; the mechanism depends on the browser's own `confirm()` semantics (synchronous, blocks the calling script) holding as assumed.

## D-046 F-002's third module promise, finally tested: module-provided compositions

With D-044 having closed F-001's last concrete gap and D-045 giving F-009 a first mitigation, the next step per [project-overview.md](project-overview.md)'s own recommendation chain — and per `open-questions.md`'s standing priority note ("F-001 and F-002 next, before further infrastructure decisions") — was F-002's own last untested claim: D-011 says modules can add "new reusable, higher-level compositions built from Element and Connection (e.g. a 'wall with a door' building block)," and [language.md](../documentation/language.md) has used exactly that example illustratively since it was written — but nothing had ever actually attempted it. Chosen over jumping straight to a real backend prototype, matching this project's own repeated practice: validate the concept question a throwaway prototype can answer cheaply before spending effort on infrastructure decisions that only make sense once it's settled.

**Built as [Prototypes/17-module-composition/](../Prototypes/17-module-composition/), same throwaway-first pattern as every other core mechanic.** `wall-with-door-module.js` lets a plan write one compact element — `element w { compose: "wallWithDoor", from: [x,y], to: [x,y], doorAt: <m>, doorWidth: <m> }` — instead of manually authoring the four corner elements plus three polylines D-018's shared-corner pattern currently requires for the same visual (exactly what every shipped wall/door in `docs/`'s `apartment` example does today, by hand). The module computes the door's start/end points along the wall and pushes three ordinary `polyline` child nodes (wall segment, door, wall segment) onto the composite element's own `children` array — using literal `[x,y]` points, the same shape a hand-authored element would use, nothing composition-specific about the generated data itself.

**The one thing this actually needed from core, and the answer to F-002's "what does the module API expose" question for this third promise specifically: a pre-render tree-transform hook.** Every existing module hook (`onRendered`, D-039/D-042) runs *after* core has already rendered — fine for adding overlays, useless for a module that needs to inject new nodes the renderer itself should treat as first-class. Added `core.registerBeforeRender(cb)`: every registered callback runs, in registration order, on the freshly-parsed tree before `render()` sees it, free to mutate `node.children`. Once that one hook existed, rendering needed *zero* composition-specific code at all — `render()`/`renderShape()` are completely unaware `compose` exists; the synthesized nodes flow through the exact same code path a hand-typed element would. Beyond that hook, the module needed nothing else from core except `numOf` (already existed, exposed since D-008). A real, if narrow, confirmation that D-011's third promise is achievable with a small, targeted addition to the module API surface — not a sign core needs to grow a general "plugin" system.

**A genuine, not-yet-solved limitation surfaced by actually building this, not assumed going in: drag-editability of a synthesized child isn't free.** D-009 requires every visual element to be representable and editable via drag-and-drop — but a synthesized `wall_a` segment has no source-text span to write an edit back to (D-012's `nodeDragEdits` machinery rewrites a literal's `start`/`end` character range in the source; a computed point was never typed at all). Dragging one would need to solve backward into the *composite's own* `from`/`to`/`doorAt`/`doorWidth` parameters instead — a per-composition-type backward-solve, genuinely more than D-012's existing generic "invert a linear expression" solving covers, and untried here. Deliberately left unattempted (matching Prototype 12's own "rendering first, interactivity is a separate, later question" precedent) rather than guessed at — flagged as a real, specific new question this test exists to have found, not a gap in scope-setting.

**Also not attempted, both flagged rather than silently assumed away:** the composite's own `position` doesn't offset its synthesized children's coordinates (from/to are treated as already being in the composite's parent-local space) — solvable, just orthogonal to the question being tested; and dynamic loading of the module via a plan's own `module "..."` declaration wasn't re-tested here, since Prototypes 12/14 already validated that mechanism — this prototype loads its one module via a plain `<script>` tag to keep the test focused purely on the new hook.

**Status: prototype only, not wired into `docs/`.** Confirms F-002's third promise is achievable for the rendering half with a small, well-scoped core addition (one hook); the drag-editability half is now a known, real, separate open question rather than an unexamined assumption. **Confirmed working in a real browser** — both walls render correctly with their doors, matching the hand-traced composition math.

## D-048 The actual deployment: PHP/MySQL on the real target server, not Node — found and fixed live, not planned

D-047 ended with deployment blocked on what looked like this session's own environment refusing outbound SSH. That conclusion turned out to be wrong, discovered by actually working through it rather than accepting the first plausible explanation — a real example of this project's standing practice (trace before trusting) applied to infrastructure, not just code.

**What actually blocked the first SSH attempt, in order:** (1) the connection info shown gave port 22, but the account's real SSH port — visible only inside the hosting portal's own "SSH-Zugang" panel, alongside the connection info box that still just said "22" — is a non-standard `52839`; (2) the account sits behind an IP-allowlist firewall requiring the connecting IP to be explicitly authorized first, which this session's own IP obviously never was. Both were fixable once found: this session's public IP (fetched via `ipify.org`/`ifconfig.me`, both IPv4 and IPv6 given to cover either) was allowlisted, and a freshly-generated SSH keypair's public half was authorized through the same panel — never a password typed into this conversation, the safer path already decided in D-045's spirit of not putting secrets in chat history. Connecting on port 52839 with the new key worked immediately.

**Once connected, a second, more fundamental finding: this hosting's SSH account is not a general-purpose Linux shell.** `node`, `which`, `ps`, `uname`, `df`, and `ldd` are all missing; `$PATH` covers only `/usr/local/bin:/usr/bin:/bin:/usr/games`. A portable Node.js v24.20.0 LTS tarball (the current LTS, fetched via `nodejs.org/dist/index.json` to confirm rather than guessing a version) was downloaded and extracted successfully — `curl`/`wget`/`tar` all work, outbound HTTPS works, disk quota is ample (10GB) — but the extracted `node` binary failed with `error while loading shared libraries: libdl.so.2: cannot open shared object file`. Investigating further: `/lib64` contains only `ld-linux-x86-64.so.2`, the dynamic linker itself — not `libc.so.6`, the C library every dynamically-linked binary needs. This SSH account is a deliberately minimal jail meant for file management and running the specific tools the hosting provider whitelisted (`composer`, `wp`-CLI, `git` presumably) — not a general execution environment. No Node.js version, howsoever obtained, can run there. This is a harder, more specific finding than "the Node.js extension isn't enabled" (D-047's assumption) — it's that the underlying shell genuinely cannot execute arbitrary compiled software at all. The downloaded tarball was deleted afterward, leaving no trace on the account.

**Confirmed real, via the same shell: PHP 8.5.5 is the account's actual native runtime**, with `pdo_mysql`, `pdo_sqlite`, `mysqli`, and a working `mysql` CLI client all present — this is what the hosting is actually built for (also evidenced by the one-click WordPress installer noted earlier, and Plesk's own `wp`/`composer` tooling visible in the account). Directly asked whether to keep pursuing Node hosting (a support ticket, or a separate VPS) or pivot the implementation to match what this hosting can run — see the discussion below on why PHP was chosen over both alternatives.

**Before rewriting anything: why deploy at all, revisited.** Asked directly why any of this backend work is needed, given none of the three core aims (code/plan sync, the purpose-built language, module extensibility) depend on it — the honest answer is that D-021's entire value is cross-device access to saved plans, a convenience nobody has yet concretely needed, not a blocker for anything else this project does. Surfaced explicitly rather than plowed past. The practical push to keep going came from already being partway through, with working infrastructure in hand (the hosting account, now with verified SSH access) — not a rediscovered urgency. Recorded here so a future reader knows this was a deliberate "we're already here, might as well finish this piece" choice, not evidence the backend became suddenly necessary.

**Also considered and rejected, asked directly: storing plans inside WordPress itself** (a custom plugin/post-type, avoiding a second implementation entirely) — this is exactly what D-021's own original reasoning already rejected, and re-examining it against the new hosting information didn't change the underlying argument: D-019 keeps WordPress core-only specifically so its strong auto-update track record isn't diluted by custom code nobody but this project maintains; a plan-storage plugin would need exactly the same ongoing security maintenance as a separate service, but with a strictly worse blast radius — a bug in it sits in the same database as user credentials, rather than in an isolated one. The hosting friction made the *convenience* of "just use WordPress for everything" more tempting, but didn't change why D-021 separated the two in the first place.

**Chosen instead: rewrite the storage service in PHP against a real MySQL database** (created via the hosting portal's own "Datenbanken" feature) rather than provisioning a separate VPS for Node. Keeps D-021's actual point — plan storage isolated from WordPress's own database and auth logic — while running on infrastructure already available, at the cost of a second backend language existing in the project for the first time (previously: zero backend code at all, so this is a first, not a regression from some prior one-language state). [storage-service/](../storage-service/) (Node) stays in the repo as a design reference for a future VPS scenario; [storage-service-php/](../storage-service-php/) is what's actually live.

**Built: same API contract, same session-token flow, same stubbed-auth swap point as the Node version** — `POST /session`, `GET/POST/PUT/DELETE /plans` (query-string routed, `?id=...`, deliberately not path-based, to avoid depending on `mod_rewrite` being configured at all for the *routing* itself — see the header finding below for where a `mod_rewrite` dependency turned out to be unavoidable anyway). Session tokens are hand-rolled HMAC-SHA256 (`hash_hmac`/`hash_equals`), not a JWT library — no Composer dependency needed for something this size, and supporting exactly one algorithm with no "alg" field to negotiate at all sidesteps a known class of real JWT implementation bugs by construction. `verify_credentials()` is stubbed identically to the Node version, with the real WordPress REST API call written out as a comment at the exact swap point.

**First tried SQLite (zero provisioning, matching the Node version's own choice), switched to MySQL on request.** The practical reason: this hosting's automatic backup coverage is understood to apply to its provisioned databases, not necessarily to an arbitrary file sitting in a webspace — a real, concrete point in MySQL's favor once actually weighed, not just "more standard." The switch touched exactly one file (`app/src/db.php`); every other file only ever talks to PDO through plain prepared statements, which was the actual point of isolating the connection there.

**Two real deployment bugs found only by testing against the live server, neither visible from code review alone:**
1. **`db_host: "localhost"` failed** with `SQLSTATE[HY000] [2002] No such file or directory` — PDO/mysqli treat the literal string `"localhost"` as a signal to connect via a Unix socket, and this hosting's actual socket path doesn't match PHP's compiled-in default. `"127.0.0.1"` forces a real TCP loopback connection instead and worked immediately. A subtle, easy-to-miss gotcha since the hosting portal itself displays "localhost" as the connection host, which reads as correct until it silently isn't.
2. **The `Authorization` header never reached PHP at all** — `bearer_token_from_headers()` already checked three fallback sources (`HTTP_AUTHORIZATION`, `REDIRECT_HTTP_AUTHORIZATION`, `getallheaders()`) defensively, on the reasonable assumption this is a known-possible issue on shared Apache/PHP hosting — but on this account, all three came back empty until an `.htaccess` rule (`RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]`) was added to `httpdocs/`. Shipped as a real, required file in the repo now, not left as an optional troubleshooting suggestion the way a first draft of the README described it — testing turned "might be needed" into "confirmed needed here."

**Fully tested end to end over real HTTP against the live server** — not hand-traced, actually exercised: login (correct and wrong credentials, missing fields), create, list, get-by-id, update, delete, get-after-delete (404), and no-token (401) all round-tripped correctly via `curl` against `https://test.planagonia.com`. Initially tested with `curl -k` (certificate verification skipped) since the subdomain had no valid HTTPS certificate yet at deploy time — issued shortly after via the hosting portal's own "HTTPS Optionen" panel, and re-confirmed working with full certificate verification on (no `-k` needed at all anymore).

**Status: built and confirmed working on the real target server, over real HTTPS** — the first piece of this entire project's backend work (D-019/D-021, decided back before F-001/F-002 were resolved) that's gone from design to a genuinely tested, live, properly-secured deployment. Still stubbed: WordPress auth (D-019 itself), rate limiting, CORS (irrelevant until `docs/` actually calls this cross-origin), and any wiring from `docs/index.html` to use this at all — deliberately, matching this project's standing practice of validating a piece standalone before it touches the live product.

**Superseded by D-049: the WordPress side of D-019 is no longer stubbed either — the full auth chain is real and tested.**

## D-049 D-019 completed: real WordPress auth, no stub, tested end to end

The direct follow-up to D-048: with the storage service live, the last stubbed piece of the originally-designed backend (D-019's own credential verification) was built out for real rather than left as a permanent placeholder.

**A real, self-hosted WordPress instance, installed via the hosting portal's own one-click installer** at a dedicated subdomain, `auth.planagonia.com` — chosen specifically so it's clearly named for its one job (D-019: "WordPress never renders any of the app's UI," purely a REST API credential backend) and kept separate from `test.planagonia.com` (the storage service). **Confirmed core-only, not just configured that way and assumed:** the WordPress one-click installer had bundled its usual two stock plugins (`akismet`, `hello`) — both inactive by default, but deleted outright via WP-CLI rather than left inactive-but-present, so the account genuinely has zero installed plugins, not zero *active* ones. **A real, non-obvious blocker found and fixed, the same way every other real deployment finding this session was found — by testing, not by reading documentation about what should work:** WordPress's REST API (`/wp-json/...`) only routes correctly under *pretty* permalinks; the installer's default *plain* permalink structure (`?p=123`-style, WordPress's own out-of-the-box setting) causes `/wp-json/wp/v2/users/me` to 301-redirect to the site's own homepage instead of reaching the REST API at all — confirmed by actually requesting it and inspecting the redirect chain, not assumed from WordPress's own documentation. Regenerating `.htaccess` this way also confirmed the same `RewriteRule .* - [E=HTTP_AUTHORIZATION:...]` line D-048 had to add by hand for the storage service was *already* included in this hosting's own WP-CLI/Plesk `.htaccess` template — the Authorization-header-stripping issue is evidently a property of this specific hosting stack generally, not particular to hand-written PHP.

**`verify_credentials()` swapped from D-047/D-048's stub to the real implementation** written out as a comment since D-047 — HTTP Basic Auth against `/wp-json/wp/v2/users/me` with a WordPress Application Password (core since WP 5.6, not the account's real login password), trusting a `200` response and mapping WP's own user id/slug onto this service's local `users` table via the same `ensure_user()` lazy-creation path the stub already used. ## D-050 `docs/` wired to the backend — minimal: explicit save/load, not automatic sync

With both backend halves live and tested (D-047–D-049), the next step was asked directly: does `docs/` itself get connected now? Confirmed yes, with the scope narrowed first rather than assumed — asked directly whether this means replacing `localStorage` with account-based sync, adding automatic cross-device sync to the existing plan-switcher, or something smaller. Chosen: the minimal option — a signed-in session lets the active plan be explicitly pushed to or pulled from the cloud, `localStorage` unchanged as the default, no automatic sync and no conflict resolution to design.

**CORS added to the storage service first** (`storage-service-php/app/src/http.php`'s `apply_cors()`), since `docs/` (GitHub Pages) and the storage service (`test.planagonia.com`) are different origins — a browser preflights any cross-origin request carrying `Authorization` or a JSON `Content-Type` with an `OPTIONS` request, and won't expose the real response to the page's JS without a matching `Access-Control-Allow-Origin` on it either. Locked to `https://tminder.github.io` specifically (configurable via `config.local.php`'s new `allowed_origins`) rather than `"*"` — this API carries session tokens, not public data, so there's no reason to widen it past the one real caller. Must run before any auth check, including in `plans.php` — a preflight `OPTIONS` request never carries the real `Authorization` header, so gating CORS behind `require_session`-style logic would make every cross-origin call fail before the browser even attempts the real one. Tested directly against the live server with a simulated `Origin` header: both the preflight and a real `POST /session.php` come back with the correct headers.

**`docs/index.html` gained four toolbar controls** (Sign in…, a status label, Save to Cloud, Sign out — the latter two hidden until signed in) **and reused the existing plan-switcher rather than building a separate picker for cloud plans.** The switcher already has two `<optgroup>`s (My plans, New from example, D-043) — a third, "Cloud," is added once signed in, lazily populated via `GET /plans.php` (a separate async function, `refreshCloudGroup()`, rather than folding a network call into `refreshPlanSwitcher()` itself, which stays synchronous exactly as D-043 built it).

**Each local plan gained an optional `cloudId` field** (alongside D-043's existing `{id, name, text, updatedAt}`) — harmless to any code that doesn't know about it, since it's carried through `JSON.stringify` in `savePlansList()` like any other property. Set the first time a plan is saved to the cloud (a `POST` creates it and records the returned id); every save after that is a `PUT` against the same id instead of creating a duplicate. Opening a cloud plan that's already linked to a local one (`cloudId` matches) switches to that local copy rather than importing a second, disconnected duplicate of the same plan — the same plan opened from two entry points (the local list and the cloud list) resolves to one local plan, not two.

**Session token lives in `sessionStorage`, not `localStorage`** — deliberately: the storage service's own tokens are short-lived (1 hour, D-021), so persisting one indefinitely in `localStorage` would mean "silently expired, next call just 401s" more often, for no real convenience gain, versus `sessionStorage`'s natural "signed in for this tab's lifetime" scope. A `401` from any cloud call (checked once, in a shared `cloudFetch()` wrapper every cloud-authenticated call goes through) clears the session and flips the UI back to signed-out, rather than leaving a stale "signed in as X" label that no longer works.

**Sign-in itself is two sequential `prompt()`s (username, then WordPress Application Password)** — not a proper form — matching this project's established minimal-native-dialog pattern (D-043's Rename already uses `prompt()`) rather than building custom modal UI for a first, minimal integration. The prompt explicitly says "Application Password, not your regular login password," since entering a real WordPress account password here would be the wrong credential entirely (D-019's whole reason for using Application Passwords) and a real, easy mistake to make otherwise.

**Status: confirmed working in a real browser.** Sign-in, Save to Cloud, and loading the saved plan back via the plan-switcher's "Cloud" group were all exercised directly by the user against the live deployment — the CORS'd `fetch()` calls, `sessionStorage` token handling, and the `cloudId`-tracking logic all worked as hand-traced. This closes out the entire D-019/D-021/D-050 backend arc: every piece, server-side and frontend, is now both built and genuinely tested, not just designed or hand-traced.

## D-056 Rate limiting, closing D-022's open gap for real

Requested directly as the concrete next step once Homepage/Documentation/Profile were all live (D-051–D-055): rate limiting had been named as an open gap since D-022, and became directly load-bearing rather than theoretical the moment self-service registration was raised and deliberately deferred specifically until this existed (D-055's own decisions.md entry). Closing it was the one remaining precondition for that deferral, not a new idea introduced here.

**Fixed-window counter, not a sliding window or token bucket** — a deliberately simpler mechanism than either, chosen because this project's actual scale (a small prototype, not a high-traffic API) doesn't need the smoother rate curve a more sophisticated algorithm buys, and a fixed window is easy to reason about and verify by hand (this project's standing constraint, no execution environment for anything but real HTTP testing against the live server). Accepted, understood tradeoff: a burst exactly at a window boundary can momentarily allow close to 2x the stated limit — not a bug, a known property of the simpler approach.

**State lives in the same MySQL database, not a new service or an in-memory cache.** A new `rate_limits` table (`bucket_key` primary key, `window_start`, `count`) added to `db.php`'s existing schema-creation block. Considered and rejected: APCu or a file-based counter — faster, but per-PHP-FPM-process without confirming this specific hosting even has an in-memory cache extension enabled, where MySQL is the already-established, confirmed-correct-across-every-worker-process mechanism this whole service already depends on (D-048).

**Two different identities for two different trust situations, not the same bucket key everywhere.** `POST /session.php` (no authenticated identity yet — it *is* the auth step) is limited by IP, 10 attempts per 15 minutes; deliberately not by attempted username, since limiting by username would let an attacker exhaust a real user's own login attempts just by guessing their name repeatedly. `/plans.php` (token already validated by this point) is limited by user id instead, 300 requests per 15 minutes — meaningfully identifies a real account rather than an IP that might be shared (NAT, a shared network) by multiple legitimate users, and set generous relative to how the app actually calls this endpoint (an explicit Save/Load-to-Cloud action or opening Profile's plan list, never per keystroke or drag).

**Opportunistic cleanup instead of a cron job** — every rate-limit check also deletes rows from expired windows, an indexed range delete cheap enough at this project's real request volume, avoiding a dependency on scheduled-task access this shared hosting account may or may not actually offer.

**Confirmed against the live server, not just reasoned through:** 10 rapid wrong-password attempts against `POST /session.php` each correctly returned `401` (rate limit not yet hit, `verify_credentials` still ran normally); the 11th correctly returned `429` with a `Retry-After: 900` header, *before* any WP REST API call was attempted for it — the expensive, attackable operation is what the limiter actually protects. A normal login and `GET /plans.php` immediately afterward (once the test lockout was manually cleared) both still succeeded normally, confirming the limiter doesn't interfere with legitimate use at real volumes.

**Status: built, deployed to `api.planagonia.com`, and verified working end to end against the live server** — not just hand-traced. Registration itself is still not built — this closes its stated precondition, not the feature.

## D-058 Self-service registration, the deferred feature from D-055, now built

D-056 closed the stated precondition (rate limiting); this closes the feature itself. Two real design questions were resolved directly with the user before writing any code, rather than picked silently, given how much more consequential this is than anything else built this session — see the two decisions below.

**Decision 1: a dedicated bot-Administrator WordPress account, not a custom role.** Creating another WordPress user via the REST API needs `create_users` (and, to also hand that new user an Application Password on their behalf without making them do it themselves, `edit_users`) — capabilities WordPress core only grants to the Administrator role, with no narrower built-in option. A genuinely restricted "can only create subscriber accounts" role would need custom code running inside WordPress — a plugin or mu-plugin — which D-019 deliberately avoids specifically to keep the auth-relevant surface limited to WP core's own strong auto-update track record. Asked directly rather than assumed: keep the constraint, accept a full-admin credential as the cost, isolated in its own dedicated account (`planagonia-bot`, not the site owner's real `tobiasminder` login) so it can be revoked/rotated independently and its actions stay attributable to "the registration bot" specifically. This is the single most privileged credential anywhere in this project — everything else built so far only ever verifies an *existing* account's own credentials or reads/writes that one account's own data.

**Decision 2: email verification before an account can sign in, not immediate activation.** Asked directly rather than defaulted to the simpler no-verification path — chosen despite two real, then-untested risks: shared hosting's mail deliverability, and PHP's `mail()` function working at all inside the restricted environment this project builds from. Both checked before writing the verification flow, not assumed: `mail()` from the SSH jail's own CLI failed outright (`sh: /usr/sbin/sendmail: not found`, consistent with the jail's already-established minimalism, D-048) — but a request through the actual **web-serving** PHP-FPM process (a small test script, `curl`'d) returned `mail() returned true`, confirming the jail's limitation doesn't extend to the real request path. Domain-level mail authentication was also checked directly via DNS rather than assumed absent: `planagonia.com` already has a correctly configured SPF record (`include:spf.hostfactory.ch`), a published DKIM key, and a DMARC policy (`p=quarantine`) — real infrastructure the hosting account already had, not something built here, substantially de-risking (not eliminating) the spam-folder concern raised directly by the user before proceeding.

**The actual account-creation flow needed a second correction after the first version, found only by testing the complete path, not by review of the pieces individually.** The first draft had `register.php` create the WordPress account with the visitor's own chosen password and stop there, assuming that password could later be used to sign in. Testing the full path end to end (register → attempt login) surfaced the real problem immediately: a self-registered account's own WordPress login password can never authenticate against the REST API at all — Basic Auth there has only ever accepted an Application Password in this entire project (every prior login, D-019 onward, used one), never the account's real password, which was never a mistake to fix so much as a fact this design hadn't accounted for yet. Fixed by moving Application-Password generation to `verify.php` instead, at the moment the emailed link is actually clicked — the bot-admin account generates one *for* the newly-verified user and displays it once, so a visitor never needs to know their WordPress account even has a separate "real" password, let alone visit `wp-admin` to generate a working credential themselves. This is the same reasoning D-019 used from the start (WordPress never renders the app's own UI) carried all the way through registration, not just ordinary sign-in — the fix wasn't just "make it work," it was "make it work the way this project already committed to."

**Concretely, three new endpoints and one schema change:**
- `POST /register.php` — validates input, rate-limits by IP (5/hour — deliberately stricter than login's own 10/15min, since spam account creation is the specific threat this endpoint exists to resist), creates the WordPress account via the bot-admin (server-side `roles: ["subscriber"]`, never accepted from the caller), inserts a local `users` row with `verified = 0` plus a random 32-byte token good for 24 hours, and emails the confirmation link. Returns a plain confirmation message — never a session token, since there is nothing valid to sign in with yet.
- `GET /verify.php?token=X` — the one HTML-rendering endpoint in an otherwise pure-JSON API, since a link clicked from an email client needs a real page. Consumes the token (valid once, then cleared either way, expired-or-not), marks the account verified, generates the Application Password, and shows it exactly once alongside a link to Profile.
- `auth.php` gained an `AccountNotVerifiedException`, thrown by `verify_credentials()` when WordPress's own auth check genuinely succeeds but the local `verified` flag is still `0` — kept distinct from a plain `401` so the frontend can eventually say something more useful than "wrong password" for a case where the password was actually right. `ensure_user()` (the lazy-creation path for accounts that never went through registration, e.g. WP-CLI-provisioned ones) defaults new rows to `verified = 1` — an admin-created account never needed verification and shouldn't retroactively require it.
- `users` table gained `verified`/`verify_token`/`verify_token_expires` via `ALTER TABLE`, guarded with try/catch per column rather than checking `INFORMATION_SCHEMA` first, since this hosting's exact MySQL/MariaDB version was never pinned down anywhere in this project and the try/catch approach works regardless of which one actually supports `ADD COLUMN IF NOT EXISTS`.

**Frontend: a toggle between Sign In and Create Account sharing one card on Profile**, not a separate page — registration is an occasional detour from signing in, not a destination worth its own URL and its own copy of the shared header/footer chrome (D-055). Deliberately duplicates the same "no build step" pattern already established (D-050/D-055) rather than sharing code with either.

**Fully tested end to end against the live server, including the parts that first drafts got wrong:** registered a real test account (rejected once, correctly, for a genuinely duplicate email — proving WordPress's own validation and this service's error-relaying both work); confirmed the local row inserted as `verified = 0` with a real token; confirmed the *original* design's login attempt correctly failed (the real bug this test surfaced); fixed the design; confirmed the verification link works exactly once (a second click on the same link correctly shows "not valid"); confirmed the generated Application Password successfully signs in and lists plans normally afterward. Test account and its generated credentials torn down afterward, matching this session's standing practice (D-052) of not leaving exposed test credentials live once a test is done.

**Status: built, deployed, and verified end to end on the live server** — the whole D-019/D-021 backend arc (D-047 through D-058) now supports the complete lifecycle a real product needs: register, verify, sign in, use, all without WordPress's own UI ever being shown to a visitor. Still open: resending a verification email if the first one doesn't arrive or the link expires, and any of this project's own UI for account management (rename, delete, rotate the Application Password) — both flagged in the storage service's own README rather than silently missing.

**Addendum, same day: the `username` field was removed from the registration form entirely.** Directly challenged by the user ("why username?") — a fair question, since WordPress needs a username as its own internal concept, but nothing about *this* project actually needs the visitor to invent one; email + password is the whole identity a visitor cares about, same as everywhere else on Profile. Fixed by deriving it server-side instead: `derive_username()` in `registration.php` lowercases the email's local part and strips it to what WordPress's own username rules accept (falling back to the literal string `user` if that leaves nothing usable, e.g. an address starting with only symbols). `create_wp_user()` now loops on collision — checking specifically for WordPress's own `existing_user_login` error code, retrying with a numeric suffix up to 20 times — while any other rejection (`existing_user_email`, an invalid password, etc.) fails immediately without retrying, since a different username wouldn't fix those. Confirmed directly against the live server, not just by reading the code: registering `mail+regtest2@tobiasminder.ch` derived `mailregtest2`; registering a second, genuinely different address that sanitizes to the same base (`mail!!regtest2@tobiasminder.ch`, symbols stripped) correctly landed on `mailregtest21` — the collision path actually firing, not just present in the source. Incidentally re-confirmed WordPress treats email addresses as case-insensitive for uniqueness (a third attempt using the same address in uppercase was rejected as a duplicate *email*, not retried as a username collision — the correct behavior, since it's the same address). Both test accounts and their rows were torn down after the test, matching this project's standing no-live-test-exposure practice. `register.php`'s request body is now just `{ email, password }`; `profile/index.html`'s registration form and its submit handler lost the username field and its label.

## D-059 A real drag bug, reported as "polygon node movement doesn't work" — the interactivity module could go silently inactive on a plan it never declared

Reported directly by the user against `docs/`, the live app — not something code review had flagged. Confirmed and root-caused by actually driving a real browser against `docs/index.html` (installed Playwright + a headless Chromium into this session specifically to do it, since no browser/Node is otherwise available here — see D-047's own standing note on this project's lack of a local execution environment), not by hand-tracing: this project's own established practice for a reported UI bug is to reproduce it live before touching any code.

**First reproduction attempt didn't reproduce anything.** Dragging both of `docs/`'s shipped polygon elements (`rug` in the apartment example, `grundstueck` — itself a parent with rect/polyline children and `allowSelfIntersectingPolygons: false` active — in the utility example) worked correctly: points updated, the SVG moved by the exact drag delta, no console errors, no regression from D-058 or anything else recent.

**Reproduced instead with a plan built from scratch: a `polygon` whose points reference sibling corner elements** (D-018's shared-corner pattern, the way this language's own shipped *walls* are built, just never previously tried for a `shape: "polygon"` in a plan pasted straight into the editor). Dragging the corner did nothing at all — no error, no warning in `dragmsg`, no change to the source text, and (confirmed directly, not assumed) `applyDrag`'s own `nothing solvable to drag` message never fired either, ruling out every code path that logs a reason. That absence of even a warning was the actual clue.

**Root cause: `rerender()` (`docs/index.html`, wired to every `input` event on the source textarea) calls `deactivateRemovedModules(parsed.modules)` using the *current text's own* module declarations, unconditionally** — any module not named in `parsed.modules` gets its cleanup run and is fully torn down, including its DOM event listeners. `withAutoModules()` (D-034: "every plan gets interactivity by default") only bakes the three shipped modules' declarations into a plan's *text* at specific entry points — new plan, load example, load a saved/cloud plan — never inside `rerender()` itself. A plan that reaches the editor any other way — typed directly, or (the actual D-003 workflow this whole language was designed around) an AI-generated plan pasted in wholesale to replace the current source — almost certainly won't itself declare `module "interactivity-module.js"`, since D-034's entire premise is that a plan author shouldn't have to know that declaration exists. The very next `input` event after such a paste tears the interactivity module down, silently: dragging is gone, with no error and no visible sign why, for as long as that declaration stays missing. My own first test plan (typed via a direct `sourceEl.value =` + dispatched `input` event, deliberately without any `module` line, to test the corner-ref-polygon case in isolation) hit exactly this — not a fabricated edge case, the same mechanism a real paste-in-a-generated-plan session would hit.

**Fix: `rerender()` now always keeps the three shipped modules active, regardless of what the current text happens to declare** — `requiredModules = [...new Set([...AUTO_MODULES, ...parsed.modules])]`, passed to both `deactivateRemovedModules` and `ensureModulesLoaded` in place of the raw `parsed.modules`. Deliberately does **not** rewrite `sourceEl.value` the way `withAutoModules()` does — D-006's "the code pane is the source of truth" means silently injecting text into what the user is looking at and editing would be its own surprise, worse than the bug; keeping the *behavior* on without touching the *visible source* was the smaller, more honest fix. No opt-out was removed by this, since none existed: D-034 never described a way for a plan to deliberately disable its own interactivity, only ways this bug accidentally caused it.

**Verified fixed the same way it was found:** re-ran the exact failing corner-ref-polygon plan (still with zero `module` declarations) against the patched file — the corner now drags correctly, the polygon's rendered points update, source text updates, no console errors. Re-ran both original shipped-example drags (`rug`, `grundstueck`) afterward as a regression check — both still work identically to before the fix, confirming `deactivateRemovedModules`/`ensureModulesLoaded` still correctly tear down and reload any *other*, non-shipped module a plan does declare and later removes (D-045's own `confirm()`-gated external-module lifecycle is untouched by this change, since `AUTO_MODULES` was already exactly the trusted set D-045's `isTrustedModule` carves out).

**Status: built and verified in a real browser.** No PHP/backend involvement — pure `docs/index.html` frontend fix. Test-only artifacts (the throwaway Playwright driver scripts and screenshots) stay in the session scratchpad, not the repo.

## D-067 Mobile-friendly, desktop-first — every page checked in a real narrow viewport, not just eyeballed

Requested directly ("make the website mobile friendly but keep desktop first policy"). Read "desktop-first" as a cascade-order constraint, not a vague vibe: every page's *base* CSS is the existing desktop design, completely untouched; every mobile adjustment lives inside a `@media (max-width: …)` override layered on top, matching the pattern this project's own pages already used in a couple of places (`homepage/index.html`'s and `site-docs/index.html`'s existing 760px/860px breakpoints) rather than switching to mobile-first `min-width` queries anywhere. Confirmed via Playwright, not assumed: measured `document.documentElement.scrollWidth` against `clientWidth` at a 390px viewport (a real, common phone width) across all five pages — Homepage, Docs, Profile, Impressum, and the App — plus re-checked a 1400px desktop viewport for each afterward to confirm nothing there changed.

**Two real overflow bugs found this way, on the first pass, neither guessable from reading the CSS alone:**
- **Homepage's `.author-diagram`** (the "you describe it → AI writes the plan → you review & adjust" three-box row) had no mobile handling at all — three `min-width: 8.5rem` boxes plus arrows simply don't fit in 390px, and `section.author .row`'s existing `grid-template-columns: 1fr` rule only ever stacked the *text* column above the *diagram* column, never touched the diagram's own internal row. Fixed by stacking the three boxes vertically and rotating the arrow 90° under the same breakpoint.
- **Docs' two-column `.layout` grid** (the 220px TOC + content grid) still overflowed even after its own existing `grid-template-columns: 1fr` mobile rule collapsed it to one column — a CSS grid item's default `min-width` is its own content's min-content size, not 0, the exact grid-layout counterpart of the flex `min-width: 0` trap `docs/index.html`'s own CSS already carries a comment about. A long unbreakable token anywhere in `main.content` kept the column, and the whole page, wider than the viewport regardless of the column count. Fixed with `.layout > * { min-width: 0; }` inside the existing mobile breakpoint. Also wrapped both `table.ref` reference tables in a `.table-scroll { overflow-x: auto }` container — not yet observed overflowing on the two current tables' own content, but a table is exactly the kind of wide content this project's own artifact/design conventions already know to guard defensively.

**Shared header/nav, one real fix duplicated across the four chrome-sharing pages** (Homepage/Docs/Profile/Impressum — matching D-034's established "small logic and markup duplicated per static page" pattern, same as the cookie notice and the footer already are): `header.site` had no `flex-wrap`, so the wordmark plus three-or-four nav links had nowhere to go below the width they stopped fitting on one line — not yet an overflow at 390px only because the links happen to be short, but a fragile near-miss, not a real fix. Added `flex-wrap: wrap` plus a margin adjustment for the wrapped state, and `flex-direction: column` for the footer's own nav row, under a new `@media (max-width: 640px)` block on each of the four pages (folded into Homepage's and Docs' existing breakpoints where one already existed).

**The App (`docs/index.html`) needed the most real work, since D-006's two-pane code+viewer split is inherently a desktop layout** — a fixed 420px-wide textarea leaves nothing for the viewer on a phone. Added a 760px breakpoint that stacks the panes vertically (`flex-direction: column`, each pane getting a flex-basis and a min-height rather than a fixed size) instead of side by side; the header's existing `flex-wrap: wrap` already handled the toolbar's own many buttons once given room to wrap onto several rows. Also added `touch-action: none` to the SVG's interactive elements (`.obj`, `.anchor-hit`) — without it, a touch-drag gesture starting on a plan element risks the browser's own default touch handling (page pan/scroll) contesting the pointer-event-driven drag this app already implements; safe to disable here specifically because `#plan-root` never natively scrolls on its own (the SVG is always fit to its container, D-035), so there's no native touch gesture being taken away.

**A second real bug, found only by actually testing a drag gesture on the new mobile layout, not by re-checking overflow:** the existing cookie notice (D-064) is `position: fixed; bottom: 1rem`, correct and harmless on every normally-scrolling page — but on the App's new short, non-scrolling stacked layout, that fixed bottom placement sat directly on top of the viewer pane, and (confirmed via `elementFromPoint`, not assumed) silently absorbed every pointer event meant for the plan underneath it until dismissed — dragging a shipped example's own polygon element landed on the banner's `<p>` instead of the plan. Fixed by repositioning it to the top and shrinking it, but only inside the App's own mobile breakpoint (the other three pages keep the bottom placement — nothing wrong with it there, since normal page scroll means it's never blocking the one thing the page is for). **A second mistake in that fix, also only caught by re-testing rather than trusting the diff:** the first attempt placed the override *before* `.cookie-notice`'s own base rule in the stylesheet — same specificity, so the later base rule's `bottom: 1rem` silently won the cascade regardless of which media query matched, and with both `top` and `bottom` now set on a `position: fixed` element with `height: auto`, the browser solves for height by stretching it to fill the gap — the notice silently grew to cover ~97% of the viewport's height instead of shrinking. Fixed by moving the override to *after* the base rule, confirmed via the same `elementFromPoint`/bounding-box check, then a full drag re-test end to end (`elementFromPoint` correctly resolves to the plan element again, the drag commits, the polygon's rendered points update) — the same "trace before trusting" practice this project has followed since its very first backend bug (D-047 onward), applied here to CSS cascade order instead of server code.

**Explicitly not attempted:** no mobile-specific redesign of anything's visual language, no separate mobile stylesheet, no changes to any interaction *logic* (only `touch-action`, a CSS hint, and layout geometry) — matching the "keep desktop-first policy" instruction literally, not just in spirit.

**Status: built and verified in a real (headless) browser at both a 390px mobile viewport and a 1400px desktop viewport, on all five pages, including an actual touch-style drag gesture on the App** — not just an overflow check. Deployed to the live server.
