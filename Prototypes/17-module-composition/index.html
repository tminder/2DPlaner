Prototype 17: module-provided composition (wall-with-door)

Tests D-011/F-002's third, never-attempted module promise: can a module offer a reusable, higher-level building block "composed from Element and Connection" — the exact illustrative example language.md itself uses — rather than the plan's author hand-writing every corner (D-018's pattern, as every shipped wall/door currently does)? wall-with-door-module.js registers a new core hook, core.registerBeforeRender(cb), and uses it to expand any element { compose: "wallWithDoor", from, to, doorAt, doorWidth } into the same three-piece wall_a/door/wall_b structure the apartment example's author currently writes by hand as four corner elements plus three polylines — entirely before core ever renders, so rendering itself needed zero composition-specific code: the synthesized nodes are ordinary polyline Elements, indistinguishable from ones typed directly. Two walls below, sharing a corner, each with its own door position — demonstrating actual reuse, not a one-off.

Scope: rendering only, matching how Prototype 12 first tested modules rendering-only before Prototype 14 tried interactivity. Not attempted: dragging a synthesized child, or the composite's own position offsetting its children (assumed [0,0] here) — see this prototype's write-up in decisions.md for why the drag gap is a real, separate problem, not just an oversight. Not testing dynamic module loading via a plan's own module "..." declaration either — already validated in Prototypes 12/14; this is purely about the new hook a loaded module would call, so it's just a plain <script> tag below. The composite element itself has no shape, so it also renders its own small anchor dot at its start point (core's existing, unrelated behavior for any shapeless element) — a known cosmetic side-effect, not a bug this test introduces.
