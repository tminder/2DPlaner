2DPlaner prototype: interactivity as a module

Terminology note: this prototype predates D-033's rename of the node keyword to element and allowUnrealisticPolygons to allowSelfIntersectingPolygons — kept as originally built, not rewritten. See 15 for the current names.

Same studio-apartment plan as 13, restructured so the core page only tokenizes, parses, and renders — no drag, no selection, no click handling of any kind beyond "typing in the editor re-renders the preview". Every interactive behavior (drag-to-move with solve-backward/realism-check, click-to-select, connect/disconnect icons with snap, hover previews, the right-click context menu with Delete Element) lives entirely in interactivity-module.js, loaded like any other external module (D-020) — declared in the plan's own preamble as module "interactivity-module.js", exactly the same mechanism a shape-rendering module uses. This is the first test of D-011's other promise ("modules can add new interactivity") — every earlier module prototype (12, reused in 13) only ever contributed a shape renderer.

The core exposes a small API, window.PlanCore, for the module to build on: parse/render, the editable-literal helpers (numOf/isEditable/formatNumber), the geometry helpers a drag needs (computePositions/computeCornerUsers/ resolvePointAbs/nodeDragEdits/connectedNodeIds), rootEl/sourceEl/dragmsgEl as DOM mount points, the scale constant M, rerender(opts) / onRendered(cb) to trigger a re-render and react once it's done, and registerModuleCleanup(name, fn) — try deleting the module "interactivity-module.js" line from the plan below: the plan keeps rendering, but dragging/selecting/right-clicking stop doing anything, and #modlog logs the teardown. Add the line back and it reloads fresh. Earlier versions of this prototype didn't have this — once loaded, the module just kept running forever regardless of whether the plan still declared it, since core's "loaded" tracking was designed for a stateless shape renderer with nothing to undo. See the page's bottom note for what else this API deliberately does and doesn't cover.

Three real seams, not hidden: (1) connect/disconnect icons are entirely the module's own overlay, appended into the SVG after core's own output — including core's anchors, which D-018 requires painting last — so icons now end up on top of anchors, a reversal of 13-unified's ordering (harmless here, since none of this plan's icons and anchors actually coincide, but a real, undecided question for a plan where they would). (2) D-026's label hover-reveal is core's own CSS rule (a rendering feature, unaware interactivity exists) — suppressing it during a drag needs the module to inject a higher-specificity override rather than core ever mentioning "dragging". (3) rerender(opts.preserveViewBox) makes the caller responsible for saying whether this edit continues a gesture in progress or starts a fresh one — core can no longer infer that itself (it used to distinguish "did the textarea's own input event fire" from a module-driven change), so the API had to make that call explicit instead of implicit.
