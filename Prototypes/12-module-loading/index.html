2DPlaner prototype: loading modules

Tests core aim #3 directly — no prototype had ever actually loaded or run a module before this one, despite module "..." being documented syntax (D-020) since early on. Two module declarations in the preamble below: "star-tool" resolves against a small built-in registry bundled in this page's own script (representing "ships with the app"); "heart-module.js" is fetched at runtime from a separate file sitting next to this one (representing "external, loaded from wherever the URL points"). Neither star nor heart is a shape the core renderer knows about — both only exist because their module registered a renderer function for that shape name.

A minimal module API surface, tried for the first time here (F-002 remains open — this is one rough attempt, not a proposal): a module calls PlanModules[shapeName] = (node, ownAbs, M, helpers) => svgMarkupString. The core renderer, when it meets a shape value it doesn't recognize (not rect/line/polygon/circle), checks that registry before falling back to D-016's invisible-anchor default — so a module can add an entirely new visual shape without the core needing to know it exists in advance.

Known gaps, on purpose: no sandboxing (matches D-020's decision — trusted like an npm package, not an untrusted download), no version/conflict handling if two modules registered the same shape name, and the module only gets to contribute *rendering* — it can't yet hook into drag behavior or add new primitives beyond a shape renderer. D-020 said modules should eventually reach further than this; this prototype only tests the rendering-extension slice.
